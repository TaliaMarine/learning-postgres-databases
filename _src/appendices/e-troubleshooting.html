PostgreSQL's error messages are precise, and most tell you what to do next. This annex lists the ones you will meet while working through the course: the exact text, what causes it, and how to fix it. Each message below was reproduced on the course's PostgreSQL 18 container, in a scratch database that was dropped afterwards.

How to read an error

An error has up to four parts: the ERROR: (or FATAL:) line, then optional DETAIL:, HINT: and CONTEXT: lines. Read the DETAIL first; it usually names the exact object or row. ERROR means this statement failed. FATAL means the connection itself was refused or closed. In a transaction, any ERROR aborts the whole transaction until you ROLLBACK.

1. permission denied for schema

Cause. To use anything inside a schema, a role needs USAGE on the schema itself, in addition to a privilege on the object. Access to the table alone is not enough.

Fix. Grant the schema privilege (you need to be the schema's owner or a superuser):

Check what the role has with \dn+ or the schema-privileges query in annex C. Details: lesson 4.

2. permission denied for table

Cause. The role can reach the schema, but has no privilege on the table for this operation. Note the name is the table's own name, without the schema. The same message appears for views, with the word view, and for sequences (permission denied for sequence), which an INSERT into a table with a serial or identity column may need.

Fix. Grant the specific privilege the statement needs:

Grants apply to existing objects only

GRANT … ON ALL TABLES IN SCHEMA covers the tables that exist now. Tables created later need ALTER DEFAULT PRIVILEGES (lesson 4).

3. role “…” does not exist

Cause. The first form comes from a statement such as SET ROLE, GRANT or ALTER ROLE that names a role that is not there. The second is a failed login. Either you misspelled it, or the role was never created, or it was dropped. Roles belong to the whole cluster, not to a database, so it is never a matter of being in the wrong database.

Fix. List the roles with \du and compare the spelling. If the exercise you are on needs the role, create it. Remember that case matters when a role is quoted: "Maria" and maria are different roles. If the course checker removed your lab_ roles for you, that is expected (lesson 3).

4. password authentication failed

Cause. The server asked for a password and the one supplied was wrong, missing, or belongs to another role. In the course container this only happens on a connection that is not from the local socket or from 127.0.0.1, because those use trust and never ask. A connection from another address (another container, or the container's own network address) must give the password (lesson 3).

Fix.

  • Check the password, and the user name in the connection string (it is case-sensitive when quoted).
  • A role created with no password cannot pass a password method at all. Set one: alter role the_role password '…'.
  • A role whose VALID UNTIL date has passed is rejected with the same message.
  • Look at the server log (./pg logs). The client always sees the same vague message, but the log adds the reason on a DETAIL line: User "…" has no password assigned., User "…" has an expired password., or, for a wrong password, no extra reason, just the pg_hba.conf line that matched.

For the course's own database the superuser password is course. That is a local-lab convenience; never use it, or a password this simple, anywhere real.

5. could not connect to server

Cause. Nothing is listening where the client looked. A wrong port gives exactly this. The variant for a local socket reads connection to server on socket "…/.s.PGSQL.5999" failed: No such file or directory. In the course the usual reasons are that the container is not running, is still starting, or you used a different port from 55432.

What to check, in order:

  1. ./pg status prints ready when the database accepts connections, or tells you to run ./pg up.
  2. docker ps should list a container whose name starts with pgcourse. If Docker itself is not running, start Docker Desktop first.
  3. ./pg logs shows why a container stopped. A seed script that failed on first start leaves it exiting; ./pg reset starts again from a clean volume (it deletes your changes).
  4. Another program may already use port 55432. Start the course on another with PG_PORT=55433 ./pg up.
  5. Right after ./pg up the server can need a few seconds. ./pg up waits until it is ready; a client that connects at once may see the database system is starting up. Wait and retry.

From your own machine, the connection is host 127.0.0.1, port 55432, user postgres, password course, database shop. From inside the container, no host or port is needed at all.

6. database “…” is being accessed by other users

Cause. DROP DATABASE (and CREATE DATABASE … TEMPLATE, and renaming) need that no one else is connected to the database. Often the "other session" is a forgotten psql window or an application. It is never your own current connection: you cannot drop the database you are in.

Fix. Connect to a different database (for example postgres), find the sessions, and either close them yourself or let PostgreSQL do it:

WITH (FORCE) disconnects people

It kills every session on that database, without asking. Use it for scratch databases, never for one a colleague or an application is using. The course helper uses it for its lab_ databases.

7. deadlock detected

Cause. Two transactions each hold a lock the other needs: one updated row 1 then wants row 2, while the other updated row 2 then wants row 1. Neither can go on. After deadlock_timeout (one second by default) PostgreSQL picks one transaction and cancels it with this error. The other one then succeeds.

Fix.

  • The cancelled transaction was rolled back completely. Your application should catch the error (SQLSTATE 40P01) and retry the whole transaction.
  • Prevent it: always touch rows and tables in the same order in every code path (for example, lowest id first), and keep transactions short.
  • log_lock_waits is on in the course container, so ./pg logs shows who waited on whom.

A walk-through with two sessions is in lesson 16.

8. could not serialize access due to concurrent update

Cause. Your transaction runs at REPEATABLE READ (or SERIALIZABLE), so it works on a snapshot from when it began. It tried to change a row that another transaction changed and committed after that snapshot. PostgreSQL will not let you overwrite a version you could not see. At the default READ COMMITTED level you do not get this error; the update simply re-reads the new row. Under SERIALIZABLE you may also see could not serialize access due to read/write dependencies among transactions.

Fix. This is not a bug to remove but a signal to retry: roll back and run the whole transaction again from the start (SQLSTATE 40001). Applications that use these isolation levels need a retry loop. If you do not need the stronger guarantee, use READ COMMITTED; if you do, keep the transaction short so conflicts are rare. See lesson 15.

9. canceling statement due to statement timeout

Cause. A statement ran longer than statement_timeout, which is 0 (no limit) by default in the course container, but is often set per role, per database, or by the application's connection string on real systems. The statement is cancelled; a surrounding transaction is aborted.

10. duplicate key value violates unique constraint

Cause. The statement would create a second row with a value that a UNIQUE or PRIMARY KEY constraint allows only once. The message names the constraint and the value. A frequent surprise: an identity or serial column that is out of step with the data, usually after rows were inserted with explicit ids or loaded with COPY, so the next generated id collides with an existing one.

Fix.

  • If it is a real duplicate, decide what you want: skip it (INSERT … ON CONFLICT DO NOTHING), update the existing row (ON CONFLICT … DO UPDATE, lesson 9), or fix the data.
  • If it is a sequence out of step, move it past the largest id: select setval(pg_get_serial_sequence('shop.t', 'id'), (select max(id) from shop.t));

11. null value in column “…” violates not-null constraint

Cause. The row has no value for a column declared NOT NULL and that has no DEFAULT. Leaving a column out of an INSERT gives it its default, or NULL if there is none. The DETAIL line prints the whole failing row, in column order, which is the quickest way to spot the missing value (here the last one, created_at).

Fix. Supply the value in the INSERT, or give the column a default (alter table … alter column … set default now()). Do not remove NOT NULL just to make the error go away; the rule is there because the data is meaningless without it.

12. relation “…” does not exist

Cause. “Relation” means table, view, index or sequence. In the course the usual reason is that the table exists, but not in a schema on your search_path. A name written without a schema is looked up only in the schemas of the path, and the default path is "$user", public. The shop tables are in the shop schema. Other causes: a typo; the object was created in another database (you are connected to postgres instead of shop); or the name was created with quotes and capitals ("Orders" is not orders).

Fix.

Also see "schema … does not exist" (a typo in the schema) and "column … does not exist" (look for a misspelling, and remember that a column alias cannot be used in WHERE; annex A1). The search_path is explained in lesson 2.

13. cannot drop … because other objects depend on it

Cause. Something else is built on the object: a foreign key from another table, a view, a function that uses its row type, or (for a role) objects it owns. PostgreSQL refuses by default, so you cannot break things by accident. The DETAIL lists every dependent.

Fix. Read the list, then choose:

  • Drop or change the dependents first, in the right order.
  • Or add CASCADE, which drops them too. It is correct when you mean to remove the whole cluster of related things, and dangerous otherwise. Run the plain DROP inside BEGIN … ROLLBACK first to see the list, and only then decide.

The same pattern for roles reads ERROR: role "lab_s91_o" cannot be dropped because some objects depend on it with DETAIL: owner of table shop.owned_by_o. Reassign or drop what it owns first: REASSIGN OWNED BY x TO y; then DROP OWNED BY x;, in every database where it owns something, then DROP ROLE x; (all three were run to check this).

14. too many connections

Cause. The server allows max_connections clients at once (100 in the course container), and every one is taken; or a role with CONNECTION LIMIT n already has n sessions. A few slots (superuser_reserved_connections, 3 here) stay free for superusers, so you can usually still log in as postgres to investigate. There is a third variant, too many connections for database, for a per-database limit.

Fix. See who is using the connections (the query is in annex C):

Many idle sessions from one application mean it opens connections it does not close or share: fix the application's pool size, or put a pooler such as pgbouncer in front. Raising max_connections is the last resort; each connection is a process with its own memory (lesson 26).

15. out of shared memory

Cause. Despite the name, this is rarely about memory. PostgreSQL keeps all locks in a shared table sized at server start from max_locks_per_transaction × (max_connections + prepared transactions) (64 × 100 in the course container, with some spare room). One transaction that touches a very large number of objects, such as a table with thousands of partitions, a script that locks or drops thousands of tables, or a long transaction that opens many tables, can use it all up. Every index of a table you read takes a lock too.

To reproduce it in a scratch database we created 25,000 small tables and locked them all in one transaction; a smaller number did not fail, because the table has spare capacity.

Fix.

  • Do the work in smaller transactions (commit every few hundred objects).
  • Or raise max_locks_per_transaction. It needs a server restart, because the table is allocated at start-up.
  • For partitioned tables, queries should filter on the partition key so only some partitions are locked (lesson 20).

16. no space left on device

These two lines are the standard shape of the message and were not reproduced, because doing so would fill the disk the whole Docker setup runs on. The relation number and path will differ on your machine. The first form fails one statement. The second, from the write-ahead log, is a PANIC and stops the server; it restarts and recovers once there is space again, but cannot start if there is still none.

Cause, in the course. Docker stores the database in a volume (pgcourse_pgdata) on Docker's own disk, which is shared with every image, container, and build cache you have. When that fills, PostgreSQL cannot write. In production, the usual culprits are a growing table or index, WAL piling up behind an abandoned replication slot or a failing archive command, a runaway temporary file from a huge sort, or logs.

Fix.

  1. Measure. In the container: ./pg exec df -h /var/lib/postgresql. On your machine: docker system df (this shows images, containers, volumes and build cache).
  2. Free space Docker is holding that you do not need: docker system prune removes stopped containers, unused networks and dangling images. docker builder prune clears build cache. Neither touches the running course database; do not add --volumes unless you want to delete data.
  3. In Docker Desktop, increase the disk image size (Settings, Resources).
  4. If the course data is the problem, ./pg reset recreates the database from scratch and gives the space back. It deletes your changes.
  5. In production, find what grew with the size queries in annex C and check replication slots (lesson 24) and the WAL archive (lesson 23).
