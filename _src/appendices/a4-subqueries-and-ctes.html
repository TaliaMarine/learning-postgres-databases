A subquery is a SELECT written inside another statement. A CTE (common table expression) is a named subquery you write at the top with WITH, so the main query reads top to bottom. This annex shows the three shapes a subquery can have, the three tests that use one (IN, EXISTS, NOT EXISTS), correlated subqueries, and CTEs.

Set up

The playgrounds run PostgreSQL 18 in your browser on a small copy of the shop (8 customers, 8 products, 12 orders). Customer 6 has never ordered and product 8 has never been sold; both help the examples. The same queries run on the Docker database with ./pg psql.

1. Scalar subquery: one value

A scalar subquery returns exactly one row with one column, and can be used anywhere a single value can. If it returns more than one row, PostgreSQL raises an error; if it returns none, the value is NULL. Wrap it in parentheses.

playground compare each product with the average price

2. Row subquery: several columns, one row

A row subquery returns one row with several columns, and you compare it with a row constructor (a, b). It is a compact way to ask “the row that is the most recent / cheapest / largest”.

playground the orders that share the biggest order's status and country

3. Table subquery: many rows

A table subquery returns any number of rows and columns. Use it in two places: after IN/EXISTS in a WHERE (next sections), or in FROM as a derived table. A derived table must have an alias.

playground a derived table: aggregate first, then filter and join

4. IN with a subquery

x IN (subquery) is true if x equals any value the subquery returns. It reads naturally for “rows whose id appears in this other set”.

playground customers who ordered something that was refunded or cancelled
NOT IN breaks when the list contains NULL

If the subquery can return a NULL, x NOT IN (subquery) returns no rows at all (annex A1). Use NOT EXISTS instead. It has no such trap.

playground see the trap: one NULL empties the result

5. EXISTS and NOT EXISTS

EXISTS (subquery) is true if the subquery returns at least one row. What the subquery selects does not matter, so people write select 1. NOT EXISTS is true if it returns none. The subquery usually refers to the outer row, which makes it correlated (next section).

6. Correlated subqueries

A subquery is correlated when it uses a column from the outer query. Conceptually it runs once for each outer row, with that row's values. (The planner often rewrites it into a join, so it is not necessarily slow.)

Window functions are often shorter

Questions like “the latest order per customer” or “above the group average” can also be written with window functions or DISTINCT ON. They are covered in lesson 8.

7. WITH: common table expressions

A CTE gives a subquery a name, defined before the main query: WITH name AS (SELECT …) SELECT … FROM name. You can chain several, separated by commas, and later ones can use earlier ones. The query then reads as a sequence of steps instead of nested parentheses.

playground three small steps instead of one nested query

Use one CTE twice

A CTE you refer to more than once is a good reason to write it: you name the logic once.

playground customers who spent more than the average customer
CTEs are not an optimisation fence any more

Since PostgreSQL 12, a CTE that is referenced once and has no side effects is folded into the main query like a subquery, so splitting a query into CTEs does not by itself make it slower or faster. A CTE referenced more than once is computed once and its result reused. You can force either behaviour with AS MATERIALIZED (…) or AS NOT MATERIALIZED (…).

CTEs that change data

A CTE can hold an INSERT, UPDATE or DELETE … RETURNING too, so that the rows it changed feed the next step. For example, archive-and-delete in one statement. That, and recursive CTEs (WITH RECURSIVE, for trees and graphs), belong to lesson 8 and lesson 9.

8. How the planner sees all this

IN, EXISTS, NOT EXISTS and many correlated subqueries become semi-joins or anti-joins in the plan, and are executed with the same hash, merge or nested-loop algorithms as a normal join. So the choice between a subquery and a join is mostly about which one you can read, as long as you avoid the NOT IN trap. To see what the planner really did, read the plan: EXPLAIN is the subject of lesson 13. Advanced uses of CTEs, LATERAL (a subquery that can refer to the tables before it in FROM), recursive queries and window functions are in lesson 8.

Summary

  • A scalar subquery returns one value; a row subquery one row; a table subquery many rows (alias it in FROM).
  • IN and EXISTS test for a match; NOT EXISTS is the safe test for “no match”.
  • NOT IN returns nothing if the subquery yields a NULL. Prefer NOT EXISTS.
  • A correlated subquery uses a column of the outer row.
  • WITH name AS (…) names a step; chain several; reuse one as often as you like.
