Every other page in this course assumes you can read a SELECT statement. This annex is the refresher: choosing columns, filtering rows, sorting, limiting, removing duplicates, and the one idea that trips up almost everybody, NULL. Each block runs in the playground on a small copy of the shop database, so you can change it and see what happens.

Set up

Nothing to install for this page: the playgrounds run a real PostgreSQL 18 in your browser, seeded with a small shop (8 customers, 8 products, 12 orders). To try the same statements against the full Docker database, start it with ./pg up and run ./pg psql. The table and column names are identical; only the number of rows differs, so the numbers you see in Docker will be larger.

The shop has five tables you will use here: shop.customers, shop.categories, shop.products, shop.orders and shop.order_items. A table name has two parts, schema.table. A schema is a folder for tables; the shop's tables live in the schema called shop.

1. SELECT and FROM: choose columns

SELECT names the columns you want, FROM names the table. * means “every column”. It is handy when you explore, and a bad habit in application code, because a later ALTER TABLE silently changes what your query returns.

playground pick columns, then try *

A statement ends with a semicolon. Keywords such as select are not case-sensitive. Unquoted names are folded to lower case, so Shop.Customers means shop.customers.

2. Expressions and aliases

A select-list item can be any expression: arithmetic, a function call, a string join with ||. An alias (AS name) gives the result column a name. Without one, PostgreSQL invents a name such as ?column? or the function name.

playground arithmetic, functions and aliases

You can also select with no table at all. That is the quickest calculator you own:

playground SELECT without FROM
Integer division truncates

7 / 2 is 3, because both numbers are integers. Make one side a decimal (7 / 2.0) or cast it (7::numeric / 2) when you want the fraction.

An alias names an output column, and you can also alias a table to shorten long names: from shop.customers as c, or just from shop.customers c. Aliases matter a lot once you join tables (annex A2).

3. WHERE: choose rows

WHERE keeps the rows for which its condition is true. Combine conditions with AND, OR and NOT. AND binds tighter than OR, so add parentheses whenever you mix them.

playground comparison and boolean operators

The comparison operators are =, <> (or !=), <, <=, > and >=. Note that “equals” is a single =, and that text values go in single quotes. Double quotes are for names, never for values.

4. NULL and three-valued logic

NULL means “no value / unknown”. It is not zero and not an empty string. In the shop, customers.phone is NULL when we never learned the number, and customers.referred_by is NULL when nobody referred the customer.

Because a NULL is “unknown”, any comparison with it is also unknown. So SQL has three truth values, not two: true, false and null (unknown). WHERE keeps only the rows where the condition is true. Unknown rows are dropped, just like false ones.

playground a comparison with NULL is never true

Use IS NULL and IS NOT NULL to test for it. IS DISTINCT FROM is a comparison that treats two NULLs as equal and never returns unknown. COALESCE(a, b, …) returns the first argument that is not NULL, which is the usual way to supply a default.

NOT IN and NULL

x NOT IN (1, 2, NULL) is never true: for any x, one of the comparisons is unknown, so the whole list is at best unknown. A subquery that can return a NULL does the same thing and makes the query return no rows at all. The safe patterns are NOT EXISTS or a subquery that filters out NULLs (annex A4).

5. LIKE, ILIKE, IN and BETWEEN

LIKE and ILIKE: patterns in text

LIKE compares text with a pattern. In a pattern, % matches any run of characters (including none) and _ matches exactly one character. LIKE is case-sensitive. ILIKE is the case-insensitive version, and it is a PostgreSQL extension rather than standard SQL.

playground starts with, contains, one character

Each column is a true/false test. Change the patterns and run it again. The playground shows the result of the last statement in a block, so keep one query per block when you want to see its rows.

A leading % cannot use a normal index

LIKE 'S%' can use a B-tree index in some setups, but LIKE '%kettle%' cannot. If you search inside text on a big table, see lesson 11.

IN: one of a list

x IN (a, b, c) is shorthand for x = a OR x = b OR x = c.

BETWEEN: a range, both ends included

x BETWEEN a AND b means x >= a AND x <= b. Both ends are included. That is convenient for numbers and risky for timestamps, where “between the 1st and the 31st” would miss most of the 31st. For dates and timestamps, prefer a half-open range: >= start AND < end.

6. ORDER BY, LIMIT and OFFSET

A table has no inherent order. Unless you write ORDER BY, PostgreSQL returns rows in whatever order is convenient, and that order can change from one run to the next. Sort explicitly whenever the order matters.

ORDER BY takes one or more expressions. Each can end in ASC (the default) or DESC. Later expressions break ties in earlier ones. You can also say where NULLs go: NULLS FIRST or NULLS LAST. By default, NULL sorts as if it were larger than any value: last in ascending order, first in descending order.

LIMIT and OFFSET

LIMIT n returns at most n rows. OFFSET m skips the first m rows first. Together they page through a result. Always combine them with an ORDER BY that gives a unique, repeatable order, or pages can overlap or skip rows. Add a tie-breaker such as the primary key.

playground the second page of three rows
Large OFFSETs get slower

OFFSET 100000 still reads and throws away 100,000 rows before returning yours. For deep paging, use keyset pagination (where id > last_seen_id order by id limit 20). The query-tuning lesson shows it in detail: lesson 14.

7. DISTINCT: remove duplicates

SELECT DISTINCT removes duplicate result rows. It compares the whole row, not just the first column. PostgreSQL also has DISTINCT ON (expr), which keeps the first row for each value of expr in the order you give. It is the quickest way to say “the latest order per customer”.

playground distinct values, then one row per group
Do not use DISTINCT to hide a bad join

If a join returns duplicate rows you did not expect, adding DISTINCT makes them disappear and leaves the real problem (a join that multiplies rows) in place. Find out why they are there first (annex A2).

8. CASE: if-then-else in a query

CASE returns a value depending on conditions. It works anywhere an expression works: in the select list, in ORDER BY, inside an aggregate. The first matching WHEN wins; with no ELSE, an unmatched row gives NULL.

playground label rows with CASE

The first form (CASE WHEN condition) tests any condition. The second (CASE expr WHEN value) compares one expression with values and is shorter for equality. The branches must produce compatible types.

9. The order a query is read in

You write SELECT first, but PostgreSQL logically processes the clauses in a different order:

  1. FROM (and joins): decide which rows exist.
  2. WHERE: keep the rows that pass.
  3. GROUP BY and HAVING: group the rows and filter the groups (annex A3).
  4. SELECT: compute the output expressions and aliases.
  5. DISTINCT, then ORDER BY, then LIMIT / OFFSET.

That is why you can use a select-list alias in ORDER BY but not in WHERE: the alias does not exist yet when WHERE runs.

playground an alias works in ORDER BY, not in WHERE

Summary

  • SELECT picks columns and expressions, FROM picks the table, WHERE picks rows.
  • Give computed columns an alias with AS.
  • NULL means unknown. Compare with IS NULL, never with =. WHERE keeps only rows that are true, not unknown.
  • LIKE is case-sensitive, ILIKE is not; % is any run, _ is one character.
  • BETWEEN includes both ends. Use half-open ranges for timestamps.
  • Without ORDER BY the row order is not defined. Pair LIMIT with a unique ordering.
  • DISTINCT removes duplicate rows; DISTINCT ON keeps one row per key.
  • CASE is the in-query if-then-else.
