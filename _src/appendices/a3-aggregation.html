An aggregate function turns many rows into one value: a count, a sum, an average. GROUP BY does that once per group instead of once for the whole table. This annex covers the everyday aggregates, how to filter before and after grouping, and the rules for NULL that make some totals surprising.

Set up

The playgrounds run PostgreSQL 18 in your browser on a small copy of the shop: 8 customers (four of them have no phone number), 8 products and 12 orders. The same queries run on the Docker database with ./pg psql; there the numbers are larger.

1. COUNT(*) versus COUNT(column)

count(*) counts rows. count(column) counts the rows where that column is not NULL. count(distinct column) counts the different non-NULL values.

playground three different counts of the same table

This is the most useful NULL rule in aggregation: count(*) - count(phone) is the number of customers with no phone. count(1) is the same as count(*); count(*) is the clearer one.

2. SUM, AVG, MIN and MAX

sum and avg work on numbers. min and max work on anything that can be sorted: numbers, text, dates.

playground summary of all orders
The result types

count returns bigint. sum of an integer column returns bigint, and sum of a numeric column returns numeric, so totals do not overflow easily. avg of an integer column returns numeric with many decimals; wrap it in round(…, 2) to show it.

3. GROUP BY: one result row per group

GROUP BY splits the rows into groups that share the same values, then computes each aggregate once per group. Every column in the select list must either be in the GROUP BY or be inside an aggregate. Otherwise PostgreSQL cannot know which of the group's values to show, and it raises an error.

playground orders and revenue per status
playground the error you get for a column not in GROUP BY

The message is column "orders.customer_id" must appear in the GROUP BY clause or be used in an aggregate function. Add the column to GROUP BY (more, smaller groups) or aggregate it (count(distinct customer_id), min(customer_id)).

You may group by several columns, and by expressions. One exception to the rule above: if you group by a table's primary key, you may select any other column of that table, because the key already decides them.

4. WHERE versus HAVING

Both filter, at different moments. WHERE runs before grouping and removes rows. HAVING runs after grouping and removes whole groups, so it can test aggregates. You cannot put count(*) > 1 in WHERE, because the count does not exist yet.

playground WHERE removes rows, HAVING removes groups
Filter in WHERE whenever you can

A condition that does not need an aggregate belongs in WHERE. It removes rows before the grouping work, and on a large table that is the difference between grouping a million rows and grouping a thousand.

5. FILTER: several conditional aggregates in one pass

aggregate(...) FILTER (WHERE condition) feeds only the matching rows to that one aggregate. It lets you compute many counts and sums in one scan, instead of one query per condition.

playground a small report per country in one query

Before FILTER existed, people wrote sum(case when status = 'delivered' then total end). It gives the same answer; FILTER says what you mean. More grouping tools (ROLLUP, GROUPING SETS, window functions) are in lesson 8.

6. How NULL behaves in aggregates

Four rules cover almost every surprise:

  1. Every aggregate except count(*) ignores NULL inputs.
  2. So avg(x) is the sum of the non-NULL values divided by their number, not by the number of rows.
  3. An aggregate over no rows returns NULL, except count, which returns 0. That is why the example above wraps sum in coalesce(…, 0).
  4. GROUP BY puts all NULLs in one group, even though NULL = NULL is not true.

Average of what?

If a missing value really means zero, avg(x) gives the wrong answer, because it skips the NULLs. Use avg(coalesce(x, 0)) in that case. If missing means unknown, the plain avg is right. Decide which one you mean.

7. string_agg and array_agg: collect values

string_agg(text, separator) joins a group's values into one string. array_agg(value) collects them into an array. Both accept an ORDER BY inside the parentheses, and without it the order of the values is not defined.

playground what is in each order, as one line

The two treat NULL differently. string_agg leaves NULL values out. array_agg keeps them, so array_agg(phone) contains NULL elements. Filter them with array_agg(phone) filter (where phone is not null) if you do not want them.

8. Where grouping fits in a query

The logical order is FROM → WHERE → GROUP BY → HAVING → SELECT → ORDER BY → LIMIT. Two consequences: ORDER BY can sort by an aggregate or its alias, and a top-N report is just ORDER BY … DESC LIMIT n after the grouping.

Summary

  • count(*) counts rows; count(col) counts non-NULL values; count(distinct col) counts distinct non-NULL values.
  • Every selected column must be grouped or aggregated (or be functionally determined by a grouped primary key).
  • WHERE filters rows before grouping; HAVING filters groups after it.
  • FILTER (WHERE …) gives conditional aggregates in a single pass.
  • Aggregates ignore NULL; over zero rows they return NULL (count returns 0). coalesce fixes the display.
  • string_agg and array_agg collect values; give them an ORDER BY.
