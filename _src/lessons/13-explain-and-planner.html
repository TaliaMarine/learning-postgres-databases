PostgreSQL does not run your query the way you wrote it. It first builds a plan: a tree of small steps, chosen by guessing which tree is cheapest. This lesson teaches you to read that plan with EXPLAIN, to tell a good guess from a bad one, and to fix the statistics behind a bad guess.

Learning goals

  • Explain what the planner is, and why it works from estimates rather than from the real data.
  • Use EXPLAIN, EXPLAIN ANALYZE and EXPLAIN (ANALYZE, BUFFERS), and say what each one costs you.
  • Read a plan from the inside out: node types, cost, rows, actual rows and loops.
  • Spot a row-estimate error and say whether it matters.
  • Look at pg_stats, run ANALYZE, and add extended statistics for an expression.
  • Tell the three join algorithms apart (nested loop, hash join, merge join) and say when each one wins.

1. What the planner does

A SQL statement says what you want, not how to get it. The planner (also called the optimizer) turns the first into the second. For every statement it:

  1. lists the ways to scan each table (read everything, or use an index) and the ways to join tables and in what order;
  2. gives each candidate a cost, a number in arbitrary units;
  3. keeps the cheapest candidate and hands it to the executor.

To price a candidate it needs to know how many rows each step will produce. It does not count them. It reads statistics that ANALYZE saved earlier: the table's size, and for every column a summary of its values. If those statistics are wrong or out of date, the plan can be wrong, even though nothing is wrong with your SQL.

2. EXPLAIN, EXPLAIN ANALYZE and BUFFERS

There are three levels of detail, and the difference between them is important.

CommandRuns the query?Shows
EXPLAINNoThe chosen plan with estimated cost and rows
EXPLAIN ANALYZEYes, fullyThe same plan, plus actual time, rows and loops for each node
EXPLAIN (ANALYZE, BUFFERS)Yes, fullyAll of the above, plus how many 8 kB pages each node read from memory (hit) or from disk (read)

Now the same query with ANALYZE and BUFFERS:

EXPLAIN ANALYZE really runs the statement

EXPLAIN ANALYZE UPDATE ... updates the rows. EXPLAIN ANALYZE DELETE ... deletes them. If you want to see the plan of a data-changing statement without keeping the change, wrap it in a transaction and roll back: 

begin;
explain analyze update shop.products set price = price * 2 where id = 1;
rollback;

The rollback undoes the data change, but not side effects outside the database (a trigger that calls a web service, a sequence that already moved forward). On a production table, prefer plain EXPLAIN.

A few more options you will use: EXPLAIN (FORMAT JSON) prints the plan as JSON, which is what tools read. TIMING OFF removes per-node clocks (they have their own overhead, and with them off the row counts are still exact). SETTINGS lists any non-default planner settings that influenced the plan.

3. Reading a plan

A plan is a tree. Each line starting with -> is a node. Data flows from the innermost (most indented) nodes up to the root, so read from the inside out. Every node carries the same few numbers:

PartMeaning
Index Scan using events_pkeyThe node type and, for scans, the table or index it reads
cost=0.42..8.44Estimated cost: the first number is the cost to produce the first row (start-up), the second the cost to produce all rows. Units are arbitrary; compare them only with each other
rows=1Estimated number of rows this node produces per loop
width=90Estimated average row size in bytes
actual time=0.063..0.064Real milliseconds to the first row and to the last row, per loop
rows=1.00 (actual)Real rows produced, per loop (an average, so it can be fractional)
loops=1How many times this node ran. Multiply per-loop numbers by this to get totals
Index Cond / FilterAn Index Cond is used to find rows. A Filter is checked on every row the node reads, and Rows Removed by Filter counts the rejects

Where do the cost numbers come from?

Cost is not magic. For a sequential scan, PostgreSQL adds the pages it must read and a small charge for each row:

With a WHERE clause, it also pays cpu_operator_cost (0.0025) per row to evaluate the test: 1 000 000 × 0.0025 = 2 500 more, giving 27 448, which is what explain prints when parallelism is off. You can check the inputs with show seq_page_cost; and select relpages, reltuples from pg_class where oid = 'analytics.events'::regclass;.

Loops: the number that fools people

A node that sits under a nested loop may run many times. Its actual rows and actual time are per loop. This plan joins ten orders to their lines:

The inner scan says rows=3.40 loops=10. It ran ten times, once per order, and found 3.4 lines on average, 34 in total. That matches the 34 rows the join produced. The estimate said rows=4 per loop, so about 40 in total, and the join node estimated 30. They are close enough.

A fast rule for reading a slow plan

Find the node whose own time (its actual time minus its children, times loops) is largest. Then compare its estimated rows with its actual rows. Most bad plans are bad because of the second comparison.

4. When the estimate is wrong

Compare rows= in the cost part with rows= in the actual part. Here the planner is badly wrong:

The planner expected 5 000 rows and got 332 937. The reason: PostgreSQL keeps no statistics about what is inside a JSONB value, so for an expression like payload ->> 'device' it falls back to a fixed guess (0.5% of the table). For a single scan this does no harm. In a join, an estimate that is too low can lead the planner to pick a nested loop that runs 332 937 times instead of a hash join. Section 8 fixes this one.

Common causes of bad estimates:

  • Stale statistics. The table changed a lot since the last ANALYZE.
  • Expressions. Functions and JSON extraction on a column have no statistics of their own (unless you create an expression index or extended statistics).
  • Correlated columns. The planner assumes columns are independent. country = 'NL' AND currency = 'EUR' is estimated as the product of two selectivities, which is too low when they go together.
  • Skewed data beyond what the statistics sample can describe.
Not every estimate error is a problem

An error matters only if it changes the decision. If the planner guesses 5 000 and gets 332 937 rows and still does the one sequential scan it would have done anyway, nobody cares. Look for errors on the nodes that decide a join method, a join order, or index versus scan. An error of one or two orders of magnitude on those nodes is a lead worth chasing.

5. Statistics: ANALYZE and pg_stats

ANALYZE reads a random sample of each table (about 30 000 rows at the default setting) and stores a summary per column. Autovacuum runs it automatically after enough rows change; you can also run it by hand. Two places hold the result:

  • pg_class.reltuples and relpages: the table's row and page counts.
  • pg_stats: per-column summaries (a readable view over pg_statistic).

On the Docker database the first query prints (rounded):

ColumnWhat it tells the planner
n_distinctHow many different values. A negative number means “this fraction of the row count”: -1 means every value is unique
null_fracThe fraction of rows that are NULL. 35% of events have no customer
most_common_vals / most_common_freqsThe most frequent values and how often each occurs. This is how kind = 'purchase' gets its estimate
histogram_boundsBucket edges for the values that are not in the common list. Drives range estimates such as occurred_at > ...
correlationHow well the physical row order follows the column order, from -1 to 1. Near 1 makes an index range scan cheap

The estimate for kind = 'purchase' is the table size times the frequency of that value. Frequency in the list: 0.029. 1 000 000 × 0.029 = 29 000, exactly the rows=29000 in the first plan. The real count is 29 952. That is the planner working correctly: it is close, from a sample of 30 000 rows.

After a big load, run ANALYZE yourself

Autovacuum analyses a table after roughly 10% of it changed, and it takes a while to notice. After a bulk load, a large delete or a migration, plans can be bad for minutes. Run ANALYZE table_name; right away. The statement is cheap because it only reads a sample.

6. The three join algorithms

When a query joins two tables, the planner chooses one of three algorithms. Each wins in a different situation.

AlgorithmHow it worksWins whenNeeds
Nested loopFor each row of the outer side, look up matching rows on the inner sideThe outer side is small and the inner side has an index on the join columnNothing, but without an index on the inner side it is quadratic
Hash joinBuild an in-memory hash table from the smaller side, then stream the other side through itBoth sides are large and there is no useful order. The usual choice for big, unindexed joinsAn equality condition (=) and enough work_mem; otherwise it splits into batches on disk
Merge joinWalk two inputs sorted on the join key side by side, like a zipBoth inputs already come sorted (from an index, say), or the result must be sorted anywayAn equality condition and sorted inputs (it will sort them if it has to)

You can see all three in the shop dataset. A join of ten orders with their lines is a nested loop (see section 3). A join of all orders with all lines becomes a hash join:

Do not leave enable_* switched off

The enable_hashjoin, enable_seqscan and similar settings do not forbid a method; they add a huge penalty to its cost. They are for experiments. If you need one in production to get a good plan, the real fix is almost always a statistics problem or a missing index.

7. Giving the planner better information

When an estimate is wrong, try these in order. Each is cheaper and safer than the next.

  1. Run ANALYZE. It fixes stale statistics.
  2. Raise the sample for one column: ALTER TABLE ... ALTER COLUMN ... SET STATISTICS 500; then ANALYZE. The default is 100; more means a bigger most-common list and a finer histogram. Use it on columns with many distinct values and skew.
  3. Create extended statistics for several columns that depend on one another, or for an expression (next section).
  4. Rewrite the query so that the planner sees a plain column rather than an expression, or add an expression index (lesson 12), which gets its own statistics.

8. Extended statistics

CREATE STATISTICS tells PostgreSQL to collect something it normally does not. On an expression it collects the usual per-column summary for the result of the expression. That repairs the bad payload ->> 'device' estimate from section 4. This changes the database, so try it in your own copy (the exercise below does exactly this in a scratch database); if you run it in shop the lesson numbers above will no longer match.

The estimate moved from 5 000 to 337 933; the real count is 332 937. Extended statistics for several columns use CREATE STATISTICS name (dependencies) ON a, b FROM t;, which teaches the planner that a determines b, fixing the independence assumption. Look them up in pg_stats_ext.

The statistics need an ANALYZE

CREATE STATISTICS only defines the object. It stays empty until the next ANALYZE (manual or autovacuum), and the estimate does not change until then.

9. Pitfalls

A cost number is not a time

A cost of 24 948 is not 24 948 milliseconds or anything else. Compare costs only inside one plan or between two plans for the same query on the same server. Never compare the cost of two different queries.

A fast EXPLAIN ANALYZE on a cold cache is a different query from a warm one

The first run reads pages from disk (Buffers: shared read=...); the second finds them in memory (shared hit=...). Run it twice and look at BUFFERS. If you only compare times, you may be comparing the cache, not the plans.

Sequential scans are not evil

Reading one million rows with a sequential scan took about 25 ms with two workers on the Docker database. If a query needs a big share of a table, a scan is the right plan. Indexes win when the query needs a small share, which is the topic of lesson 12.

Generic plans can differ from what you tested

Prepared statements (used by most drivers) may be planned without looking at your parameter values after a few executions. The plan you see with literal values in psql can differ from the one the application uses. EXPLAIN (GENERIC_PLAN) select ... where id = $1; shows the generic form.

Summary

  • The planner picks the cheapest plan using estimates from statistics. Bad statistics cause bad plans.
  • EXPLAIN shows the plan; EXPLAIN ANALYZE runs the statement and adds real rows, times and loops; BUFFERS adds page reads. Never ANALYZE a destructive statement without a transaction you will roll back.
  • Read a plan from the inside out. Per-loop numbers must be multiplied by loops. A cost is only comparable to other costs on the same server.
  • Compare estimated and actual rows. An error matters when it flips a decision, such as the join method.
  • pg_stats holds n_distinct, null_frac, common values, histograms and correlation. ANALYZE refreshes them; run it after bulk changes.
  • Nested loop suits a few outer rows with an indexed inner side; hash join suits big unsorted inputs; merge join suits sorted inputs.
  • CREATE STATISTICS repairs estimates for expressions and for columns that depend on one another.
