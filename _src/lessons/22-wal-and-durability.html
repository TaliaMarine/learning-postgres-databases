When COMMIT returns, your data is safe even if the power goes out one millisecond later. PostgreSQL achieves that without writing every table page to disk at commit. It writes a short, sequential log first, the write-ahead log (WAL), and tidies the tables later. This lesson shows how that works, how to watch it, and which settings trade safety for speed, with a real crash to prove the point.

Learning goals

  • Explain, in two sentences, what a crash loses and what it cannot lose, and why.
  • Read a WAL position (pg_lsn), find its segment file, and compute how much WAL lies between two positions.
  • Say what a checkpoint is, what triggers one, and read pg_stat_checkpointer.
  • Explain what fsync and full_page_writes protect against, and why you leave both on.
  • Describe each synchronous_commit level and what you can lose with it.
  • Use UNLOGGED tables and per-transaction synchronous_commit for data you can afford to lose.

1. What a crash loses

A table is stored in 8 kB pages. When you change a row, PostgreSQL changes the page in memory (in shared buffers) and marks it dirty. Writing that page to its table file can wait. What must not wait is the record of the change. So before it tells you “commit OK”, PostgreSQL appends a WAL record describing the change to the log and forces that log to disk. The log is written in order, which is fast. If the server dies, the next start replays the log from the last checkpoint (section 3): any committed change whose page never reached the table file is redone.

This was tested for real, on a throwaway PostgreSQL 18 container. A table t got a row, then a checkpoint, then a second row. A third row was inserted in a transaction that stayed open. Then the server process was killed with SIGKILL (docker kill -s KILL), the harshest stop there is, with no chance to clean up:

Both committed rows survived, including the one written after the last checkpoint, whose page had not been written to the table file. That is the replay (redo) at work. The row from the open transaction is gone: it was never committed. The line “invalid record length” is normal: it marks the end of the usable WAL, where the crash cut it off.

So, in one sentence each:

  • A crash loses uncommitted transactions, anything in unlogged tables, and (only if you chose to allow it, section 5) the last few commits.
  • A crash cannot lose a commit that returned successfully, as long as the disk really kept what it was told to flush.

2. WAL positions and segment files

Every byte of WAL has an address, the LSN (log sequence number), shown as two hexadecimal numbers such as 14/B943C1C8. The type is pg_lsn, and you can subtract two of them to get a distance in bytes. The WAL lives in files called segments in the pg_wal directory, 16 MB each by default (wal_segment_size, fixed when the cluster is created), and the file name encodes the position.

Notice fsync = off in the browser. On the course container the same query returns on, and so does every production server. The other settings match the Docker database: 16 MB segments (16777216 bytes), a 5-minute checkpoint_timeout and 1 GB max_wal_size.

Two positions 32 MB apart are exactly two segments apart; position 0/3001234 is in segment 000000010000000000000003. The name is 24 hex digits: 8 for the timeline (1 until you promote a replica or restore to a point in time), 8 for the high part of the LSN, and 8 for the segment number. The exact figure changes from run to run and with other sessions' activity, so do not build a check on it. (Drop public.wal_demo when you are done.)

How much WAL did this statement write?

EXPLAIN (ANALYZE, WAL) adds a WAL: line with the records and bytes for that statement alone. That is the cleanest way to compare, and it also shows the effect of UNLOGGED:

playground a logged table writes WAL
playground an unlogged table does not

The first plan has a WAL: records=... bytes=... line. The second has none: an unlogged table skips the WAL entirely, which makes writes cheaper. The price is that after a crash PostgreSQL cannot replay the table's changes, so it truncates the table (it comes back empty), and its contents are not sent to replicas. Use it for caches, staging tables and scratch data you can rebuild.

WAL fills the disk if nothing can remove it

PostgreSQL recycles old segments after a checkpoint, unless something still needs them: an archive command that keeps failing (lesson 23), or a replica or replication slot that has fallen behind (lesson 24). Then pg_wal grows until the disk is full and the server stops. A growing pg_wal directory is an alarm to investigate, not a number to tune away. You can list it with select count(*), pg_size_pretty(sum(size)) from pg_ls_waldir();.

3. Checkpoints

A checkpoint writes every dirty page in shared buffers to its table file, flushes those files, and records in the WAL “everything up to here is safely in the table files”. Recovery after a crash only has to replay the WAL written since the last checkpoint. So checkpoints bound the recovery time and let old WAL be recycled. They also cost I/O, because they write a lot of pages, so PostgreSQL spreads that work out over time (checkpoint_completion_target, 0.9 by default).

A checkpoint starts when one of these happens:

  • checkpoint_timeout (5 minutes by default) has passed since the last one. This is a timed checkpoint.
  • The WAL written since the last checkpoint approaches max_wal_size (1 GB in the course container). This is a requested checkpoint.
  • Someone runs CHECKPOINT, or a shutdown, base backup or CREATE DATABASE asks for one. These count as requested too.

The view pg_stat_checkpointer counts them (in PostgreSQL 18 it is this view that holds checkpoint statistics; older releases kept them in pg_stat_bgwriter):

num_timed is checkpoints because of the clock, num_requested those started early (by WAL volume or by hand). write_time and sync_time are milliseconds spent writing and syncing. Verified on the Docker server: running CHECKPOINT and reading the view again raised num_requested by exactly 1. (Statistics reach the view a moment after the event, so read it a second later.)

What good looks like

On a busy server, most checkpoints should be timed. If num_requested keeps growing, WAL volume reaches max_wal_size before the timer fires, so the checkpoints come too often, each one writes many pages, and the log shows “checkpoints are occurring too frequently”. The cure is a larger max_wal_size (a reload is enough, lesson 21), not more frequent tuning of anything else. A larger value costs disk space and a longer crash recovery, and nothing else.

4. fsync and full_page_writes

Writing to a file does not mean the data is on disk: the operating system keeps it in memory and writes it out later. To be sure, PostgreSQL calls fsync (or fdatasync, the course container's wal_sync_method), which does not return until the device says the data is stable. The setting fsync turns these calls on.

fsync = off can destroy your database

With fsync = off, a crash or power loss can leave the data files corrupt, not merely a few commits short, and PostgreSQL cannot tell afterwards. The only legitimate uses are a throwaway database you can recreate, such as a bulk load that you will redo if it fails, or a test suite's database. Never use it on data you care about. The browser playground runs this way for the reason above.

The second protection is full_page_writes (on). The operating system may write an 8 kB page in smaller pieces, and a crash in the middle leaves a torn page: half old, half new, which WAL replay alone cannot repair because the records assume a consistent starting page. So the first time a page changes after a checkpoint, PostgreSQL writes the whole page into the WAL (a full-page image, “fpi” in EXPLAIN (WAL) and in pg_stat_wal.wal_fpi). Replay starts from that complete copy. This is a large part of the WAL volume right after each checkpoint, which is one more reason not to checkpoint too often. Turning it off is only safe on storage that guarantees atomic 8 kB writes, and you would have to know that. The course container also has data checksums on (show data_checksums), which detect a corrupt page when it is read, but cannot repair it.

wal_compression (off by default) compresses those full-page images and trades a little CPU for less WAL. It is a reasonable thing to try on a write-heavy server; measure the WAL volume before and after.

5. synchronous_commit: how long COMMIT waits

At commit, PostgreSQL flushes the WAL and waits for the confirmation before it answers you. synchronous_commit controls how long it waits. It is a plain user setting, so you can change it per session, per transaction (SET LOCAL) or per role.

synchronous_commitCOMMIT returns when…A crash can lose…
on (default)the WAL is flushed on the primary (and on the synchronous standbys, if you configured any)nothing that was acknowledged
offthe transaction is in the WAL buffer. The WAL writer flushes it shortly afterthe last few commits (documented as up to three times wal_writer_delay, 200 ms by default, so under a second). No corruption
localthe primary's WAL is flushed; waiting for standbys is skippednothing on the primary; a failover may lose it
remote_writeflushed locally and a synchronous standby has written it to its OS (not yet to disk)little: needs the primary and standby to fail together
remote_applya synchronous standby has replayed it, so a read there sees itnothing; slowest

The last three only matter once you have standby servers and a non-empty synchronous_standby_names (lesson 24); on a single server they behave like on. You can list the valid values yourself: select enumvals from pg_settings where name = 'synchronous_commit'; returns {local,remote_write,remote_apply,on,off}.

The difference between on and off is visible in the WAL positions. On the Docker server (flush position versus insert position, read right after COMMIT):

With off the commit was acknowledged before its WAL reached the disk, and the WAL writer flushed it within the next second. If the server had crashed in that window, the commit would be gone (and every later commit would be gone too: the database is always consistent, it just rewinds slightly).

The sensible use is per transaction, for work you can redo:

Page views and click events are the textbook case: losing the last 200 ms in a crash matters less than the throughput gain when thousands of tiny transactions each wait for a disk flush. Payments are the opposite case. Keep on as the default and opt out narrowly.

Three ways to give up durability, three different risks

synchronous_commit = off loses the latest commits and keeps the database consistent. An UNLOGGED table loses that table's contents after a crash. fsync = off can lose the whole database. They are not interchangeable, and only the first two are ever appropriate on real data.

Summary

  • The write-ahead rule: flush the WAL before acknowledging a commit; table pages can be written later. A crash loses uncommitted work, never an acknowledged commit.
  • WAL positions are LSNs. Subtract them for a byte distance; pg_walfile_name() gives the 16 MB segment file.
  • A checkpoint writes dirty pages and bounds crash recovery. Timed checkpoints are healthy; many requested ones mean max_wal_size is too small. Read pg_stat_checkpointer.
  • fsync = off risks the whole database; full_page_writes protects against torn pages. Keep both on.
  • synchronous_commit = off can lose the last few commits but never corrupts; use it per transaction for losable data. UNLOGGED tables skip the WAL and are emptied by a crash.
  • A WAL directory that keeps growing means something (archiving, a replica) is holding the log back.
