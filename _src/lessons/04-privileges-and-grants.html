A privilege is a permission to do one specific thing to one specific object: read this table, create things in that schema, connect to that database. GRANT gives a privilege and REVOKE takes it back. This lesson covers every level where privileges exist, who holds them by default, how to make new tables pick them up automatically, and how to audit what any role can really do.

Learning goals

  • Say which privileges exist on a database, a schema, a table, a column, a sequence and a function.
  • Explain the difference between an owner and a grantee, and what PUBLIC means.
  • Give a role exactly the access it needs, and see why a table grant alone is not enough without schema USAGE.
  • Use ALTER DEFAULT PRIVILEGES so tables created later are readable without another GRANT.
  • Hand privileges on with WITH GRANT OPTION, and remove a whole chain with REVOKE ... CASCADE.
  • Remove a role cleanly with REASSIGN OWNED and DROP OWNED.
  • Read \dp, \dn+ and \l, and audit with the has_*_privilege functions and aclexplode.

1. Three questions behind every privilege

When a statement fails with permission denied, ask three questions. They keep the whole lesson organised.

  1. Which object? Privileges are attached to objects, and objects sit in a hierarchy.
  2. Who owns it? The owner can do everything to the object and can grant to others.
  3. Who has been granted what? Everyone else needs an explicit grant, directly or through a group role they belong to.

The hierarchy matters because to reach a column you must pass every level above it. Each level has its own check.

2. Owners and grantees

Every object has exactly one owner: the role that created it, unless someone changed that. The owner is not listed in the privilege list, because the owner holds every privilege on the object implicitly. That is why shop.orders shows an empty access list (relacl is NULL): only its owner, postgres, has rights, and the owner's rights are the default.

A grantee is any other role that has been given a privilege. A privilege list entry records three things: who received it, which privileges, and who granted it. The owner's own privileges can be revoked from itself, but the owner can always grant them back, and only the owner (or a superuser) can drop or alter the object.

The columns are pg_database.datdba, pg_namespace.nspowner and pg_class.relowner. The function pg_get_userbyid turns the role number into a name. In the course database, shop and its tables are owned by postgres. The public schema is owned by a special built-in role, pg_database_owner, which always means "whoever owns the current database".

Superusers skip the list

A superuser passes every privilege check, so GRANT and REVOKE change nothing for it (lesson 3). When you test a grant, test it as an ordinary role, or ask has_table_privilege('role', 'table', 'select'), which answers for any role.

The schema is the gate

USAGE on a schema does not let a role read anything by itself. It only lets the role look names up inside the schema. SELECT on a table without USAGE on its schema is just as useless. You need both.

4. Database and schema privileges

Database. CONNECT lets a role open a session in the database. TEMPORARY lets it create temporary tables. CREATE lets it create new schemas there (not tables: tables belong in a schema). A new database grants CONNECT and TEMPORARY to PUBLIC (section 7), so every role may connect until you say otherwise:

Revoking CONNECT from PUBLIC is the way to lock a database to a known list of roles. \l then shows =T/postgres (PUBLIC keeps only TEMPORARY) next to postgres=CTc/postgres (the owner) plus one line for every role you granted CONNECT. Superusers still get in, whatever the list says.

Schema. USAGE and CREATE, as above. The built-in public schema deserves a moment, because older tutorials describe it wrongly. Since PostgreSQL 15 its access list is:

The second line has an empty name before the =, which is PUBLIC (everyone). So every role has USAGE on public but only the database owner has CREATE. Before version 15, everyone could create tables in public, and that was the root of the "public schema trap" covered in lesson 5. The schema shop in the course database has no PUBLIC entry at all, which is why a new role cannot even look inside it.

5. Tables and columns

Table privileges are the ones you use daily. A column privilege is a finer cut: the role may read or write only the columns you list. Use it to expose most of a table while hiding a few columns, such as email, phone and profile in shop.customers.

In the Docker database, an ordinary role with this kind of grant (on id, full_name and country) behaved like this. The first query worked; the other two failed with permission denied for table customers. Notice that select * fails, because it expands to include the forbidden columns. The role must name its columns.

playground column privileges, audited with has_column_privilege

Four columns are readable (id, full_name, country, status), only status is updatable, and table_level_select is false on every row. That last column is the one to remember: a column grant never turns into a table grant.

Column REVOKE does not undo a table GRANT

If a role has SELECT on the whole table, revoke select (email) on shop.customers from that_role removes nothing. In the Docker database has_column_privilege still answered true afterwards. Table-level and column-level grants are tracked separately, and a role gets the union of both. To hide a column, revoke the table-level SELECT first and grant the allowed columns one by one.

6. Sequences and functions

Sequences hand out numbers. A role that inserts into a table whose default calls nextval needs USAGE on the sequence behind it. The tables in the shop dataset use GENERATED ... AS IDENTITY columns, which is the exception: an INSERT into an identity column does not check privileges on the hidden sequence, so only the table privilege matters. Test results from the Docker database:

Column definitionRole has INSERT on the table, no sequence privilege
id integer generated always as identityinsert works
id serial (default nextval(...))fails with permission denied for sequence until you grant usage on sequence
Calling nextval('shop.categories_id_seq') yourselfneeds USAGE on the sequence, even for an identity one

GRANT USAGE ON SEQUENCE is therefore the usual partner of GRANT INSERT for older serial tables. In \dp, a sequence shows letters rwU for its owner: SELECT (r), UPDATE (w) and USAGE (U).

Functions have one privilege, EXECUTE, and one surprise: when a function is created, EXECUTE is granted to PUBLIC automatically. Every role can call it as soon as it can reach the schema. To restrict a function, revoke from PUBLIC and grant to the roles you trust:

Before the revoke, \df+ shop.order_count shows an empty access column, which means "the default": owner and PUBLIC both have EXECUTE. After the revoke and the grant it shows postgres=X/postgres and one entry for the role you granted. (This default is also why a SECURITY DEFINER function needs an explicit revoke; see lesson 5.)

7. PUBLIC: the grantee that is everyone

PUBLIC is not a role you can log in as or find in pg_roles. It is a keyword meaning "every role, including ones created later". Privileges granted to PUBLIC apply to everyone, and are the source of the most common surprise in permission audits: you revoked from a role, but the role still has access because PUBLIC allows it.

The defaults in a freshly created database are small and worth knowing by heart:

ObjectWhat PUBLIC gets by default
DatabaseCONNECT and TEMPORARY
Schema publicUSAGE only (PostgreSQL 15 and later)
Schemas you createnothing
Tables and sequencesnothing
Functions and proceduresEXECUTE

In an access list, PUBLIC is the entry with an empty grantee name: =U/pg_database_owner. In aclexplode output it appears as grantee 0. Revoke from it with revoke ... from public.

8. Tables created later: ALTER DEFAULT PRIVILEGES

GRANT SELECT ON ALL TABLES IN SCHEMA shop TO role is handy, but it grants on the tables that exist right now. A table created tomorrow gets no entry, and the role cannot read it. In the Docker database, after the grant, has_table_privilege was true for shop.orders and false for a table created afterwards.

ALTER DEFAULT PRIVILEGES fixes that. It stores a rule: "when role X creates a table (or sequence, or function) in schema S, apply these grants to it". The two parts that people forget:

  • FOR ROLE x names the creator the rule applies to. Without it, the rule applies to objects the current role creates. Tables created by anybody else are not affected.
  • IN SCHEMA s limits it to one schema. Without it, the rule is database-wide.

It never changes tables that already exist.

playground an old table and a new table, same owner role · run once, “Reset data” to re-run

notes_new is owned by builder, has the access list {builder=arwdDxtm/builder,reader=r/builder} and reader_can_select is true. notes_old is owned by postgres, has no access list and reader_can_select is false. In the Docker database, \ddp lists the stored rules, and the catalog is pg_default_acl.

The rule belongs to the creator

A default privilege set FOR ROLE builder does nothing for tables created by postgres. If your migrations run as one role and an engineer sometimes creates tables as another, you need a rule for each creator, or you need to make sure all objects are created by the same owner role (lesson 5 sets up that layout).

9. Passing privileges on: WITH GRANT OPTION and CASCADE

Normally only the owner can grant privileges on an object. WITH GRANT OPTION lets a grantee pass that privilege on to others. In an access list a grantable privilege shows a star: r*.

playground a grant chain: postgres → mgr → helper · run once, “Reset data” to re-run

The result is {postgres=arwdDxtm/postgres,mgr=r*/postgres,helper=r/mgr}. Read each entry as grantee=privileges/grantor. helper holds SELECT because of mgr, not because of the owner. That dependency matters when you revoke:

CASCADE is the safe-by-default design: PostgreSQL refuses to leave a grant hanging without its source. The grantor recorded in the list is the role that ran the statement. You can write GRANTED BY role to say so explicitly, but it must name the current user: running grant select on shop.orders to helper granted by mgr as postgres fails with grantor must be current user.

10. Removing a role: REASSIGN OWNED and DROP OWNED

DROP ROLE refuses to run while the role still owns objects or appears in any access list. The error lists what is left, for example owner of table shop.t_new or privileges for schema shop. Two commands clear the way, and they do different things:

CommandWhat it doesRisk
REASSIGN OWNED BY old TO newHands every object old owns to new. Data stays.None for the data; check that new is the right owner.
DROP OWNED BY old [CASCADE]Drops every object old owns and removes its privileges everywhere in the current database.Deletes tables. Run REASSIGN first if you want to keep the data.

Both commands act only on the current database. Roles are cluster-wide, so if the role has objects or grants in three databases you must run the first two statements in each of them before DROP ROLE works. That is exactly what the course checker does when it removes your lab_ roles.

DROP OWNED really drops

drop owned by some_role deletes tables, views and functions that role owns, and with CASCADE everything that depends on them. It is the right tool for a role that only held privileges, and a data-loss command for a role that owns your tables. Run reassign owned first whenever the data matters.

11. Reading the access list: \dp, \dn+ and \l

Every access list is a set of entries in one format: grantee=privileges/grantor. An empty grantee is PUBLIC. A star after a letter means "with grant option". An empty list means "defaults only".

The first entry says that postgres holds arwdDxtm, which is INSERT, SELECT (r for "read"), UPDATE (w for "write"), DELETE, TRUNCATE (D), REFERENCES (x), TRIGGER and MAINTAIN, granted by postgres to itself. Once any grant exists, PostgreSQL writes the owner's entry out, so you see it. The second entry says that reporting has only SELECT. The same list in full:

In the course database, before you change anything, \dp shop.orders shows empty access columns, \dn+ public shows pg_database_owner=UC/pg_database_owner and =U/pg_database_owner, and \l shop shows an empty Access privileges column (database defaults).

12. Auditing: asking the server what a role can do

Do not decode lists by eye when the question is "can role X do Y?". The server answers directly, and the answer includes inheritance through groups, PUBLIC, ownership and superuser status. Each function takes the role, the object and a privilege name:

FunctionExample
has_database_privilegehas_database_privilege('app', 'shop', 'connect')
has_schema_privilegehas_schema_privilege('app', 'shop', 'usage')
has_table_privilegehas_table_privilege('app', 'shop.orders', 'select')
has_column_privilegehas_column_privilege('app', 'shop.customers', 'email', 'select')
has_sequence_privilegehas_sequence_privilege('app', 'shop.orders_id_seq', 'usage')

You can add with grant option to a privilege name, as in 'select with grant option'. For pg_has_role the last argument is member (is a member, directly or indirectly) or usage (is a member and inherits its privileges, lesson 3). A role is always a member of itself.

Use information_schema when you want portable SQL that works on other databases, and the pg_catalog columns when you need the whole truth about this server.

ALTER OWNER rewrites the list

When you change an object's owner, the old owner's entry is replaced by the new owner's, and the grantor of existing grants becomes the new owner. Changing the owner of shop.customers to lab_04_y gave {lab_04_y=arwdDxtm/lab_04_y,lab_04_x=r/lab_04_y}: the earlier grant to lab_04_x is now "granted by" the new owner. Check lists again after any ownership change.

Summary

  • Ask three questions about any permission error: which object, who owns it, who was granted what. permission denied for schema versus for table tells you which level is missing.
  • Owners hold all privileges implicitly. Everyone else needs a grant, directly or through a group role.
  • Privileges exist on databases (CONNECT, CREATE, TEMPORARY), schemas (USAGE, CREATE), tables, columns, sequences and functions (EXECUTE).
  • PUBLIC means everyone. Know its defaults: database CONNECT and TEMPORARY, schema public USAGE (since PostgreSQL 15), function EXECUTE.
  • GRANT ... ON ALL TABLES covers existing tables only. ALTER DEFAULT PRIVILEGES FOR ROLE creator IN SCHEMA s covers tables that creator makes later.
  • WITH GRANT OPTION creates grant chains; REVOKE ... CASCADE removes a whole chain.
  • Retire a role with REASSIGN OWNED, DROP OWNED and DROP ROLE, in every database it touched.
  • Audit with has_*_privilege and pg_has_role; use aclexplode for the full list, and remember information_schema only shows what concerns you.
