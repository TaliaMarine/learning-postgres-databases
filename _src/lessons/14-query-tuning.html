Tuning a query is not guessing which index might help. It is a loop: find out which statements cost the most, look at one plan, change one thing, and measure again. This lesson gives you that loop, shows you how to find the expensive statements with pg_stat_statements, and covers two patterns that cause a large share of real-world slowness: OFFSET pagination and the “N+1” query.

Learning goals

  • Follow a repeatable tuning method: measure, pick one target, read its plan, change one thing, measure again.
  • Find the most expensive statements with pg_stat_statements and explain what calls, total_exec_time and mean_exec_time tell you.
  • Read the Buffers lines of EXPLAIN (ANALYZE, BUFFERS) and use them to compare two versions of a query.
  • Rewrite a predicate so that an index can serve it.
  • Replace OFFSET pagination with keyset pagination, including the tie-break that keeps it correct.
  • Recognise an N+1 pattern from the statistics and replace it with one query.

1. A repeatable method

Without a method, tuning turns into trying things. Use these five steps and do not skip ahead:

  1. Find the target. Pick the statement that costs the most in total, not the one that merely looks ugly.
  2. Reproduce it. Run it by hand with real parameter values. Write down the plan and the numbers.
  3. Read the plan. Where are the rows and the buffers spent? Is the estimate close to what really happened?
  4. Change one thing. One index, or one rewrite. Never two at once, or you will not know which helped.
  5. Measure again. Same query, same values, same kind of cache. Keep the change only if the numbers moved.

Two facts make step 1 matter. A query that takes 2 ms and runs a million times a day costs far more than one that takes 3 s and runs once. And the first run of any query is often slower than the second, because the pages it needs are not yet in memory. That is why this lesson compares buffers (how many 8 kB pages a plan touched), which do not depend on the cache, and quotes timings sparingly.

2. Finding the expensive statements: pg_stat_statements

pg_stat_statements is an extension that keeps one row of counters per kind of statement. The server removes the literal values from the text first (this is called normalising) so that where country = 'NL' and where country = 'DE' are counted together as where country = $1. The columns you will use most:

ColumnWhat it tells you
callsHow many times the statement ran. A huge number with a small mean points at N+1 (section 6).
total_exec_timeMilliseconds spent running it, summed over all calls. Sort by this to find the biggest cost.
mean_exec_timeAverage per call. Sort by this to find the individually slow statements.
rowsRows returned or affected, summed. rows / calls is the average result size.
shared_blks_hit, shared_blks_readPages found in shared buffers versus pages that had to be requested from the operating system.
temp_blks_writtenPages written to temporary files: a sort or hash that did not fit in work_mem.
queryidA stable number for the normalised statement. Use it to find the same statement again.

Statistics are cluster-wide and not deterministic

pg_stat_statements collects statements from every database in the cluster, which is why the queries above filter on dbid. The numbers also include your own diagnostic queries and everything other sessions ran, and they change on every run. Use them to rank statements, never to assert an exact time. pg_stat_statements_reset() wipes the counters for everyone, so do not call it on a server that other people are watching.

Where the extension is installed

Loading it needs shared_preload_libraries = 'pg_stat_statements' in the server configuration and a restart. Each database that wants to query it also needs create extension pg_stat_statements. The course seed does both. The setting is covered in lesson 21 and the other statistics views in lesson 25.

4. Rewrites that let an index work

An index on a column helps only when the query compares the column itself. Wrap the column in an expression and the index on the bare column is no longer usable. This is the most common reason that “we added the index and nothing changed”.

With BUFFERS, the first plan is a Parallel Seq Scan that touches about 15 000 pages (hit=667 read=14281); the second is a Bitmap Index Scan that touches about 2 450. Casting to date uses the session time zone to decide where a day starts, so the range version states that boundary explicitly. That is better: it is clearer and it is faster.

Other rewrites worth knowing:

  • Ask for fewer columns. select * drags every column through the plan, and prevents index-only scans (lesson 12).
  • Existence, not count. If you only need to know whether a row exists, where exists (select 1 from ... ) can stop at the first match; count(*) > 0 counts them all.
  • Filter early. Put the restrictive condition in WHERE so the join sees fewer rows, rather than filtering after a large join.
  • Add LIMIT with a matching ORDER BY. “The latest 10 of one customer” is cheap with an index on (customer_id, occurred_at) and expensive without it. Exercise 3 builds that index.
Do not index every slow query

A new index slows every INSERT, UPDATE and DELETE on the table. If the plan shows a badly wrong row estimate, the fix may be ANALYZE or better statistics (lesson 13), and an index would only hide the problem. Look at the whole plan first.

5. Pagination: OFFSET versus keyset

Pagination means returning a long result in pages. The familiar way is LIMIT n OFFSET m. The cost is hidden: to return page 10 000, PostgreSQL must produce the first 9 999 pages and throw them away.

The primary-key index serves both, so the contrast is clean. The OFFSET plan has an Index Scan that returns rows=900020 to the Limit node above it and touches 15 915 pages. The keyset plan has Index Cond: (id > 900000), returns rows=20 and touches 7 pages. The first grows with the page number; the second does not.

The keyset rule

Keyset (also called seek) pagination remembers the sort key of the last row on the page and asks for rows after it. The rule that makes it correct: the sort key must be unique. If you sort by a column that can repeat, add a tie-break column (usually the primary key) to both the ORDER BY and the condition, and compare the two columns as a row value:

(a, b) < (x, y) compares the pair the way sorting does: first on a, then on b when the a values are equal. The sort direction in ORDER BY must match the comparison operator (desc goes with <). On the 200 000 orders in the course database, the page-2 query without an index is a Parallel Seq Scan plus a top-N sort over every row. After create index on shop.orders (ordered_at desc, id desc) (try it in your throwaway copy), it becomes an Index Scan with Index Cond: (ROW(ordered_at, id) < ROW(...)) and touches 8 pages. Keyset pagination is only fast when an index matches the sort order.

Both page-2 queries return orders 8, 7, 6 and 2. They agree only because nothing changed between the two requests. Say a new order arrives after you fetched page 1: the OFFSET count now points one row too far, so page 2 repeats the last row of page 1, while the keyset position (“after order 9”) does not move. Try it: run insert into shop.orders (customer_id, status, ordered_at, shipping_country) values (1, 'paid', '2025-08-01', 'NL'); in the first playground, then compare the two page-2 queries again (use Reset data afterwards).

The tie trap

Leaving out the tie-break is the classic bug. The next playground pages through customers sorted by country. Several customers share a country, so “country greater than the last one” skips them.

playground why the tie-break matters · tiny dataset

With only eight customers the two page-2 results happen to match, because each country on page 1 has exactly one customer. The skipped rows appear as soon as a country has more rows than fit on a page; in the course database NL alone has thousands. The row-value comparison is correct either way, which is why you should always use it.

What keyset pagination cannot do

You cannot jump to “page 4 000”: you only know how to continue from a row you have seen. It suits “next” and “previous” buttons, feeds and exports. A page-number navigator with deep jumps is the one case that still needs OFFSET, and there the honest fix is to limit how deep a user may go. Also make sure the sort columns are NOT NULL or handle NULL explicitly: a row-value comparison with a NULL yields no row.

6. The N+1 query

An N+1 query is a pattern, not a single statement. The application runs one query to get a list of N items, then runs one more query per item to get a related value. That is N+1 queries where one would do. Object mappers produce it easily: loading customers, then touching customer.orders inside a loop.

Each statement is fast, so no single one looks slow. The cost is the N network round trips and N times the planning and executor start-up. pg_stat_statements exposes it clearly. Simulate the loop with 200 customers in your throwaway copy:

N+1 is not always wrong

Ten queries for ten rows on a page you view once an hour are not a problem. Fix it when the statistics show a large calls multiplied by a real cost, or when each call crosses a slow network. And a big join is not free either: a join that multiplies rows (customers by orders by items) can be slower than two simple queries. Measure, as in section 1.

7. More pitfalls

EXPLAIN ANALYZE really runs the statement

EXPLAIN ANALYZE executes the query. For INSERT, UPDATE or DELETE the changes happen. Wrap it in a transaction you roll back: begin; explain analyze update ...; rollback; (lesson 15).

Tune with realistic data

A plan on a 100-row table says nothing about a 100-million-row table: the planner chooses by size and by statistics. Test on a copy with production-like volume and run ANALYZE after loading it. The browser playgrounds in this lesson show that a rewrite returns the right rows, never that it is fast.

One measurement is not a result

Run the query two or three times and compare buffers, not just milliseconds. A cold first run, a busy laptop or a parallel worker that did not start can each change a timing by a factor of two.

Summary

  • Tune in a loop: find the costly statement, read its plan, change one thing, measure again.
  • pg_stat_statements ranks normalised statements by total_exec_time, calls and buffers. It is cluster-wide and not deterministic, so use it to rank, not to assert.
  • Compare plans by Buffers: pages touched do not depend on cache warmth the way timings do.
  • An index helps only when the query compares the bare column; ranges beat casts and functions on the column.
  • OFFSET produces and discards every skipped row. Keyset pagination with a unique, indexed sort key does constant work per page.
  • N+1 shows up as a huge calls with one row per call. Replace the loop with a join or = any(array).
