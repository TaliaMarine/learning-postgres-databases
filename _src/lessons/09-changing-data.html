Reading data is the easy half of SQL. This lesson is about writing it well: inserting rows that might already exist, getting back what the database generated, updating one table from another, merging a feed into a table, loading a file, and wrapping a multi-step change so that it either happens completely or not at all. Every example uses the shop tables.

Learning goals

  • Write INSERT ... ON CONFLICT with DO NOTHING and DO UPDATE, and explain why the conflict target must match a unique index.
  • Use RETURNING to read generated values, and old and new to see a row before and after a change.
  • Update or delete rows based on another table with UPDATE ... FROM and DELETE ... USING.
  • Chain several writes in one statement with data-modifying CTEs.
  • Write a MERGE with several WHEN branches and read its result with merge_action().
  • Load and export data with COPY and \copy, and know what the in-browser playground cannot do.
  • Protect yourself from the classic mistakes: UPDATE without WHERE, and duplicates in a table with no key.

Set up for this lesson

Use the shop database. Most examples change data, so run them between begin; and rollback;. A transaction is a group of statements that succeed or fail together (lesson 15 goes deep); rollback throws every change in the group away, so your data stays as the course seeded it. The exercises work on a fresh copy of the database, so you can change shop freely there.

Playground and Docker give different numbers

The in-browser playground has the small shop (8 products, 12 orders), the Docker database has 500 products and 200 000 orders. The same statement can print different ids and prices in the two places. The outputs quoted in this lesson say which one they came from. Playground boxes on this page share one database, so run them from top to bottom, and use “Reset data” to start over.

1. Insert, and get back what the database made

INSERT accepts many rows in one statement, and one statement is faster and safer than many: it is one round trip and it is atomic (all rows go in, or none). Add RETURNING and the statement also returns rows, using any expression over the inserted row. That is how you learn the ids the database generated without a second query.

Run the same block again after the rollback and you get 16 and 17, not 14 and 15. A counter that could be rolled back would make concurrent inserts wait for each other.

2. INSERT ... ON CONFLICT

What should an insert do when the row already exists? By default it fails with a unique violation. With ON CONFLICT you choose. A conflict means: the new row would break a unique index or primary key. Inserting a row that does not exist and updating one that does is called an upsert.

DO NOTHING: skip the duplicates

DO NOTHING silently skips the conflicting rows and inserts the rest. RETURNING only returns the rows that were really inserted, which makes it easy to see what happened.

playground 'Garden' already exists after the last box, 'Pets' does not

Only Pets comes back, with id 13, not 12. Id 12 was handed out to the skipped Garden row and then thrown away: the counter moved even though nothing was stored. Gaps in identity numbers are normal; never build logic that expects them to be consecutive.

DO UPDATE: insert or change

DO UPDATE changes the existing row instead. Inside it, excluded is the row you tried to insert, and the table name (or its alias) is the row already stored. A price feed is the classic case: new SKUs are added, known SKUs get their price refreshed.

The existing row kept its name, stock and category: only the columns in SET changed. The old and new aliases in RETURNING are explained in section 3; here they also tell inserted rows from updated ones, because a freshly inserted row has no old version.

playground the same upsert on the small shop

The conflict target must match a unique index

ON CONFLICT (sku) is not a filter, it is a pointer to a unique index or constraint. PostgreSQL uses that index to detect the conflict and to lock the existing row, which is what makes the upsert safe when two sessions run it at the same time. If no unique index matches the columns you named, the statement is rejected:

You can also name the constraint, ON CONFLICT ON CONSTRAINT products_sku_key, or omit the target with DO NOTHING to skip a conflict on any unique index. Omitting it is convenient and hides which rule fired, so prefer an explicit target.

Partial unique indexes need their predicate

A partial index only covers rows that satisfy a WHERE condition. If a unique index is partial, the conflict target must repeat the same condition. Here a coupon code must be unique among active coupons only:

The second insert is skipped, so one coupon remains. Now leave out the where active. This next box fails on purpose, with the same “no unique or exclusion constraint matching” error as above. The index exists, but it does not cover every row, so it cannot answer “does this code exist?”:

One source row, one target row

If the same statement proposes two rows with the same key and you use DO UPDATE, PostgreSQL refuses: ON CONFLICT DO UPDATE command cannot affect row a second time. It cannot decide which of your two versions wins. Remove the duplicates from the input first (DISTINCT ON or an aggregate). DO NOTHING does not have this problem.

Update only when something changed

DO UPDATE ... WHERE shop.products.price IS DISTINCT FROM excluded.price skips rows whose value is already right. An update that changes nothing still writes a new row version, which costs I/O and, later, vacuum work (lesson 17). On the Docker shop, upserting SKU-00001 at its current price 45.80 with this WHERE returns zero rows.

3. RETURNING, old and new, and changing rows based on other tables

Old and new values

RETURNING works on INSERT, UPDATE, DELETE and MERGE. Since PostgreSQL 18 you can write old.column and new.column to get the value before and after the change. Before 18, UPDATE ... RETURNING gave you only the new values, and you needed a trick to see the old ones. For an insert, old is null; for a delete, new is null.

UPDATE ... FROM: join inside an update

To change a table using values from another table, list the other table in FROM and join it in WHERE. The target table is not repeated in FROM. The order totals in shop.orders are a stored copy of the sum of the lines; if they ever drift, one statement repairs them.

playground break three totals, then repair them from the order lines

Only the three damaged orders are touched, because the extra IS DISTINCT FROM condition skips rows that are already right. IS DISTINCT FROM is a comparison that treats null as an ordinary value, so it works when either side could be null.

A join that matches twice is silently wrong

If a target row matches several rows in the FROM table, UPDATE ... FROM picks one of them without telling you which, and without an error. Make sure the joined source has at most one row per target row (group it, as above, or join on a unique key). MERGE, in section 5, refuses this situation instead.

4. Several writes in one statement: data-modifying CTEs

A WITH query (a CTE, common table expression; see lesson 8) may contain INSERT, UPDATE or DELETE ... RETURNING. The rows it returns feed the next step. The whole statement is atomic. Here is a new order and its lines created together, using the id the first insert generated:

playground create an order and its lines in one statement

The same pattern moves rows from one table to another without a window where a row is in both or in neither: WITH moved AS (DELETE FROM a WHERE ... RETURNING *) INSERT INTO b SELECT * FROM moved. Exercise 3 uses it.

All parts of a statement see the same snapshot

The sub-statements of one WITH run against the data as it was when the statement began. They do not see each other's changes to the tables. In a test on the Docker shop, an UPDATE that tried to find an order inserted by a CTE in the same statement, by looking it up in shop.orders, updated zero rows. The only way to hand data between steps is RETURNING and the CTE name, as above.

5. MERGE

MERGE compares a source of rows with a target table and applies a different action to each group of rows: those found in both, those only in the source, and those only in the target. It arrived in PostgreSQL 15; WHEN NOT MATCHED BY SOURCE and RETURNING with merge_action() were added in 17, and old/new in RETURNING in 18. All three work in this course database.

BranchRows it applies toAllowed actions
WHEN MATCHEDSource row and target row have the same join keyUPDATE, DELETE, DO NOTHING
WHEN NOT MATCHEDSource row with no target row (also written BY TARGET)INSERT, DO NOTHING
WHEN NOT MATCHED BY SOURCETarget row with no source rowUPDATE, DELETE, DO NOTHING

Each branch can have an extra AND condition, and PostgreSQL uses the first branch whose condition is true for each row. A stocktake is a natural fit: the warehouse counted some products. Counted products get their stock set, unknown SKUs are added, and products in one category that were not counted at all are switched off.

playground MERGE a stocktake and read what happened to every row

merge_action() returns INSERT, UPDATE or DELETE for each row. Here the rows for SKU-00001 and SKU-00002 were matched, SKU-90002 was inserted, and the other products of category 6 were deactivated by the “not matched by source” branch. Without the extra AND p.category_id = 6 that branch would have switched off every product that was not in the list.

MERGE is not a safer ON CONFLICT

MERGE checks for a matching row first and inserts afterwards, so two sessions can both decide that a row is missing and both insert it; one of them then fails with a unique violation. INSERT ... ON CONFLICT is built to avoid that race. Use ON CONFLICT for a plain insert-or-update on one key under concurrent load. Use MERGE when you need several different actions, deletes, or conditions per row. Also note that MERGE raises MERGE command cannot affect row a second time when two source rows match one target row, which is the safe answer to the UPDATE ... FROM trap in section 3.

6. COPY: bulk in and out

COPY moves many rows between a table (or a query) and a file or stream, much faster than a series of INSERT statements. There are two ways to run it, and the difference matters.

  • COPY (the SQL command) runs on the server. A file path means a file on the server's disk, and reading or writing server files needs special privileges.
  • \copy (a psql command) runs in the client: psql reads or writes the file on your machine and streams it to the server through COPY ... FROM STDIN or TO STDOUT. This is what you want from your laptop.

Because the course database runs in a container, a server-side file path points inside the container, where you have nothing to read. The simple, portable way is to use STDIN and STDOUT. A SQL file can carry its own data after a FROM STDIN line, ending with a line holding \.:

The tag COPY 3 is the number of rows loaded. A temporary table (create temp table) lives only for your session, which is why it is a good staging area: load the raw file into it, check it with SQL, then use INSERT ... SELECT or MERGE to move the good rows into the real table.

Bad rows: ON_ERROR

By default one bad line aborts the whole COPY and nothing is loaded. Since PostgreSQL 17, ON_ERROR ignore skips lines whose values cannot be converted to the column type (for example text in a number column) and loads the rest. LOG_VERBOSITY verbose reports each skipped line:

Server-side COPY is a privilege, not a convenience

COPY ... FROM '/path', TO '/path' and especially FROM PROGRAM run as the operating-system user of the database server. Only superusers and members of pg_read_server_files, pg_write_server_files or pg_execute_server_program may use them. Do not grant these to an application role (lesson 5).

7. Loading a lot of rows

When you need many rows, work with sets, not loops. The simplest bulk source is generate_series, a function that returns the numbers from one value to another:

playground generate a thousand rows in one statement

Rules of thumb for loading real data:

  • Prefer COPY to INSERT for files. If you must use INSERT, send many rows per statement (hundreds to a few thousand) rather than one row per round trip.
  • Batch, do not load a billion rows in one transaction. A very large transaction holds locks and leaves a lot of work for vacuum if it fails. Batches of 10 000 to 100 000 rows are a common size. Measure on your own data.
  • Load into a staging table, then move. Validate with SQL before the rows reach the real table.
  • Indexes slow loading down, because every index is updated for every row. For a one-time initial load into an empty table, creating the indexes after the load is often faster. Whether that is acceptable on a table that is in use is an operations decision, because the table has no index (and no unique protection) until the build finishes.
  • After a big load, run ANALYZE on the table so the planner knows the new data (lesson 13).

8. Making changes safe

Wrap related changes in a transaction

A transaction ends with commit (keep everything) or rollback (discard everything). If any statement inside it fails, PostgreSQL marks the whole transaction as failed and only accepts rollback. Group steps that must succeed together: the order and its lines, or the archive and the delete.

UPDATE and DELETE without WHERE

The most common data accident is a statement that touches every row. In a transaction you can see the damage and undo it:

The row count in the command tag, UPDATE 200000, is the number to look at before you type commit. If it is not the number you expected, rollback. The playground shows the same habit on the small shop:

playground a mistake you can undo
Habit: write the SELECT first

Before a risky UPDATE or DELETE, run the same WHERE as a SELECT count(*). Then run the write inside begin and compare the row count in the command tag. psql has no “undo”; rollback is the undo.

INSERT ... SELECT and tables without a key

INSERT INTO t SELECT * FROM s copies rows. If the target table has no primary key or unique index, running it twice quietly stores everything twice. The database cannot call the second copy a duplicate, because you never told it what “the same row” means.

CREATE TABLE ... AS copies the rows but not the primary key, which is why this works at all. CREATE TABLE shop.products_keyed (LIKE shop.products INCLUDING CONSTRAINTS INCLUDING INDEXES) copies the primary key and the unique index on sku too. With it, the second insert fails with duplicate key value violates unique constraint "products_keyed_pkey", or inserts zero rows if you add ON CONFLICT DO NOTHING. (Avoid INCLUDING ALL for this copy: it also copies the GENERATED ALWAYS identity, and then INSERT ... SELECT * is rejected because it supplies the id values itself.) Giving every table a key is the cheapest data-quality tool you have (lesson 7).

Autocommit means every statement is final

Outside begin, psql runs each statement in its own transaction and commits it immediately. There is no confirmation prompt for DELETE FROM shop.orders. If you work in a production database, open a transaction by habit, and consider \set AUTOCOMMIT off in your psql session.

Summary

  • ON CONFLICT (key) needs a unique index on exactly that key (with the same WHERE for a partial index). DO NOTHING skips, DO UPDATE changes the stored row, and excluded is the row you proposed.
  • RETURNING gives back generated ids and, since PostgreSQL 18, old and new values for INSERT, UPDATE, DELETE and MERGE.
  • UPDATE ... FROM and DELETE ... USING join other tables; make sure the source has one row per target row.
  • Data-modifying CTEs chain several writes in one atomic statement, passing rows with RETURNING.
  • MERGE handles matched, not matched and (from 17) not matched by source rows, and merge_action() tells you what it did. For simple concurrent upserts, ON CONFLICT is the safer tool.
  • COPY loads fast. Use \copy or STDIN/STDOUT from a client, stage the data first, and batch very large loads.
  • Put risky changes in a transaction and read the row count before you commit. A table without a key will happily store duplicates.
