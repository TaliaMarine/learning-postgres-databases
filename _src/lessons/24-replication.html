A replica is a second server that keeps a copy of the first one's data, a few milliseconds behind. This lesson shows the two kinds of PostgreSQL replication: streaming (a byte-for-byte copy of the whole cluster) and logical (chosen tables, as row changes). It covers how to measure how far behind a replica is, what failover is, and what tools such as Patroni or a managed service do that PostgreSQL on its own does not.

Learning goals

  • Explain how a streaming standby stays up to date by replaying the primary's WAL.
  • Name the settings and views of streaming replication: primary_conninfo, replication slots, pg_stat_replication, synchronous_standby_names.
  • Measure replication lag in bytes with pg_current_wal_lsn() and pg_wal_lsn_diff(), and in time.
  • Set up logical replication with CREATE PUBLICATION and CREATE SUBSCRIPTION, and explain wal_level = logical and REPLICA IDENTITY.
  • Describe failover and split-brain, and what an HA tool adds.
  • Choose streaming or logical replication for a given job.

Set up for this lesson

So this lesson teaches the mechanism, and you run only the parts that work on a single server: the replication views (they exist, and are empty), the WAL position functions, and publications, which you can create and drop in a scratch database. The standby examples were run on a separate, throwaway pair of servers, and the output is what they printed. Do not try to change wal_level or other server settings in the course container.

The playgrounds run a real PostgreSQL in your browser. It is a single process with no network, so it can never have a replica either. The views and functions are the same, though, so the queries behave as they do on a lone primary.

1. Streaming replication: replaying the WAL elsewhere

Every change a primary makes is first written to the WAL (lesson 22). A standby is a server that starts from a base backup of the primary (lesson 23) and then never stops recovering. It connects to the primary, receives WAL records as they are written, and replays them. This is physical streaming replication. The primary process that sends WAL is a WAL sender; the standby process that receives it is a WAL receiver.

Because the standby replays the same WAL, it is an exact physical copy. It must run the same major version on the same platform. With hot_standby = on (the default) it accepts read-only queries while it replays. Writes fail with ERROR: cannot execute INSERT in a read-only transaction.

Setting one up

On the primary, wal_level must be replica or higher (the default), and max_wal_senders must leave room (default 10). A role with the REPLICATION attribute, plus a replication line in pg_hba.conf, lets the standby connect. Then one command on the standby machine creates the copy and the configuration:

primary_conninfo is the connection string the standby uses to reach the primary. primary_slot_name names a replication slot: a marker on the primary that records how far this standby has got, so the primary keeps every WAL segment the standby still needs, even if it disconnects for an hour.

An abandoned slot fills the disk

A slot keeps WAL forever if its standby never comes back. The primary's pg_wal directory grows until the disk is full and the primary stops. Drop slots you no longer need with pg_drop_replication_slot('name'), watch pg_replication_slots for inactive ones, and set max_slot_wal_keep_size (default -1, no limit) to cap how much WAL a slot may hold.

2. Watching replication: pg_stat_replication and lag

On the primary, pg_stat_replication has one row per connected standby. On the course server it is empty, because nothing replicates from it. That is the normal answer on a single server, not an error:

Both the playground and the Docker database answer f, replica, 0, 0: a primary with no standbys and no slots. On the throwaway primary with one standby attached, the same view showed this:

An LSN (log sequence number) is a position in the WAL, written as two hexadecimal numbers. The four columns are four steps: the primary sent the WAL, the standby wrote it, flushed it to disk, and replayed it so queries can see it. The view also has write_lag, flush_lag and replay_lag, which are times.

Lag in bytes

pg_current_wal_lsn() is the primary's current position, and pg_wal_lsn_diff(a, b) subtracts two positions and returns bytes. The difference between the primary's position and a standby's replay_lsn is how much WAL the standby still has to apply:

The same subtraction tells you how much WAL a statement writes, which is what a standby must then receive. Try it:

playground WAL positions are byte offsets you can subtract

The positions differ from run to run; the point is that wal_bytes is a plain number of bytes (712 in one test run, for 8 products). The example uses pg_current_wal_insert_lsn(), the position where the next record will be inserted, because in the browser's single process the flushed position does not always move inside one script. On a standby, ask the reverse question: how long since the last replayed transaction?

Time-based lag grows when nothing happens

now() - pg_last_xact_replay_timestamp() measures time since the last replayed transaction. On a quiet primary nothing new is committed, so this number keeps growing although the standby is fully caught up. Alert on the byte lag from the primary, or on replay_lag, and treat time-based lag on a standby as meaningful only when the primary is busy.

Synchronous replication

By default replication is asynchronous: COMMIT returns once the primary has flushed its own WAL, and the standby catches up a moment later. If the primary dies in that moment, the last few commits exist only on the dead machine. synchronous_standby_names makes COMMIT wait for standbys too:

The names match each standby's application_name (set in its primary_conninfo). pg_stat_replication.sync_state then shows sync or quorum instead of async. synchronous_commit = remote_apply waits until the standby has also replayed the change, so a read on the standby right after the commit sees it. Lesson 22 covers the other values.

One synchronous standby stops all writes when it stops

With synchronous_standby_names = 'standby_a' and only that one standby, every COMMIT on the primary waits forever when standby_a goes down. Synchronous replication needs at least two candidate standbys (ANY 1 (a, b)), so losing one does not stop the primary.

3. Logical replication: chosen tables, as row changes

Logical replication sends row changes (this row was inserted, that one updated) instead of WAL bytes. The source server publishes a set of tables and the target server subscribes to them. Because the target receives rows, not bytes, it can be a different major version, have extra tables and indexes of its own, and accept writes to other tables.

CREATE SUBSCRIPTION copies the existing rows first, then streams changes. It creates a logical replication slot on the publisher. Unlike streaming replication, it does not copy table definitions (DDL), sequences' current values or roles: you create the tables on the subscriber yourself, usually with pg_dump --schema-only.

wal_level = logical

To decode row changes from the WAL, the publisher needs wal_level = logical, which writes a little extra information into the WAL. Changing it needs a restart. The course server runs with replica, so creating a publication there succeeds but warns you:

A publication is just catalog data, so it can exist before anyone subscribes. Create one and look at it:

playground create a publication and read it back

The browser shows the result but not the wal_level warning, because the playground displays rows and errors only. A publication can be narrower than whole tables:

  • with (publish = 'insert, update') sends only those kinds of change.
  • A column list, for table shop.orders (id, status, total), sends only those columns.
  • A row filter, for table shop.orders where (shipping_country = 'NL'), sends only matching rows.
  • for all tables publishes every table in the database, including ones created later.

REPLICA IDENTITY: which row was updated?

When a row is updated or deleted, the subscriber has to find the same row. The replica identity of a table is the set of columns sent to identify it. By default it is the primary key. A table with no primary key has no replica identity, and once it is in a publication that publishes updates, PostgreSQL refuses the update on the publisher itself:

playground step 1: a table without a primary key, published
playground step 2: the update is refused

The error is cannot update table "page_views" because it does not have a replica identity and publishes updates. Inserts still work, because a new row needs no identifying. There are three fixes: add a primary key (best), name a unique index on non-null columns with replica identity using index, or send the whole old row with replica identity full. The last works for any table but makes the subscriber search for each row, which is slow on big tables without a suitable index.

playground step 3: give the table a replica identity, then clean up

relreplident is d for the default (the primary key), f for full, i for an index, and n for nothing. In the shop dataset, shop.order_items has no primary key, so it needs one of these fixes before you publish updates of it. Exercise 3 meets a subtler version: a row filter or column list must cover the replica identity, too.

Logical replication as an upgrade path

Because the subscriber can run a newer major version, logical replication can upgrade with only a few seconds of downtime. You subscribe a new server to the old one, wait until it has caught up, stop writes, and point the application at the new server. Lesson 26 compares this with pg_upgrade.

4. Failover, split-brain and what HA tools add

Failover means making a standby the new primary when the old one fails. In PostgreSQL itself it is one command on the standby, and it worked on the throwaway pair:

After that pg_is_in_recovery() returns f and the server accepts writes. The command is the easy part. The hard parts are deciding that the primary has failed, making sure it stays down, and moving the clients. PostgreSQL does none of that by itself.

Split-brain is the failure you must design against: the old primary was only unreachable, not dead. It comes back, still believes it is the primary, and now two servers accept writes. Their data diverges, and there is no automatic way to merge it. Preventing this is called fencing: before promoting a standby, make sure the old primary cannot accept writes, for example by stopping it, cutting its network, or making it lose a lock in a consensus store. A distributed key-value store such as etcd is the usual consensus store.

ToolWhere it runsWhat it adds to plain PostgreSQL
PatroniYour servers or VMsLeader election through etcd, Consul or ZooKeeper; automatic failover and fencing; rebuilds old primaries as standbys; a REST API for health checks
CloudNativePGKubernetesAn operator that creates the primary and standbys, fails over, moves a service to the new primary, and schedules backups
Managed services (Amazon RDS and Aurora, Google Cloud SQL, Azure Database for PostgreSQL, …)The providerStandbys, failover, a stable endpoint, backups and PITR, all behind a setting; less control and no superuser

Clients find the current primary through something that moves on failover: a DNS name, a virtual IP, a Kubernetes service, or a connection string listing several hosts with target_session_attrs=read-write, which makes libpq-based drivers try each host until one accepts writes.

A replica is not a backup

A standby replays every change, including DROP TABLE and the DELETE without a WHERE, within milliseconds. Replication protects you against losing a machine, not against mistakes. Keep the backups and WAL archive of lesson 23 as well.

Summary

  • A streaming standby starts from a base backup and replays the primary's WAL continuously; it copies the whole cluster.
  • primary_conninfo says where the primary is; a replication slot makes the primary keep the WAL a standby still needs, and an abandoned slot fills the disk.
  • pg_stat_replication (empty on a single server) shows each standby's sent, written, flushed and replayed position; pg_wal_lsn_diff turns positions into bytes of lag.
  • Logical replication publishes chosen tables as row changes, needs wal_level = logical, and needs a replica identity on every table whose updates or deletes it publishes.
  • Promoting a standby is one command; deciding when, fencing the old primary and moving clients is what Patroni, CloudNativePG and managed services do.
  • Replication is not a backup: mistakes replicate too.
