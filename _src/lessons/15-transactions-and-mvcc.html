A transaction is a group of statements that the database treats as one unit: all of it happens, or none of it. PostgreSQL also lets many transactions run at the same time without readers waiting for writers. It does this by keeping several versions of a row. This lesson shows you those versions, explains what a snapshot is, and tells you exactly what each isolation level protects you from.

Learning goals

  • Use BEGIN, COMMIT, ROLLBACK and SAVEPOINT, and explain what autocommit does when you do not.
  • Explain MVCC (multi-version concurrency control) in one paragraph: why an UPDATE writes a new row version.
  • Read xmin, xmax and ctid and say what each tells you about a row version.
  • Describe a snapshot, and tell when READ COMMITTED and REPEATABLE READ take theirs.
  • Say which anomalies each of the four isolation levels prevents in PostgreSQL, including write skew.
  • Handle serialization_failure (SQLSTATE 40001) by retrying the whole transaction.

1. What a transaction is

A transaction gives you the four guarantees known as ACID:

  • Atomic: all statements take effect, or none do.
  • Consistent: constraints hold at the end. A transaction that would break a CHECK or a foreign key cannot commit.
  • Isolated: concurrent transactions do not see each other's half-finished work (how strictly depends on the isolation level, section 5).
  • Durable: once COMMIT returns, the change survives a crash (the WAL does this, see lesson 1).

Autocommit

If you do not write BEGIN, PostgreSQL wraps every statement in its own transaction and commits it for you. That is autocommit. It is why a lone UPDATE is atomic, and also why two separate UPDATE statements are not: a crash between them leaves only the first applied.

Errors abort the transaction

When any statement in a transaction fails, the whole transaction enters an aborted state. Every following statement is refused until you end it with ROLLBACK (a COMMIT at that point is also turned into a rollback).

Savepoints

A savepoint marks a point inside a transaction that you can return to without giving up everything before it.

DDL is transactional

In PostgreSQL, CREATE TABLE, ALTER TABLE and DROP INDEX are rolled back with everything else. That makes a migration that runs in one transaction all-or-nothing. (A few commands refuse to run inside a transaction block, for example CREATE INDEX CONCURRENTLY from lesson 12.)

2. MVCC: many versions of a row

Suppose readers and writers had to take turns on a row. A long report would block every order update. PostgreSQL avoids this with MVCC (multi-version concurrency control): an UPDATE does not overwrite a row. It writes a new version of the row and marks the old version as no longer current. Each transaction then sees the versions that were valid for it. Readers do not block writers, and writers do not block readers.

Three consequences follow, and you will meet each of them again:

  • Old versions pile up as dead tuples until VACUUM cleans them: lesson 17.
  • Two writers on the same row still have to take turns: that is locking, in lesson 16.
  • An UPDATE that touches an indexed column writes new index entries too, which is part of the write cost from lesson 12.

3. See the versions: xmin, xmax, ctid

Every table has hidden system columns. Three of them describe the row version you are looking at:

ColumnMeaning
xminThe id of the transaction that created this version.
xmaxThe id of the transaction that deleted or updated it, or 0 if none has. A non-zero value on a visible row can also mean a transaction that locked the row, or one that has not committed yet.
ctidWhere the version physically sits: (page number, item number). It changes when the row is updated. Never use it as a key.

They are not part of SELECT *, but you can name them. Run this in ./pg psql. The rollback leaves the data as it was; the aborted UPDATE still leaves its mark in xmax. (Do not use ctid or these ids in application code; they are for looking.)

In the Docker database the first query printed xmin = 770, xmax = 773, ctid = (0,1) for product 1. The non-zero xmax on a live row is typical: a transaction that only locked the row (for example, a foreign-key check when an order item was inserted) leaves its id there without deleting anything. Inside the transaction the row came back as xmin = 1180, xmax = 0, ctid = (15,21): a new version on a different page. After the rollback the old version was visible again, now with xmax = 1180. That xmax belongs to a transaction that aborted, so PostgreSQL ignores it. Your numbers will be different, but the pattern is the same.

Transaction ids

A transaction gets an id only when it first writes. A read-only transaction has none, which keeps it cheap. pg_current_xact_id_if_assigned() returns NULL until the first write. The ids are 32-bit numbers that eventually wrap around, which is one of the reasons VACUUM must run: see lesson 17.

4. Snapshots: who sees which version

A snapshot is the list of transactions that had committed at one moment. When your statement reads a row version, PostgreSQL asks: was the transaction in xmin committed in my snapshot? Was the transaction in xmax, if any? A version is visible when it was created before your snapshot and not yet ended before it. Your own changes are always visible to you.

The isolation level decides when a snapshot is taken:

  • READ COMMITTED (the default): a new snapshot for each statement.
  • REPEATABLE READ and SERIALIZABLE: one snapshot for the whole transaction, taken at its first statement.

5. The four isolation levels

The SQL standard names four levels and defines them by which problems (anomalies) they allow:

  • Dirty read: you see changes another transaction has not committed.
  • Non-repeatable read: you read a row twice and get different values, because someone committed in between.
  • Phantom read: you run the same query twice and the set of rows differs, because someone inserted or deleted matching rows.
  • Serialization anomaly: the combined result of concurrent transactions is not what any one-after-another order would produce. Write skew (section 7) is the classic example.

REPEATABLE READ: one snapshot per transaction

Inserts behave the same way: rows committed by another session after A's snapshot stay invisible to A for the rest of its transaction, so there are no phantoms. In the standard, REPEATABLE READ may allow phantoms; PostgreSQL's snapshot does not.

Writing to a row that changed: the update conflict

A snapshot protects reads. What if session A (at REPEATABLE READ) tries to update a row that session B changed and committed after A's snapshot? A would silently overwrite a version it has never seen, so PostgreSQL stops it:

Under READ COMMITTED the same update would instead wait for B to commit, re-read the newest version of the row, and apply stock + 10 to it. That is why stock = stock + 10 is safe at the default level, and why select-then-update stock = <value you computed> is not (see the pitfall below).

6. SERIALIZABLE and SSI

SERIALIZABLE promises the strongest thing: the outcome is the same as if the transactions had run one after another in some order. PostgreSQL does this without blocking readers. It runs REPEATABLE READ snapshots and adds SSI (serializable snapshot isolation): it watches for dangerous patterns of read and write dependencies between concurrent transactions. When it finds one, it aborts one transaction with SQLSTATE 40001 (serialization_failure).

The application must retry

A 40001 error does not mean your SQL is wrong. The message says The transaction might succeed if retried. Code that uses REPEATABLE READ or SERIALIZABLE must catch 40001 (and the related 40P01, deadlock detected, from lesson 16) and run the whole transaction again from BEGIN. Retrying only the failed statement is wrong: the snapshot is gone.

7. Write skew: what REPEATABLE READ does not stop

Hospital rule: at least one doctor must stay on call. Two doctors, both on duty, each check the count and then take themselves off duty. Each transaction touches a different row, so no update conflict appears, and each saw "2 on duty" in its snapshot.

Two other ways to stop write skew

You do not always need SERIALIZABLE. A SELECT ... FOR UPDATE on the rows you depend on makes the second transaction wait (lesson 16), and a constraint, such as a unique or exclusion constraint, lets the database reject the bad state itself. Prefer a constraint when one can express the rule.

8. Pitfalls

Read-modify-write loses updates

If your code runs select stock, computes stock - 1 in the application, and writes the result with update ... set stock = 41, two concurrent requests both start from the same number and one decrement is lost. At READ COMMITTED nothing stops this. Write the change as one statement (set stock = stock - 1), lock the row first with FOR UPDATE, or use REPEATABLE READ and retry on 40001.

An idle open transaction holds the world back

A session that ran BEGIN and then went quiet (an app that forgot to commit, a person who walked away) keeps its snapshot alive. VACUUM cannot remove any row version that snapshot might still need, so dead tuples accumulate, and the locks it holds stay held. Look for these in pg_stat_activity (see "Inspect it") and set idle_in_transaction_session_timeout in production.

now() is the transaction's start, not the current moment

Inside a transaction now() returns the same value for every statement: the time the transaction started. Use clock_timestamp() if you need the actual time, and avoid now() as a stopwatch inside a long transaction.

Sequences ignore rollback

A rolled-back INSERT still used a value from its sequence or identity column, and the number is not returned. Gaps in ids are normal.

Summary

  • A transaction is all-or-nothing. Without BEGIN, each statement is its own transaction (autocommit). An error aborts the whole block until ROLLBACK.
  • MVCC: an UPDATE writes a new row version. xmin and xmax record who created and who ended a version; ctid is its physical place.
  • A snapshot decides which versions you see. READ COMMITTED takes one per statement; REPEATABLE READ and SERIALIZABLE one per transaction.
  • PostgreSQL never shows dirty reads; READ UNCOMMITTED is READ COMMITTED. REPEATABLE READ also prevents phantoms but still allows write skew.
  • SERIALIZABLE uses SSI and may abort a transaction with 40001. Retry the whole transaction.
  • Keep transactions short: open ones hold locks and stop VACUUM from cleaning up.
