PostgreSQL is a set of ordinary operating-system processes that share some memory and read and write files in one directory. Once you can picture that, a lot of behaviour stops being mysterious: why connections cost something, why a commit survives a power cut, why the first run of a query is slower than the second. This lesson walks through the pieces, then shows where each one lives in the catalogue so you can look for yourself.

Learning goals

  • Explain what a cluster is and how it relates to databases, schemas and tables.
  • Name the postmaster, the backend and the main background processes, and say what each one does.
  • Explain the difference between shared buffers, the operating-system page cache and the files on disk.
  • Explain, in your own words, why a committed transaction survives a crash (write-ahead logging).
  • Describe the four stages a query goes through: parse, rewrite, plan, execute.
  • Find the answer to “what exists here?” in the system catalogs instead of guessing.

1. The cluster: one server, many databases

A PostgreSQL cluster is one running server together with the directory of files it manages (the data directory). The word “cluster” has nothing to do with several machines. One cluster has:

  • one postmaster, the first process, which listens for connections and starts everything else;
  • one set of background processes (section 3) and one block of shared memory;
  • one write-ahead log (section 5), shared by every database in it;
  • one list of roles, shared by every database (lesson 3);
  • any number of databases, each isolated from the others.

Inside a database the objects nest like folders: a database holds schemas, a schema holds tables (and views, indexes, sequences, functions), a table holds rows. A name like shop.orders means “table orders in schema shop, in the database I am connected to”. A connection is always to one database: you cannot join a table in one database to a table in another with plain SQL.

Lesson 2 takes this hierarchy apart, including templates and search_path. For now it is enough to know the nesting.

2. The postmaster and one process per connection

When a client connects, the postmaster does not handle the work itself. It starts a new operating-system process for that connection, called a backend (in the statistics views it appears as a client backend). That backend authenticates the client, then reads your SQL, runs it and sends rows back, until you disconnect.

  • One connection means one backend process, with its own memory. A hundred idle connections are a hundred processes.
  • Starting a backend is not free. Applications that open and close a connection for every request pay for it every time. The fix, connection pooling, comes later in the course.
  • The limit is the setting max_connections (100 by default). The server refuses the 101st client.
  • If one backend crashes, the postmaster restarts all of them, because shared memory may be damaged. That is rare, but it is why a crash in one session can briefly disconnect everybody.

4. Shared buffers and the operating-system cache

Tables and indexes are stored in files, cut into 8 kB pages. A backend never works on the file directly. It asks for a page, and the page is loaded into shared buffers, a block of shared memory that all backends use. If the page is already there (a hit), no disk is touched. If not, it is a read.

  • Changing a row changes the page in memory. The page is now dirty. It is written to its file later, by the background writer or the checkpointer.
  • There are two caches, not one. When PostgreSQL asks the operating system for a page, the operating system may serve it from its own page cache without touching the disk. So PostgreSQL does not need to cache the whole database itself; the default shared_buffers is 128 MB.
  • Each backend also has private memory for sorting and hashing (work_mem). That memory is per operation, not per server.

5. The write-ahead log: why a commit survives a crash

Dirty pages sit in memory, so how can a commit be safe? Because before a transaction is reported as committed, PostgreSQL writes a short description of what it changed into the write-ahead log (WAL) and forces that log to disk. The big, scattered data pages can be written later.

  1. Your UPDATE changes a page in shared buffers.
  2. The change is also recorded, as a small record, in the WAL. Each record has a position called an LSN (log sequence number).
  3. On COMMIT, the WAL up to that point is flushed to disk (fsync). Only then do you get “COMMIT”.
  4. The data page reaches its file at some later time.

If the server crashes between steps 3 and 4, nothing is lost: at the next start PostgreSQL replays the WAL from the last checkpoint and redoes the changes. Writing the log is cheap, because it is one sequential append; writing the data pages is expensive, because it is random. WAL also feeds backups and replication, which are later lessons. fsync = off is not a tuning option

The setting fsync controls whether the WAL is really forced to disk. With off, a power cut can corrupt the whole cluster, not just lose the last transaction. It exists for throw-away loads and tests. (The browser engine runs with it off, because it has no disk to protect. Your Docker database has it on.)

6. What is in the data directory

Everything the cluster stores is in one directory, the one the server was started with. You do not edit it by hand, but knowing the main folders explains a lot. These exist in the course container:

EntryWhat is in it
base/One sub-folder per database (named by the database's OID). The table and index files live here, 8 kB pages in each file.
global/Cluster-wide catalogs: the list of databases and the list of roles.
pg_wal/The write-ahead log, as files of 16 MB each (wal_segment_size).
pg_xact/Which transactions committed and which aborted (section 8).
postgresql.conf, pg_hba.confServer settings, and the rules that decide who may connect (lesson 3).
PG_VERSIONThe major version that created the directory. A directory made by one major version cannot be started by another without an upgrade.
Never touch the files while the server runs

Do not copy, edit or delete files in the data directory of a running cluster, and above all never delete files from pg_wal/ to “free some space”. A file copy of a live cluster is not a valid backup, and removing WAL can make the cluster unable to start. Use SQL and the backup tools instead.

7. The life of a query

When a backend receives select … from shop.orders where …, it runs it in four stages:

  1. Parse. The text is checked for correct syntax and turned into a tree. Tables and columns are looked up in the catalogs; a missing table fails here.
  2. Rewrite. Rules are applied. The most important rule: a view is replaced by the query that defines it.
  3. Plan. The planner considers different ways to get the answer (which index, which join order, which join algorithm) and picks the one with the lowest estimated cost. The result is a plan, a tree of steps.
  4. Execute. The executor runs the plan step by step, pulling pages through shared buffers and sending rows to the client.

EXPLAIN shows the plan without running the query. The numbers (cost, rows) are the planner's estimates, based on statistics it keeps for each table.

8. Row versions and transaction IDs

PostgreSQL never overwrites a row in place. An UPDATE writes a new version of the row and marks the old version as ended; a DELETE only marks the version as ended. This is MVCC (multi-version concurrency control), and it is why readers do not block writers. Every transaction that changes data gets a transaction ID (xid), and every row version records the xid that created it in a hidden column, xmin. The commit state of each xid is kept in pg_xact/. The old versions that nobody can see any more are removed later by vacuum. The course covers the details in the transactions part.

The update did not change any value, yet both xmin and ctid are different after it. ctid is the physical address of the row version: (page number, slot in the page). A new version means a new slot, and a new xmin because a new transaction wrote it. Still only one version is visible, so the row looks unchanged to every query.

An update is a delete plus an insert

A table that is updated heavily collects dead row versions until vacuum cleans them. That is called bloat. It is the cost of MVCC, and it is the reason a table can be much larger on disk than the data you can see.

9. The catalogue knows everything

PostgreSQL describes itself in ordinary tables, the system catalogs, all in the schema pg_catalog. Anything you can create, you can find there with a SELECT. The four to know first:

Every psql command that starts with a backslash (\dt, \dn, \l) is just a query over these catalogs. Run psql -E (or \set ECHO_HIDDEN on) and it prints the SQL it ran. That is a good way to learn the catalogs.

Summary

  • A cluster is one server with one data directory. It holds many databases, and one list of roles shared by all of them.
  • The postmaster starts one backend process per connection, so connections have a real cost.
  • Background processes (checkpointer, background writer, walwriter, autovacuum launcher …) do the housekeeping you never see.
  • Pages are cached twice: in shared buffers and in the operating system's page cache. Changed pages are written to disk later.
  • A commit is durable because the write-ahead log is flushed first; after a crash, the WAL is replayed.
  • A query is parsed, rewritten, planned and executed. EXPLAIN shows the plan, with estimates.
  • An update writes a new row version (new xmin, new ctid); vacuum removes the old ones.
  • The system catalogs (pg_database, pg_namespace, pg_class, pg_roles) describe everything that exists.
