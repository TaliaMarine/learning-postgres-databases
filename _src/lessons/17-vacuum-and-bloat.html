In PostgreSQL an UPDATE never changes a row in place: it writes a new version and leaves the old one behind. This lesson shows where those leftovers go, what VACUUM and autovacuum do about them, how to tell whether a table is bloated, and what the transaction-ID counter has to do with any of it.

Learning goals

  • Explain why UPDATE and DELETE leave dead row versions behind, and where you can see them.
  • Say what plain VACUUM does, what VACUUM FULL does differently, and why the second one is a last resort.
  • Explain HOT updates and how fillfactor makes them more likely.
  • Work out, for a given table, how many dead rows it takes before autovacuum starts, and change that for one table.
  • Read pg_stat_user_tables and measure real bloat with pgstattuple.
  • Explain freezing and read the age of a table's oldest unfrozen transaction ID.

1. Where old row versions go

Lesson 15 showed that every row version carries xmin (the transaction that created it) and xmax (the transaction that deleted or replaced it). An UPDATE is therefore a delete plus an insert: the old version is marked as ended, and a new version is written, usually in a different place. The old version stays in the table file because another transaction that started earlier may still need to see it. Once no transaction can see it any more, it is a dead tuple (a dead row version). The word “tuple” is just the engine's name for a physical row version.

A table that is updated or deleted from heavily collects them, and they take space and make scans slower. That accumulated waste is called bloat.

2. What VACUUM does, and what VACUUM FULL does

VACUUM walks the table, finds the dead tuples that no transaction can need any more, and marks their space as reusable. It does not shrink the file and it does not block readers or writers. It also updates two maps: the free space map (where there is room for new rows) and the visibility map (which pages contain only rows every transaction can see, which lets index-only scans skip the table).

The dead tuples are gone and their space is free for new rows, but the file is still 64 kB, exactly as big as before. That is normal: plain VACUUM recycles space inside the file. It only gives space back to the operating system when the last pages of the table are completely empty.

You can see the rewrite: the table gets a new relfilenode (the number in its file name). select relfilenode from pg_class where relname = 'vac_demo'; returns a different value after vacuum full, and VACUUM alone leaves it unchanged.

VACUUM FULL takes the table away

VACUUM FULL holds an ACCESS EXCLUSIVE lock for as long as the rewrite takes, so every query on that table queues behind it (lesson 16). On a large table that can be minutes or hours of downtime. When you must shrink a big table while it is in use, people use the third-party pg_repack extension, which rebuilds the table in the background and takes the heavy lock only for a moment at the end. It is an extension you install and test, not part of core PostgreSQL, and it needs free disk space and a primary key (or other unique index). The course container does not include it.

3. HOT updates and fillfactor

Every index entry points at a table row. A normal update therefore has to insert a new entry into every index of the table, even for indexes on columns the update did not touch. A HOT update (heap-only tuple) avoids this. If the update changes no indexed column and the new version fits on the same page as the old one, PostgreSQL writes the new version on that page and chains it to the old one. The indexes are left alone, and the page can later clean up its own dead versions without a full VACUUM.

The column n_tup_hot_upd in pg_stat_user_tables counts HOT updates; n_tup_newpage_upd counts updates where the new version had to go to a different page. The first one fails if the page is full. That is what fillfactor is for: it tells PostgreSQL to fill table pages only to a given percentage (default 100) and keep the rest empty for exactly these new versions.

All 50 updates were HOT: the column is not indexed and the pages had room. Statistics counters are sent to the statistics system a moment after the statement, which is why this example calls pg_stat_force_next_flush() first. You will not need that in normal use, but it explains why counters can lag by a second or so when you query them immediately.

The trade-off of fillfactor

A lower fillfactor makes the table physically larger (more pages for the same rows), so scans read more. Set it below 100 only for tables that are updated often on non-indexed columns, such as counters and status flags, and leave append-only tables at the default.

4. Autovacuum: when does it run?

You normally never run VACUUM by hand. The autovacuum launcher, a background process, wakes up every autovacuum_naptime (one minute by default), looks at the statistics, and starts a worker for each table that crossed a threshold. A table is vacuumed when its dead rows exceed:

With the defaults a table needs 50 dead rows plus 20% of its size. That is fine for small tables and slow to react on big ones: a table with 1 million rows waits for about 200,050 dead rows. (PostgreSQL 18 also has autovacuum_vacuum_max_threshold, default 100 million, as a ceiling for that number on enormous tables.) Rows that are only inserted have their own, similar trigger (autovacuum_vacuum_insert_threshold 1000, autovacuum_vacuum_insert_scale_factor 0.2), which exists so append-only tables still get their visibility map and freezing work done. A parallel pair, autovacuum_analyze_threshold and autovacuum_analyze_scale_factor, decides when to refresh the planner statistics.

You can change the rule for one table without touching the server, with storage parameters. They are stored in pg_class.reloptions:

Autovacuum is deliberately polite. It sleeps for autovacuum_vacuum_cost_delay (2 ms) whenever it has used up its I/O budget, so that it does not starve your queries. That makes it slow on big tables by design; if it cannot keep up, the usual fix is a lower scale factor for the busiest tables (so each run has less to do) and a higher cost limit, not turning it off.

Never switch autovacuum off to “save resources”

Without it, dead tuples pile up, tables and indexes grow, queries slow down, and eventually the transaction-ID counter runs out of room (section 6). Setting autovacuum_enabled = off on a table is occasionally right for a table you bulk-load and drop; as a general setting it is a mistake that arrives later as an outage.

5. Why vacuum sometimes cannot clean

VACUUM can only remove a dead tuple that no running transaction might still need. The oldest transaction that is still open therefore sets a line: nothing that died after it started can be removed. A session left idle in transaction overnight, an abandoned replication slot, or a very long report query can hold that line back for hours, and bloat grows no matter how often autovacuum runs.

Long transactions are the usual cause of bloat

If a table keeps growing although autovacuum runs, look for old transactions before tuning anything: select pid, state, xact_start, query from pg_stat_activity where xact_start is not null order by xact_start;. A VACUUM log line such as “N dead row versions cannot be removed yet” is the same symptom. Lesson 25 returns to this query.

6. Measuring bloat, and freezing

The statistics view pg_stat_user_tables gives a cheap, approximate picture:

n_dead_tup is an estimate that the statistics system maintains as updates happen; it is cleared when a vacuum finishes, and it can briefly disagree with the table (statistics counters arrive a moment after the statement, as in section 3). Use it to find tables worth a look, and use pgstattuple (section 1) when you need the exact number. Do not build alerts that expect it to be exactly zero.

Freezing and transaction-ID age

Transaction IDs are 32-bit numbers that PostgreSQL hands out in order and compares in a circle: at any moment, about two billion IDs are “in the past” and two billion “in the future”. A row written long ago would eventually look like it comes from the future, and vanish. To prevent this, VACUUM freezes old row versions, marking them as “older than every transaction, forever”, so their xmin no longer matters. Each table remembers in relfrozenxid that every row older than that ID is frozen. The function age() turns it into a distance:

In a fresh course database every age is a few thousand: very young. When a table's age passes autovacuum_freeze_max_age (200 million by default) autovacuum starts an anti-wraparound vacuum on it, even if autovacuum is otherwise switched off. As a last defence, at vacuum_failsafe_age (1.6 billion) vacuum drops its politeness and skips non-essential work. If the counter ever gets within a few million IDs of the limit, PostgreSQL stops accepting new transactions until a vacuum finishes. This is the real reason vacuum is not optional.

Watch the oldest age, per database

select datname, age(datfrozenxid) from pg_database order by 2 desc; is the one number worth graphing. It should stay far below 200 million and drop every time an anti-wraparound vacuum completes.

Summary

  • UPDATE and DELETE leave dead row versions in the table; collected waste is bloat.
  • Plain VACUUM makes dead space reusable without blocking; it rarely shrinks the file. VACUUM FULL rewrites the table under an exclusive lock.
  • HOT updates skip the indexes when no indexed column changes and the page has room; fillfactor leaves that room.
  • Autovacuum starts when dead rows exceed threshold + scale_factor * reltuples; tune hot tables with per-table storage parameters, never by switching it off.
  • Old open transactions stop vacuum from cleaning. n_dead_tup is an estimate; pgstattuple is exact.
  • Freezing keeps the 32-bit transaction counter safe. Watch age(datfrozenxid).
