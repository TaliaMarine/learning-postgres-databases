A database is secure when each role can do its job and nothing more. This lesson puts the earlier lessons together into a layout you can copy for a real application: one role that owns the tables, one that the application uses, one for reporting. Then it adds the sharper tools: row-level security, functions that run with their owner's rights, and passwords.

Learning goals

  • Lay out three roles for an application (owner, app, read-only) and explain why the app must not own its tables.
  • Make new tables pick up the right privileges automatically with default privileges.
  • Read the public schema's access list on PostgreSQL 18 and say what is, and is not, still a risk.
  • Turn on row-level security, write USING and WITH CHECK policies, and explain who bypasses them.
  • Write a SECURITY DEFINER function that cannot be hijacked through search_path.
  • Explain how passwords are stored, and what pg_hba.conf does with them in the course container.

Roles are cluster-wide

A role you create while connected to the scratch database exists in every database of the server, as lesson 3 explained. Its privileges, however, are stored per database. When you drop a role that has privileges in a database, run drop owned by … in that database first.

1. A least-privilege layout: owner, app, read-only

Least privilege means giving each role only the rights it needs. For one application, three roles cover almost every case:

  • Owner (nologin): owns the schema and the tables. Only schema migrations run as the owner (an administrator uses SET ROLE to it, or a separate migration login is made a member of it).
  • App (login): what the application connects as. It reads and writes rows. It does not change the shape of anything.
  • Read-only (nologin group): reporting and BI tools. People or tools get a login role that is a member of it.

Why must the app not own its tables? In PostgreSQL the owner can always ALTER, DROP and TRUNCATE the table and can grant it to others, whatever has been granted or revoked. An application that owns its tables turns a SQL injection bug into drop table. Try it in the playground. It builds the layout on shop.products and then prints what each role may do.

2. New tables: default privileges

grant … on all tables in schema shop covers the tables that exist today. A table created next month has no grants, and the app fails with “permission denied” after the next deployment. The fix is to say, once, what every future table created by the owner should get. This is ALTER DEFAULT PRIVILEGES (lesson 4 explains it in depth). Run this in your scratch database:

The tables you already have are still owned by postgres. To make them match the layout, change their owner with ALTER TABLE … OWNER TO lab_05_owner (one statement per table, and the sequences that belong to identity columns follow automatically). Default privileges belong to the creator

ALTER DEFAULT PRIVILEGES FOR ROLE lab_05_owner only affects objects created by lab_05_owner. If a migration runs as postgres instead, the new table gets nothing. Run migrations as the owner role (SET ROLE lab_05_owner), or repeat the statement for each creator.

3. The public schema, on PostgreSQL 18

Older tutorials warn that “anyone can create tables in public”. That was true until PostgreSQL 14. From version 15 on, a normal role cannot create objects in public. Read the access list yourself instead of trusting a blog post, including this one:

In the course container, and in a new PostgreSQL 18 database, the answer is:

nspnameownernspacl
publicpg_database_owner{pg_database_owner=UC/pg_database_owner,=U/pg_database_owner}

Read each item as grantee=privileges/grantor. The first says the database owner has U (USAGE) and C (CREATE). The second has an empty grantee, which means PUBLIC (everybody): USAGE only. So everybody can look up names in public, and only the database owner can create there. The special role pg_database_owner is a placeholder that means “whoever owns the current database”.

The trap has moved, not gone

Three things can still bite you. (1) A database restored or upgraded from an old version keeps its old access list, where PUBLIC had CREATE. Run the query above on every database. (2) The default search_path is "$user", public, so public is searched by everyone. Any schema where untrusted roles can create objects can shadow the names you meant, which is exactly how the function attack in the next sections works. (3) Granting CREATE on a schema to the app role to “make a migration work” brings the problem back. Lesson 2 explains search_path and the public schema in detail.

4. Row-level security

Privileges decide which tables a role may touch. Row-level security (RLS) decides which rows of that table it sees or changes. One table can hold every tenant's or every agent's rows, and the database itself enforces who sees what, even when the application has a bug.

RLS has three parts:

  1. ALTER TABLE … ENABLE ROW LEVEL SECURITY turns it on for a table.
  2. CREATE POLICY adds a rule. USING (…) says which existing rows are visible, and for UPDATE/DELETE, which can be touched. WITH CHECK (…) says which new or changed rows are allowed to be written.
  3. A role that is not exempt (next sections) is then limited to what the policies allow.

The next playground builds a tickets table where each row belongs to the role that created it, turns RLS on and, deliberately, adds no policy yet:

The answer is 0. With RLS on and no policy, PostgreSQL applies default deny: nobody who is subject to RLS sees any row. That is the safe failure mode. Add a policy that lets each role see its own rows:

lab_05_alice sees her two rows and not Bob's. The same policy has a WITH CHECK part, which stops her writing a row for someone else. Last step, an attempt to do that (it fails, so it goes last):

playground step 3: WITH CHECK refuses the write

The error is new row violates row-level security policy for table "tickets". Some behaviour worth knowing, all seen in the course container with the same policy:

  • Reading and filtering is silent. An UPDATE or DELETE aimed at somebody else's row does not fail: it reports UPDATE 0 or DELETE 0, because the row is invisible to you.
  • Writing a forbidden row is loud. An INSERT, or an UPDATE that would hand your row to someone else, is rejected by WITH CHECK.
  • One policy per command is possible. CREATE POLICY … FOR SELECT | INSERT | UPDATE | DELETE lets reading follow one rule and writing another. FOR ALL (the default) covers all four. INSERT policies take only WITH CHECK.
  • Several permissive policies are OR-ed. A row passes if any policy allows it. Add AS RESTRICTIVE to make a policy that must also pass.

Test as the role, not as postgres

When you test a policy while connected as postgres you see every row, and the policy looks broken or useless. Use SET ROLE some_role (as the playground does) or ./pg psql-as some_role. A table that has policies but is owned by the role your app connects as is also not protected. This is another reason for the owner/app split in section 1.

Tenant ids with current_setting

A web application usually connects as one database role for all its users, so current_user cannot tell tenants apart. A common pattern is to pass the tenant id as a custom setting at the start of each transaction and to compare it in the policy:

current_setting(name, true) returns NULL instead of an error when the setting was never set, so a session that forgot to set it sees 0 rows, not everything. With a few rows for tenants 10 and 20, we saw 0 rows before set_config and the right 2 rows after it.

A setting is not a credential

Any session that can run SQL as the app role can also run set_config('app.tenant_id', '20', …). This pattern protects against bugs in the application (a forgotten WHERE), not against an attacker who already has SQL access as that role. When the user must be unable to cross tenants, give each user their own database role and use current_user. Use set_config(…, true) (transaction-local) so a pooled connection does not keep the previous user's value.

5. SECURITY DEFINER and search_path

A normal function runs with the privileges of the role that calls it. A SECURITY DEFINER function runs with the privileges of the role that owns it. That is useful: you can let a role get one narrow answer from a table it cannot read. It is also dangerous, because the function now executes caller-influenced code with the owner's power. The weak point is search_path, the list of schemas used to resolve a name like refund_staff that is not written as schema.name. The caller chooses their own search_path, and the function inherits it.

The fix has two parts, both in the function definition: pin the function's own search_path and qualify every name.

playground step 3: the fix

Mallory is rejected again (false) and the clerk still passes (true), even though Mallory's session still uses the hostile search_path. The setting pg_catalog, pg_temp keeps the built-in schema first and puts the temporary-table schema last. That is deliberate: by default PostgreSQL searches pg_temp first, so any role could shadow a name with a temporary table.

Checklist for every SECURITY DEFINER function
  • Put SET search_path = pg_catalog, pg_temp in the definition.
  • Schema-qualify every table, function and operator the body uses (shop.refund_staff).
  • Give it a dedicated owner with only the privileges the function needs. Never make a superuser own it.
  • Remember that new functions are executable by PUBLIC. revoke execute on function … from public, then grant it to the roles that need it.
  • Treat the arguments as untrusted input, exactly like application input.

6. Passwords and pg_hba.conf

A password is checked only if pg_hba.conf says that method applies to the connection (lesson 3 introduced the file). First look at the rules the course container really has. This is worth doing in Docker rather than in the browser, because the browser engine has its own rules:

rule_numbertypedatabaseuser_nameaddressauth_method
1local{all}{all}trust
2host{all}{all}127.0.0.1trust
3host{all}{all}::1trust
4-6the same three, for the replication pseudo-database
7host{all}{all}allscram-sha-256

The first matching line wins. A connection through the local socket or the loopback addresses (127.0.0.1, ::1) matches a trust line, so no password is asked. Anything else (rule 7, for example another container, or the container's own network address) must give a valid scram-sha-256 password. Create a role with a password and a role without one, and try both ways:

This is what we saw:

  • Wrong password for lab_05_pw: FATAL: password authentication failed for user "lab_05_pw".
  • Right password: it prints lab_05_pw.
  • lab_05_nopw over the network address (any password): password authentication failed, because the role has no stored password to match.
  • lab_05_nopw over loopback: it prints lab_05_nopw. trust never looked at a password at all.

Passwords are never stored in readable form. With the default password_encryption = scram-sha-256, the server stores a salted verifier, not the password:

The first query returns a value starting with SCRAM-SHA-256$4096: (the number is the iteration count), followed by random-looking salt and keys, and the expiry 2030-01-01. The second shows ********: the view pg_roles hides the verifier from everyone. Clean up with ./pg sql "drop role lab_05_pw" postgres and the same for lab_05_nopw.

No secrets in SQL files

The password lab-only in this course is acceptable because the container exists only on your machine. A real password in a .sql file ends up in Git history, in the server log (when statement logging is on) and in psql's history. In real systems, set passwords with the \password rolename command in psql, which hashes the password on your side and sends only the verifier, or take them from a secrets manager at deploy time. And rotate them: VALID UNTIL is the database's half of that story.

trust on the network

The image's trust lines are limited to the machine itself, which is why they are acceptable here. A trust line for an address range that other machines can reach means anyone who can reach the port can become any role, including postgres. A real server needs scram-sha-256 (or a certificate method) on every line that matches network connections, plus a firewall.

Superusers and the other bypasses

A superuser ignores grants and row-level security, and BYPASSRLS skips policies only. Keep both rare, and know who has them. The first query under “Inspect it” lists them.

Summary

  • Split ownership from use: a nologin owner for the tables, a login role for the app with DML only, a read-only group for reporting.
  • An owner can always alter or drop its tables. An app that owns them can destroy them.
  • ALTER DEFAULT PRIVILEGES FOR ROLE owner makes future tables usable, but only for objects that owner creates.
  • On PostgreSQL 15 and later public no longer lets everyone create objects. Check old and restored databases, and keep CREATE away from application roles.
  • With RLS on and no policy nobody sees any rows. USING filters, WITH CHECK guards writes. Owners, BYPASSRLS roles and superusers are exempt, and FORCE removes the owner exemption.
  • A SECURITY DEFINER function needs a pinned search_path, qualified names, a dedicated owner and an EXECUTE grant that excludes PUBLIC.
  • Passwords are stored as SCRAM verifiers. In the course container the loopback and socket lines are trust, everything else is scram-sha-256. Keep secrets out of SQL files.
