A view gives a query a name. A materialized view stores the query's result. A function or procedure runs logic next to the data. This lesson shows when each one helps, the keywords that change how PostgreSQL treats them (STABLE, SECURITY DEFINER, CONCURRENTLY), and the one security mistake that turns a helpful function into a hole.

Learning goals

  • Create a view, read its stored definition, and explain why a simple view can be updated through.
  • Create a materialized view, refresh it, and say why REFRESH ... CONCURRENTLY needs a unique index.
  • Write a SQL function and a PL/pgSQL function, with parameters, defaults and errors.
  • Choose the right volatility (IMMUTABLE, STABLE, VOLATILE) for a function.
  • Write a procedure, run it with CALL, and use COMMIT inside it to work in batches.
  • Explain SECURITY INVOKER versus SECURITY DEFINER, and pin search_path in definer functions.

1. Views: a stored query

A view is a named SELECT. It stores no data: each time you query it, PostgreSQL substitutes the view's query into yours and plans the whole thing together. Use views to give a complicated join one name, to hide columns, or to present a stable interface while the tables underneath change.

playground a view of revenue per customer

PostgreSQL stores the view as a parsed query, not as your text. select pg_get_viewdef('shop.v_customer_orders'::regclass, true); prints it back, rewritten: IN (...) becomes = ANY (ARRAY[...]) and every name is resolved. One consequence: if you later add a column to shop.customers, a view written with select c.* does not gain it. The column list was fixed when the view was created.

Updatable views and WITH CHECK OPTION

A view over a single table with no aggregates, DISTINCT or joins is automatically updatable: INSERT, UPDATE and DELETE on it change the table underneath. Add WITH CHECK OPTION and PostgreSQL also refuses changes that would make a row fall outside the view.

Views and privileges

By default a view reads its tables with the privileges of the view's owner, so you can grant SELECT on a view without granting it on the tables. Create the view with (security_invoker = true) if you want the caller's privileges (and row-level security policies) to apply instead. Lesson 5 covers why that matters with row-level security.

2. Materialized views: a stored result

A materialized view runs its query once and stores the rows, like a table. Reading it is fast; the price is that it is out of date until you run REFRESH MATERIALIZED VIEW. It suits expensive summaries that may lag: dashboards, daily reports, search facets.

playground step 2: new data does not appear until you refresh

The playground shows only the last result (9). Run the script up to the first select to see the 8. A plain REFRESH rebuilds the result and locks the materialized view against reads while it works. On a big summary that means readers wait. REFRESH MATERIALIZED VIEW CONCURRENTLY builds the new result on the side, compares it with the old one and applies only the differences, so readers keep reading. To compare rows it must be able to identify each one, so it requires a unique index (on plain columns, without a WHERE clause):

Nothing refreshes a materialized view for you

PostgreSQL has no automatic refresh. Schedule one (a cron job, the pg_cron extension, or your application's job runner), and show the age of the data to whoever reads it. A CONCURRENTLY refresh does more work overall than a plain one; it is cheaper only for the readers.

3. Functions in SQL and PL/pgSQL

A function takes arguments and returns a value (or a set of rows), and you call it inside a query. The simplest kind is written in SQL: its body is one or more SQL statements and it returns the result of the last one.

The $$ ... $$ is dollar quoting: a string literal that needs no escaping of single quotes inside it. When the logic needs variables, IF, loops or error handling, use PL/pgSQL, the procedural language that ships with PostgreSQL:

playground a PL/pgSQL function with checks

Product 1 had 120 in stock, so the function returns 130. Now try select shop.restock(999, 1);: it fails with no product with id 999. RAISE EXCEPTION aborts the statement and the transaction around it, exactly like a constraint violation, so the caller sees a normal error. FOUND is a built-in variable that tells you whether the last statement touched a row.

4. Volatility: what the planner may assume

Each function declares how its result behaves. The planner trusts the declaration and does not check it.

CategoryPromiseExampleWhat the planner may do
IMMUTABLESame arguments, same result, forever. Reads no tables.price_with_vat, lower()Compute it once at plan time; use it in an index expression
STABLESame result within one statement. May read tables.order_total, now()Call it once per scan and use it for an index lookup
VOLATILE (default)Anything goes: may change data or return a new value each call.restock, random()Call it for every row, in order, every time

You can read the declaration back from pg_proc.provolatile (i, s or v). Leaving a read-only function at the default VOLATILE is safe but slow: it can stop the planner from using an index on where id = my_function().

Do not lie about volatility

Marking a function IMMUTABLE when it reads a table, or depends on a setting such as TimeZone, gives wrong results. Results get cached in plans, and an index built on it holds stale values. When in doubt, choose STABLE.

5. Procedures and transaction control

A procedure looks like a function but returns nothing, and you run it with CALL, not SELECT. Its special power is that it may COMMIT or ROLLBACK part-way through. That lets one call work through a big job in small transactions, so locks are held briefly and an interruption loses at most one batch.

Try it in a scratch database rather than in shop, since it really moves 14,197 orders. Two rules come with transaction control:

  • select shop.archive_cancelled(); fails with is a procedure and the hint To call a procedure, use CALL.
  • COMMIT inside a procedure only works when the CALL itself is not inside an explicit transaction. After begin;, the first commit in the procedure fails with invalid transaction termination.

6. SECURITY INVOKER, SECURITY DEFINER and search_path

By default a function runs with the privileges of the role that calls it (SECURITY INVOKER). Declare it SECURITY DEFINER and it runs with the privileges of the role that owns it, like a setuid program. That is how you give a role one narrow ability, “look up a customer id by e-mail”, without granting it the table.

Every function is executable by PUBLIC by default. For a definer function, run revoke execute on function ... from public and grant it only to the roles that need it.

The search_path trap

A definer function that uses an unqualified name (clean_email(...) instead of shop.clean_email(...)) looks that name up through the caller's search_path. A caller who can create objects in any schema can put a function with the same name first on their path, and the owner's privileges run the caller's code. This was tested on the Docker database:

The caller's function ran as postgres, the owner of find_customer. The fix is to pin search_path on the function (and to qualify names anyway):

Every SECURITY DEFINER function needs SET search_path

Put set search_path = pg_catalog, <your schema> on the function (or = '' and qualify every name), never include a schema that untrusted roles can write to, and revoke EXECUTE from PUBLIC. A definer function owned by a superuser and missing these is a privilege escalation waiting to happen.

Summary

  • A view is a stored query, expanded into yours at plan time. Simple views are updatable; WITH CHECK OPTION keeps rows inside the view.
  • A materialized view stores a result and is stale until refreshed. CONCURRENTLY keeps readers going and needs a unique index.
  • SQL functions suit one query; PL/pgSQL adds variables, control flow and RAISE.
  • Declare volatility honestly: IMMUTABLE reads nothing, STABLE may read, VOLATILE is the default.
  • Procedures run with CALL and may COMMIT between batches, but not inside an outer transaction.
  • Functions run as the caller by default. SECURITY DEFINER runs as the owner, and always needs SET search_path and a narrow GRANT EXECUTE.
