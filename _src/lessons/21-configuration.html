PostgreSQL has about 350 settings, and the defaults are chosen to start on almost any machine, not to run well on yours. This lesson shows where a setting's value comes from (it can be set in six places), how to find out which place won, which settings can change without a restart, and the ten that are worth your attention first.

Learning goals

  • List the layers a setting can come from and say which one wins.
  • Read pg_settings to find a setting's current value, its source and its context.
  • Say what a restart, a reload and a plain SET each can change, from the context column.
  • Use SET, SET LOCAL, ALTER ROLE, ALTER DATABASE and ALTER SYSTEM for the right job.
  • Explain what each of the ten settings that matter does and what happens when it is too small or too large.
  • Attach a setting to a single function so that it applies only while the function runs.

1. The layers: where a value can come from

When PostgreSQL starts a session it builds each setting from several sources, applying them in this order. Later ones override earlier ones:

  1. Built-in default, compiled into the server. pg_settings.boot_val shows it.
  2. postgresql.conf, the main configuration file, edited by hand.
  3. postgresql.auto.conf, a second file that ALTER SYSTEM writes. It is read after the first, so it wins over it.
  4. The server command line (postgres -c name=value, which is what Docker's command: does). It wins over both files.
  5. ALTER DATABASE ... SET and ALTER ROLE ... SET, stored in the catalog and applied when a session starts. A setting for one role in one database beats a role-wide one, which beats a database-wide one.
  6. The session: SET name = value, or SET LOCAL for the current transaction only.

The column pg_settings.source tells you which layer produced the current value: default, configuration file, command line, database, user, database user, session. This is the first thing to look at when a setting “is not what I configured”.

The playground shows the result of the last query only: work_mem is now 65536 kB, the source is session, and reset_val still says 4096, the value you get back with RESET work_mem. On the Docker database, the first query reports source default and the value 4096 kB (4 MB).

SET versus SET LOCAL

playground SET LOCAL lasts until the end of the transaction

Inside the transaction the value is 256MB; after COMMIT it is back to the session's 64MB. SET LOCAL is the safe way to give one query a bigger sort area: nothing is left behind if the code forgets to undo it. That matters with connection pools, where a plain SET would leak to the next user of the same connection.

A plain SET follows the connection, not the request

Behind a connection pool (lesson 26), the next request may reuse your connection and inherit your SET. Use SET LOCAL inside a transaction, or put the setting on the role.

3. ALTER SYSTEM, reload and pending restart

Editing postgresql.conf by hand is fine, but you need file access to the server host. ALTER SYSTEM does the same from SQL, for a superuser: it writes the value to postgresql.auto.conf, a file you should not edit by hand. It does not apply the value; a reload or a restart does. Do not ALTER SYSTEM on the shared course container

The change survives restarts and affects every database on the server, including the template the checker clones. If you want to practise, start a separate server (for example docker run --rm -e POSTGRES_PASSWORD=x postgres:18) and throw it away afterwards. Some managed services block ALTER SYSTEM and give you a parameter-group screen instead.

5. The ten settings that matter

Most of the rest can stay at their defaults for a long time. These ten are where tuning starts. The values in the table are what the course container reports, and “typical start” is a common rule of thumb for a dedicated database server, not a promise: measure before and after.

An eleventh setting, track_io_timing (default off, switched on in the course container), is worth knowing too: it records how long I/O waits take, so EXPLAIN (ANALYZE, BUFFERS) and pg_stat_io can show times, not just counts. It costs a little on systems with a slow clock.

work_mem is per operation, not per connection

A query with three sort or hash steps can use three times work_mem, and ten such queries at once use thirty times. That is why the default is small. The planner thinks a random page read is four times as expensive as a sequential one. On an SSD that is untrue. Lowering the setting makes it choose index scans more eagerly. With an index on analytics.events (customer_id), the same query changes plan when only random_page_cost changes:

6. Pitfalls

A bigger value is not a better value

work_mem multiplied by concurrent sort steps can exceed RAM and get the server killed by the operating system. A very large shared_buffers leaves less memory for the operating system's cache, which PostgreSQL also relies on. max_connections = 1000 costs memory even for idle sessions. Change one setting at a time and measure.

The file says one thing, the server does another

Editing postgresql.conf does nothing until you reload or restart, and a mistake in the file can make a reload skip some or all of your changes. Always check what is live: select name, setting, source, pending_restart from pg_settings where name = '...'; and what the files say: select * from pg_file_settings where error is not null;.

Units

pg_settings.setting is in the base unit shown in unit (work_mem in kB, shared_buffers in 8 kB pages), while show and current_setting() give a friendly string such as 4MB. To convert, use pg_size_bytes(current_setting('work_mem')). Do not apply it to shared_buffers through the setting column, which counts pages.

When to use, when not to

Situation✅ Do this❌ Not this

Summary

  • A setting's value comes from the default, postgresql.conf, postgresql.auto.conf, the command line, database and role settings, or the session, in that order. pg_settings.source says which won.
  • context tells you how to change a setting: postmaster needs a restart, sighup a reload, user and superuser a plain SET.
  • ALTER SYSTEM writes postgresql.auto.conf; pg_reload_conf() applies it; pending_restart flags what still waits.
  • Use SET LOCAL, ALTER ROLE or a function-level SET to scope a change instead of changing the whole server.
  • The ten that matter: shared_buffers, work_mem, maintenance_work_mem, effective_cache_size, max_connections, random_page_cost, effective_io_concurrency, checkpoint_timeout, max_wal_size and log_min_duration_statement.
  • Change one thing at a time and measure. Defaults are safe; guesses are not.
