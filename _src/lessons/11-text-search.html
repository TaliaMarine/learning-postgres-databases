Searching text is where LIKE stops being enough. This lesson shows what LIKE and ILIKE can and cannot do with an index, how PostgreSQL's built-in full-text search turns words into searchable stems and ranks the matches, how to store and index a search column, and how trigram similarity finds names that are spelled a little wrong.

Learning goals

  • Say which LIKE patterns a B-tree index can serve, and fix a prefix search with text_pattern_ops.
  • Turn text into a tsvector and a search string into a tsquery, and match them with @@.
  • Choose between to_tsquery, plainto_tsquery, phraseto_tsquery and websearch_to_tsquery.
  • Explain stemming and stop words, and rank results with ts_rank and ts_headline.
  • Keep a tsvector in a generated column and serve it with a GIN index, and write a query the index can actually use.
  • Find similar strings with pg_trgm (%, <->, similarity()) and index ILIKE '%…%' with it.

1. LIKE, ILIKE and what they cannot do

LIKE matches a string against a pattern. % stands for any run of characters (including none) and _ for exactly one character. ILIKE is the case-insensitive version, a PostgreSQL extension. To match a literal % or _, put a backslash in front of it.

2. Which LIKE patterns can use an index

A B-tree index stores values in sorted order, so it can find a prefix quickly. A pattern with a leading wildcard, such as '%anna%', has no known starting point, so a B-tree cannot help and the planner reads the whole table. Even for a prefix pattern, a plain index is not enough in most databases. The course database uses the en_US.utf8 collation (the language-aware sort order), and a B-tree built with that order is not arranged the way LIKE 'anna%' needs. The plans below are from the Docker database (20 000 customers):

The plain index serves equality but not the prefix. The fix is an index built with the operator class text_pattern_ops (an operator class tells an index which comparison rules to use for a column). It compares character by character, ignoring the collation, which is exactly what a prefix search needs.

Read the Index Cond line: the planner rewrote like 'anna%' into a range, "at least anna and below annb", and the index answers that range. The leading-wildcard query is still a sequential scan. The same limits apply to ILIKE; for a case-insensitive prefix, index the lowered value and search the lowered value:

This is also how you get case-insensitive text without an extension

The citext extension adds a case-insensitive type. You do not need it: store the text as text, and use an index on lower(column) (a unique one if the value must be unique ignoring case) and queries on lower(column). The index and the query must use the same expression, or the planner will not connect them.

When you need %word% anywhere in the text, or typo tolerance, you need a different kind of index. That is what the rest of the lesson is about.

3. Full-text search: documents and queries

Full-text search matches meanings of words rather than characters. Two types do the work:

  • A tsvector is a document reduced to a sorted list of normalised words (lexemes) with their positions.
  • A tsquery is a search expression over lexemes, combined with & (and), | (or), ! (not) and <-> (followed by).

The operator @@ asks "does this document match this query?". Four functions build a tsquery from text; they differ in how forgiving they are:

FunctionInput styleUse it for
to_tsqueryQuery syntax: quick & fox, prefix kett:*Queries you write yourself. Raises an error on bad syntax.
plainto_tsqueryPlain words, all combined with ANDSimple "all of these words" boxes.
phraseto_tsqueryPlain words that must appear next to each other, in orderExact phrases.
websearch_to_tsquerySearch-engine syntax: "quoted phrase", or, -excludedText typed by users. Never raises a syntax error.

The output, exactly as the engine prints it:

  • document: 'brown':3 'dog':10 'fox':4 'jump':6 'lazi':9 'quick':2
  • to_tsquery: 'quick' & 'fox'
  • plainto: 'quick' & 'brown' & 'fox'
  • websearch: 'quick' <-> 'fox' & !'lazi' | 'dog'

Look at what happened to the document. foxes became fox, jumping became jump, lazy became lazi. The words the, were and over are gone. The numbers are positions in the original text (which is why <-> can ask for neighbouring words). The next section explains why.

to_tsquery is not for user input

to_tsquery('english', 'quick fox') (two words, no operator) fails with syntax error in tsquery: "quick fox", and so does any stray quote, parenthesis or &. Pass text typed by users to websearch_to_tsquery or plainto_tsquery; both accept anything. For example websearch_to_tsquery('english', 'quick "fox & (') quietly becomes 'quick' & 'fox'.

4. Configurations, stemming and stop words

A text search configuration decides how text is split into words and normalised. The english configuration does two things:

  • Stemming cuts a word to its root, so kettle and kettles, or clean and cleaning, become the same lexeme. The root need not be a real word (lazi).
  • Stop words are very common words (the, and, of) that are dropped because they match everything.

The simple configuration does neither: it only lowercases. pg_ts_config lists the configurations the server has (english, dutch, german, and many more). The configuration is part of the data: build the document and the query with the same configuration.

playground stemming, stop words, and what ILIKE misses

english_match is true and simple_match is false: without stemming, foxes is not fox. only_stop_words is an empty vector. In the mini seed, the only description with the word is "Easy to clean, rechargeable.": ilike_cleaning is 0 because the text says clean, and fts_cleaning is 1 because stemming connects cleaning to clean.

See why a word did or did not match

ts_debug('english', 'The foxes jumped') shows, for each token, which dictionary handled it, and the lexeme it produced (empty for a stop word). Reach for it before guessing.

Phrases and prefixes

phraseto_tsquery('english', 'cat sat') matches "the cat sat" but not "cat the sat", because stop words still occupy a position and the words must be adjacent. For "starts with", use a prefix match in a to_tsquery: to_tsquery('english', 'kettl:*') matches kettle and kettles. Write the prefix as a stem, not a full word: kettle:* is stemmed to kettl:* first, but a prefix like kett:* also works since it is a prefix of the stem.

5. Ranking and highlighting

Matching is yes or no. ts_rank turns "how well does it match" into a number (higher is better), based on how often the query lexemes occur. ts_headline returns a snippet of the original text with the matches wrapped in <b> tags. Both take the query as an argument, so a common pattern is to put the query in the FROM clause once and use it three times.

playground rank, order and highlight

Two kettles match. Smart kettle ranks 0.0760 and Retro kettle 0.0608, and the headline for the first is A <b>kettle</b> with a temperature setting. For the second, the word kettle is only in the name, which the headline did not look at, so you get an unmarked snippet of the description. A headline is computed only from the text you pass it.

Rank numbers are relative

Use rank only to order results of the same query. Do not compare numbers across queries or set a fixed cut-off. ts_rank_cd is a variant that also rewards matched words being close together. Calling ts_headline on every candidate row is slow: apply it only to the few rows you actually show (for example, after a LIMIT, in an outer query).

6. A stored search column and a GIN index

Calling to_tsvector in every query rebuilds the document for every row, and no index can help. Instead, compute it once into a column and index that column. A generated column is a column PostgreSQL computes from other columns on every insert or update, so it can never be out of date. A GIN index (generalised inverted index) stores, for each lexeme, the list of rows that contain it, which is exactly what text search needs.

setweight labels lexemes with a weight from A (most important) to D. Here a hit in the product name counts more than a hit in the description, and ts_rank takes the weights into account. Look at one stored value to see the weights (select search from shop.products where id = 2): 'ear':8B 'headphon':2A,9B 'over-ear':6B 'premium':1A 'quiet':3B 'reliabl':5B.

On the Docker database (500 products), add the index and look at the plan:

The first query uses the index. The second asks the same question about a different expression, so the planner ignores the index and scans the table. This is the most common full-text mistake, and it is silent: both queries return rows.

The index only helps queries written the same way

A GIN index on search serves search @@ …. It does not serve to_tsvector('english', description) @@ … (a different expression) and it does not serve a query that uses 'simple' or another configuration than the one that built the column. If you index an expression instead (create index … using gin (to_tsvector('english', description))), the query must repeat that expression with the configuration written out as a literal.

Generated columns and indexes need immutable expressions

A generated column or an index expression must be immutable: same input, same output, always. to_tsvector('english', description) is immutable because the configuration is a fixed literal. to_tsvector(description), which reads the session's default_text_search_config, is not, and create table t (d text, v tsvector generated always as (to_tsvector(d)) stored) fails with generation expression is not immutable. Always write the configuration name. If the search document must combine other tables, a generated column cannot read them; use a trigger (lesson 19) that sets a plain tsvector column instead.

7. Trigram similarity with pg_trgm (Docker only)

Full-text search compares word roots. It cannot find Jansn when the data says Jansen, and it does not search inside words. A trigram is a group of three consecutive characters; the extension pg_trgm compares strings by how many trigrams they share. Its similarity score runs from 0 (nothing in common) to 1 (identical).

Docker only

The in-browser playground cannot load pg_trgm, so there is no playground box in this section. Run the code in the lab_text copy of the database from the set-up section. Outputs below come from that Docker database.

show_trgm('cat') shows that a string is padded with two spaces in front and one behind before it is cut into trigrams. The operator % is true when similarity() is above the setting pg_trgm.similarity_threshold (default 0.3). <-> is the distance, 1 - similarity. word_similarity compares the first string against the best-matching part of the second, which suits a short search word against a long text.

Indexes for trigrams

The big win: a trigram index serves LIKE and ILIKE with a leading wildcard, plus the % operator. The operator class gin_trgm_ops goes with a GIN index.

The timing is from one run on the course machine; yours will differ. The second query has only two letters, which gives the index too little to work with, so the planner scans the table. Trigram search needs at least three useful characters.

A GIN trigram index answers "which rows match" but cannot sort by closeness. For "give me the 5 nearest names" use a GiST index (gist_trgm_ops), which supports order by full_name <-> 'Anna Jansn' limit 5 as an index scan. With only the GIN index, that same query reads and sorts all 20 000 rows.

Pitfalls with trigrams

% uses the similarity threshold of the session, so the same query returns different rows after set pg_trgm.similarity_threshold = 0.5. A trigram index is big (here 512 kB for 20 000 short names) and slows writes, so index only the columns you search. Case and accents matter to similarity as the characters are compared, not their meaning.

Summary

  • A B-tree can serve LIKE 'abc%' only if it is built with text_pattern_ops; a leading % always scans.
  • For case-insensitive matching, index and query lower(column); no extension needed.
  • Full-text search turns text into stemmed lexemes (tsvector) and searches them with a tsquery and @@. Use websearch_to_tsquery for user input.
  • ts_rank orders matches, ts_headline highlights them; compute headlines only for the rows you show.
  • Store the document in a generated tsvector column with an explicit configuration, and put a GIN index on it. Queries must use that column, or the index is ignored.
  • pg_trgm (Docker only here) finds similar strings and indexes ILIKE '%…%'; it needs at least three useful characters.
