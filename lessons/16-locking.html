Lesson 16 · Part 4

Locking and concurrency

lesson 16Docker exerciseslive playground

Lesson 15 showed that readers never block writers. Writers still block other writers, and schema changes block almost everyone. This lesson shows which locks PostgreSQL takes, how to see who is waiting for whom, how to build a safe job queue, what a deadlock is, and how to run ALTER TABLE on a busy table without taking the application down.

Learning goals

  • Explain which statements take row locks and which take table locks, and why plain SELECT takes neither kind that blocks anyone.
  • Choose between FOR UPDATE, FOR NO KEY UPDATE, FOR SHARE and FOR KEY SHARE.
  • Claim work from a queue table with FOR UPDATE SKIP LOCKED, and fail fast with NOWAIT or lock_timeout.
  • Read pg_locks and pg_blocking_pids() to find the session that is blocking another.
  • Recognise a deadlock error, explain why it happens, and prevent it by locking in a consistent order.
  • Use advisory locks, and tell session-level from transaction-level ones.
  • Run a schema change safely: know the lock level, set lock_timeout, and split risky changes into short steps.

Set up for this lesson

Use the shop database. Several demonstrations need two sessions. Open two terminals, run ./pg psql in each, and call them session A and session B. Every two-session example below is marked “two terminals”. The browser playground has only one session, so it can show which locks a statement takes, but not one session waiting for another. The playground's tiny dataset and single connection are for illustration only.

Everything you change in the two-terminal examples is rolled back at the end. If a session hangs, press Ctrl+C to cancel the waiting statement, then run rollback;.

1. Two kinds of lock: row and table

A lock is a promise that makes other sessions wait (or fail) when they want something incompatible. PostgreSQL uses two layers:

  • Row locks protect individual rows. UPDATE, DELETE and SELECT … FOR UPDATE take them. A row lock is not stored in a lock table in memory; it is recorded in the row's own header (the xmax field from lesson 15) and held until the transaction ends.
  • Table locks protect a whole table (or index). Every statement takes one. Most of them are weak and compatible with each other. A few, such as ALTER TABLE, are strong.

All locks are released at COMMIT or ROLLBACK. You cannot release one earlier (advisory locks, section 8, are the exception).

Look at what a row update really takes. Run this in the playground, then think about the output:

playground locks held by one session · one session only, so nothing waits

In the Docker database the answer is the same: RowShareLock on the table and on each of its indexes, plus an ExclusiveLock on the session's own transactionid. The table lock is weak: it only conflicts with the strongest table locks. The row lock itself is not in this list. That is why PostgreSQL can lock millions of rows without running out of memory. Another session that wants the same row finds the lock by waiting on this transactionid.

Why a plain SELECT never waits for a writer

A plain SELECT takes only AccessShareLock on the table, and no row locks. It reads the snapshot from lesson 15 instead. So a long report does not hold up an UPDATE, and an UPDATE does not hold up the report. Locks matter when two sessions write to the same rows, or when someone changes the table's structure.

2. Row lock modes

SELECT can lock rows without changing them. You choose how strong the lock is:

ClauseBlocks other sessions from…Use it when…
FOR UPDATEupdate, delete, and every other FOR … lock on the rowyou read a row and will delete it or change a key column
FOR NO KEY UPDATEupdate, delete, FOR UPDATE, FOR SHARE, but not FOR KEY SHAREyou read a row and will update it, without touching its primary or unique key. A normal UPDATE takes this lock.
FOR SHAREupdate and delete (many sessions can share the lock)you need the row to stay as it is while you read related data
FOR KEY SHAREonly DELETE and key changesPostgreSQL uses it for you inside foreign-key checks

The two weaker modes exist because of foreign keys. When you insert an order, the foreign key checks that the customer exists with FOR KEY SHARE. If an unrelated UPDATE of the same customer took a full FOR UPDATE, every order insert for that customer would wait. Because a normal UPDATE that does not change the key takes only FOR NO KEY UPDATE, they do not wait.

Two terminals. Prove it yourself:

Default to the weakest lock that works

If you lock a row so that you can update it a moment later, use FOR NO KEY UPDATE. Use FOR UPDATE only when you will delete the row or change its key. Strong locks block more sessions than you intended, including ones that only wanted to insert a child row.

3. Why you lock: the lost update

Reading a value in the application and writing it back later is a race. Two sessions both read stock 5, both write 4, and one sale is lost. There are two correct fixes.

Fix 1 is better whenever the new value can be computed in SQL. It is one round trip, and it holds the lock for the shortest possible time. Under READ COMMITTED, the waiting session re-reads the updated row and re-checks where stock > 0, so it does not oversell. Fix 2 is for decisions that really need application code.

4. Wait, skip, or fail fast: SKIP LOCKED, NOWAIT, lock_timeout

By default a session that meets a locked row waits for as long as it takes. Three options change that.

OptionIf a row is locked…
FOR UPDATE NOWAITraise an error at once: could not obtain lock on row in relation "products"
FOR UPDATE SKIP LOCKEDsilently leave that row out of the result and take the next ones
SET lock_timeout = '2s'wait up to two seconds, then raise canceling statement due to lock timeout. Applies to any lock, including table locks.

SKIP LOCKED turns a table into a work queue. Many workers can each ask for “the next job” and never take the same one, and none of them waits for another. Here is the pattern, which you will build in exercise 2. Run it in the playground to see one job being claimed:

Two terminals. See the skip happen against the shop's own products:

SKIP LOCKED gives an incomplete view on purpose

A query with SKIP LOCKED returns a result that depends on what other sessions are doing at that moment. That is exactly right for a queue and exactly wrong for a report. Never use it to count or to sum rows.

A queue worker must commit quickly

The claim only works while the row lock is held. If a worker commits the claim and then crashes while processing, the job stays marked as claimed forever. Real queues also store a lease time or a status and re-queue stale jobs. Do the claim and the status change in one transaction, and keep it short.

5. Seeing locks: pg_locks and pg_blocking_pids

When a statement hangs, two questions matter: what is it waiting for, and who holds it?

  • pg_stat_activity lists every session. A waiting one has wait_event_type = 'Lock'.
  • pg_blocking_pids(pid) returns the process ids that block the given session.
  • pg_locks lists every lock held or requested. A row with granted = false is a session in the queue.

Three terminals. A waiting session cannot run queries, so you diagnose from a third one (session C):

On the Docker database this returned one row: the update of session B, with wait_event_type = Lock and wait_event = transactionid, state active, and blocked_by holding session A's pid. In pg_locks the waiting request showed as locktype = transactionid, mode = ShareLock, granted = f: session B is waiting for session A's transaction to finish. To end the problem, either commit/roll back session A, or (as a last resort, from a superuser) call select pg_cancel_backend(pid) to cancel its statement, or pg_terminate_backend(pid) to end the whole session.

The real culprit is usually “idle in transaction”

A session that ran BEGIN, did some work, and then went quiet keeps all its locks. In pg_stat_activity it shows state = 'idle in transaction'. It is the most common reason a table “is locked”. Protect yourself with idle_in_transaction_session_timeout (exercise 1), and make sure application code never keeps a transaction open while it waits for a user or a remote service.

6. Deadlocks

A deadlock is a cycle of waiting: A waits for B, and B waits for A. Neither can ever finish, so PostgreSQL detects the cycle (after deadlock_timeout, one second by default) and cancels one of the transactions so the other can continue.

The victim gets this error (the process ids and transaction ids will differ on your machine):

The error has SQLSTATE 40P01. The other session simply continues. The cancelled transaction was rolled back as a whole, so your application must retry the entire transaction, not just the failing statement.

Prevent deadlocks with one rule

Always lock rows in the same order. If every transaction that touches several products does so in ascending id order, a cycle cannot form. In SQL: select id from shop.products where id = any($1) order by id for update; before you update. Keep transactions short, and treat 40P01 (and 40001, the serialization failure from lesson 15) as “retry”.

7. Table locks and the lock queue

Table locks have eight modes, from weak to strong. You do not need to learn the whole conflict matrix. Remember these modes:

ModeTaken byConflicts with
AccessShareLockplain SELECTonly AccessExclusiveLock
RowShareLockSELECT … FOR UPDATE and friendsthe two strongest modes
RowExclusiveLockINSERT, UPDATE, DELETEmodes that block writers (ShareLock and stronger)
ShareUpdateExclusiveLockVALIDATE CONSTRAINT, VACUUM, CREATE INDEX CONCURRENTLYitself and stronger modes, but not ordinary reads and writes
ShareLockplain CREATE INDEXall writers
AccessExclusiveLockmost ALTER TABLE, DROP TABLE, TRUNCATE, VACUUM FULLeverything, including plain SELECT

The queue effect

Locks are granted in order. If an ALTER TABLE waits for an older transaction that still holds a weak lock, every statement that arrives after it waits behind it, even plain SELECTs that would have been fine on their own. A migration that merely “waits a bit” can freeze the whole table.

Safe migrations

From the queue effect follows the rule for changing a busy table: ask for the lock with a short timeout and retry, instead of waiting in line.

Three more habits make migrations safe:

  1. Add constraints in two steps. ADD … NOT VALID is quick and checks only new rows. VALIDATE CONSTRAINT then scans the old rows with a lock that lets reads and writes continue. This is exercise 3.
  2. Build indexes with CREATE INDEX CONCURRENTLY (lesson 12), which takes ShareUpdateExclusiveLock instead of ShareLock. It cannot run inside a transaction block, and a failure leaves an INVALID index to drop.
  3. Avoid table rewrites. In current PostgreSQL, ADD COLUMN … DEFAULT constant does not rewrite the table, but changing a column's type often does. The rewrite holds an AccessExclusiveLock for as long as it takes.
A foreign key locks two tables

Adding a foreign key takes ShareRowExclusiveLock on both the child and the parent table (observed above), which blocks writes to both. Adding it as NOT VALID shortens the time it is held, because the scan of old rows moves to VALIDATE CONSTRAINT.

8. Advisory locks: locks you define

An advisory lock is a lock on a number that you choose. PostgreSQL does nothing with it except make other sessions wait for the same number. It is useful for “only one worker may run this job” or “only one process may migrate at a time”, without a table to lock.

FunctionHeld until
pg_advisory_xact_lock(key)the transaction ends. It cannot be forgotten.
pg_advisory_lock(key)you call pg_advisory_unlock(key), or the session ends. It survives COMMIT.
pg_try_advisory_lock(key)same as pg_advisory_lock, but returns false immediately instead of waiting
playground take, inspect and release an advisory lock

In a second session, select pg_try_advisory_lock(42); would return false while the first holds it.

Session-level locks and connection pools

A session-level advisory lock belongs to the connection, not to the transaction. If a connection pool hands your next statement to a different connection (lesson 26), you can unlock on the wrong session and leave the lock stuck on another one. Calling pg_advisory_lock twice needs two unlocks. Prefer pg_advisory_xact_lock whenever the work fits in a transaction.

When to use, when not to

Situation✅ Do this❌ Not this
Decrement stock safelyOne UPDATE … SET stock = stock - 1 WHERE stock > 0Read, compute in the app, write back
Many workers consume jobsFOR UPDATE SKIP LOCKED with a short transactionPlain FOR UPDATE (workers queue behind each other) or polling without locking (duplicates)
Fail fast instead of hangingNOWAIT or lock_timeoutWaiting forever and letting the user time out
Touching several rowsLock in a fixed order (by id) and retry on 40P01Random order, no retry
“Only one process may do X”pg_advisory_xact_lockA lock row you must clean up, or LOCK TABLE
Schema change on a busy tableSET lock_timeout, NOT VALID then VALIDATE, CONCURRENTLYA bare ALTER TABLE during peak traffic

Summary

  • Row locks live in the row header and last until the transaction ends. Plain reads take no row locks and never wait for writers.
  • Prefer the weakest lock that works: FOR NO KEY UPDATE over FOR UPDATE. Prefer one atomic UPDATE over read-then-write.
  • SKIP LOCKED makes a queue table, NOWAIT and lock_timeout make a session fail fast instead of hang.
  • pg_blocking_pids() and pg_locks show who blocks whom. The usual culprit is a session that is idle in a transaction.
  • A deadlock (SQLSTATE 40P01) is a cycle of waits. Lock in a consistent order, and retry the whole transaction.
  • Most ALTER TABLE forms take AccessExclusiveLock, and a waiting request blocks everyone behind it. Use lock_timeout, NOT VALID + VALIDATE, and CREATE INDEX CONCURRENTLY.
  • Advisory locks are locks on numbers you pick. Prefer the transaction-level form.
