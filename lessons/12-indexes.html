Lesson 12 · Part 3

Indexes

lesson 12Docker exerciseslive playground

An index is a second, sorted copy of some columns that lets PostgreSQL find rows without reading the whole table. It is the single most effective performance tool you have, and also one of the easiest to misuse. This lesson shows what a B-tree index can and cannot do, how to choose the column order of a composite index, when a partial, expression or covering index is the right shape, what GIN, GiST and BRIN are for, and what every index costs you on every write.

Learning goals

  • Explain what a B-tree index stores and why it speeds up equality, range and ORDER BY queries.
  • Choose the column order of a composite index from the query's equality, range and sort columns.
  • Build partial, expression and covering (INCLUDE) indexes, and say when each one pays off.
  • Pick between B-tree, GIN, GiST and BRIN for a given column and operator.
  • Measure what an index costs: disk space, slower writes and bloat.
  • Create and drop indexes on a live table with CONCURRENTLY, and recover from a failed build.

Set up for this lesson

Use the shop database, and in particular analytics.events: one million rows and, on purpose, no secondary indexes (only the primary key). Start with ./pg up if the container is not running.

1. What an index is

A table (the heap) stores rows in no particular order. To answer where customer_id = 42 without help, PostgreSQL must read every page of the table. That is a sequential scan:

The table is 117 MB. This plan reads all of it (workers share the job) to return about 200 rows. An index is a separate structure that maps column values to the location of their rows. The default kind, a B-tree, keeps the values in sorted order in a balanced tree, so finding one value takes a few page reads, however big the table is.

The estimated cost fell from about 21 000 to about 850. The actual query returns 217 rows, and EXPLAIN (ANALYZE, BUFFERS) shows it touched a few hundred pages instead of roughly 15 000. Three scan types appear in plans, and you should be able to tell them apart:

Plan nodeWhat it doesTypical when
Seq ScanReads the whole tableMany rows match, or no usable index
Index ScanWalks the index and fetches each row from the heap, in index orderFew rows, or the order of the index is wanted
Bitmap Index Scan + Bitmap Heap ScanCollects all matching row locations from the index, sorts them by heap page, then reads each page onceA middle number of rows
Index Only ScanAnswers from the index alone, without visiting the heap (section 6)The index contains every column the query needs

Reading plans in detail is the subject of lesson 13. Here, you only need to recognise which index (if any) a plan names.

2. What a B-tree is good at

Because a B-tree keeps values sorted, it helps with three things, not one:

  • Equality: where customer_id = 42.
  • Ranges: <, <=, >, >=, BETWEEN, and IS NULL.
  • Ordering: order by occurred_at can read the index in order instead of sorting.

The third is easy to forget. Without an index, “the 5 newest events” sorts a million rows:

A B-tree can be read forwards or backwards, so one ascending index serves both ORDER BY x and ORDER BY x DESC. With LIMIT 5 the scan stops after five rows; it never reads the rest. You only need DESC inside the index definition when a composite index mixes directions, for example (kind, occurred_at DESC) for ORDER BY kind, occurred_at DESC.

An index is not always used, and that is fine

Reading a row through an index means a random page read; reading the table sequentially is far cheaper per page. So when a query returns a large share of the table, the planner is right to ignore the index. We created one on kind to check:

The first query matches 55% of the table: a seq scan wins. The second matches 3%: the index wins. The share of rows a condition keeps is its selectivity. An index on a low-selectivity column (few distinct values, like kind or a boolean) rarely helps by itself. Section 5 shows how a partial index fixes exactly that.

3. Composite indexes and column order

An index can cover several columns: (a, b, c). It is sorted by a, then by b within equal a, then by c. That ordering decides what it can do, in the way a phone book sorted by last name, then first name can find “Smith, Anna” but cannot find every “Anna”.

  • It can search on a leading prefix: a; a, b; a, b, c.
  • Columns after the first range condition are scanned, not seeked.
  • It can deliver sorted output for the columns after the equality-matched prefix.

The rule of thumb for choosing the order:

  1. Columns tested with = first.
  2. Then the column used for a range condition or for ORDER BY.
  3. Among equality columns, put the one used most often on its own first.

Take this query, “the 10 latest page views of one customer”:

Two equality columns and a sort column, so the index is (customer_id, kind, occurred_at). We tried three indexes on the 1 000 000-row table:

IndexPlan for the feed query
(occurred_at)Index Scan Backward over the whole index, with Filter on the other two columns, stopping when 10 rows pass: it works only because 10 matches turn up early; for a rare customer it would walk most of the index
(customer_id, kind)Bitmap scan, then a Sort of the 128 matching rows, then Limit
(customer_id, kind, occurred_at)Index Scan Backward with Index Cond: (customer_id = 42 AND kind = 'page_view'). No sort, and it stops after 10 rows.

The equality columns can be in either order for this query: (kind, customer_id, occurred_at) gave the same plan shape. The order matters for other queries. An index led by customer_id also serves where customer_id = 42 alone (the plan names the index), and the one led by kind serves where kind = .... But a query on kind alone cannot use the customer_id-first index well: our test chose a sequential scan.

PostgreSQL 18 skip scan

PostgreSQL 18 can sometimes use a multi-column B-tree without a condition on its first column, by skipping through each distinct value of that column. It pays off only when the leading column has few distinct values. Do not design indexes around it: with a leading column like customer_id (thousands of values) we saw the sequential scan above.

A composite index is bigger, and one index is not several

(customer_id, kind, occurred_at) is 41 MB on this table, against 7 MB for (customer_id) alone. Do not add every possible combination. List the important queries and design a few indexes that serve several of them through their leading prefixes. An index on (a) is redundant if you already have (a, b).

4. Partial indexes

A partial index has a WHERE clause and contains entries only for rows that satisfy it. It is smaller, cheaper to maintain, and can turn a low-selectivity column into a useful one. Suppose customers are looked up in the events table only for purchases (3% of the rows):

The index is 448 kB instead of 7 MB. The planner can use it only when it can prove that the query's condition implies the index's condition. The kind = 'search' query cannot use it: a sequential scan.

Other classic uses: where deleted_at is null (only live rows), where status = 'pending' (a small work queue inside a big table), and a UNIQUE index that applies to a subset: create unique index on t (email) where deleted_at is null.

5. Expression indexes

An index on a column cannot serve a query on a function of that column. The plain index on email does nothing for a case-insensitive search:

The query must contain the same expression as the index. where email = '...' keeps using customers_email_key; the new index is only for lower(email). (The row estimate of 100 is a default guess; the planner has no statistics for the expression until the next ANALYZE, which autovacuum runs for you after enough changes. Lesson 13 explains statistics.)

The function must be IMMUTABLE

An index stores computed values, so the function must always return the same result for the same input. That excludes anything that depends on a setting such as the session time zone. create index on analytics.events (date_trunc('day', occurred_at)) fails with ERROR: functions in index expression must be marked IMMUTABLE, because the day boundary of a timestamptz depends on TimeZone. Fix the zone inside the expression: (occurred_at at time zone 'UTC')::date, and use that same expression in queries. We built that index and a query for one UTC day returned 2 773 events through it.

Another common expression index reads one key out of a JSONB document: create index on analytics.events ((payload->>'device')). The extra pair of parentheses is required around an expression that is not a plain function call. (JSONB indexing is the subject of lesson 10.)

6. Covering indexes: INCLUDE and index-only scans

Normally an index finds the rows, then PostgreSQL visits the heap to read the columns you asked for. If the index already contains every column the query needs, the heap visit can be skipped. That is an index-only scan. To add columns that are only carried (not searched or sorted), use INCLUDE:

Heap Fetches: 0 says that no row needed a trip to the table. Two conditions are needed for that.

  • The query uses only indexed columns. Selecting kind, payload as well gives a plain Bitmap Heap Scan again.
  • The visibility map is up to date. An index entry does not say whether a row is visible to your transaction (lesson 15). PostgreSQL keeps a visibility map of pages where all rows are visible to everyone, and VACUUM maintains it. On a table with lots of recent changes, an index-only scan still reads the heap for those pages, and Heap Fetches will be high.
Covering indexes are big

The index above is 32 MB, against 7 MB without INCLUDE (kind), because every entry now carries the text value. Use INCLUDE for a few small columns of one hot query, not as a habit. Do not INCLUDE a column you also filter or sort on: make it a key column instead.

7. GIN, GiST and BRIN

A B-tree needs values it can sort with < and =. Other data needs other shapes. PostgreSQL has a handful of index access methods, chosen with USING:

MethodGood forOperators it servesCost
btree (default)Scalars: numbers, text, dates= < > BETWEEN, sortingModerate size; cheap writes
ginValues that contain many items: arrays, JSONB, full-text@> <@ && on arrays, @> and ? on JSONB, @@ on tsvectorSlow to build, fast to read, slower writes
gistRanges, geometry, “nearest”, exclusion constraints&& @> <@ on ranges, distance operatorsFlexible; somewhat lossy
brinHuge tables whose values follow the physical row orderRanges and equality on a naturally ordered columnTiny; coarse

(Hash, SP-GiST and the pg_trgm operator classes also exist; trigram indexes are in lesson 11.)

GIN: many items per value

A Generalized Inverted Index stores, for every item inside a value, the list of rows that contain it. That is what you want for “which rows have the tag sale?”:

The JSONB query matches 55 601 of the 1 000 000 events, and the plan uses the GIN index through a bitmap scan. The jsonb_path_ops operator class supports only @>-style containment, but yields a smaller index: 6.6 MB here. The default class also supports key-existence operators, at a larger size.

GiST: ranges and geometry

A Generalized Search Tree arranges values by overlap. Its classic use is a range column: “which promotions are running on this date?”. We built a 5 000-row table of promotions with a daterange column to test it:

With 5 000 promotions of 10 days each, the plan was a Bitmap Index Scan on promotions_during_gist returning 10 rows. GiST is also what powers an EXCLUDE USING gist constraint (lesson 7).

BRIN: tiny indexes for huge, ordered tables

A Block Range Index stores only the minimum and maximum of each group of heap pages (128 pages by default). It is tiny, but it can only skip page groups whose min–max range excludes your value, so it works only if the column's values follow the physical row order. The statistic that tells you is correlation, in pg_stats: 1 means perfectly ordered, 0 means random.

In our table, id has correlation 1, but occurred_at has about 0.005: the seed data was inserted in random time order. A BRIN index on occurred_at there would be nearly useless (the planner chose a B-tree over it when both existed). Real event logs are written in time order, so we rebuilt the table sorted by time to see the ideal case:

A 24 kB index replaced a 21 MB one. The price is visible in the plan: the index is lossy. It returns whole block ranges, and PostgreSQL re-checks every row in them (“Rows Removed by Index Recheck”). It read 128 pages, not 15 000, and that is what you want from a BRIN index on a table of billions of rows.

BRIN depends on insert order

If rows are later updated or deleted and new rows land in old free space, the physical order drifts and the index loses its power, silently. Check correlation from time to time, and remember that a BRIN index can never give you sorted output.

8. What an index costs

An index is not free. Every index you add:

  • takes disk space, often a large fraction of the table;
  • slows every INSERT and DELETE, because each index must be updated too;
  • slows UPDATEs that change an indexed column, and prevents the cheaper “HOT” update path described in lesson 17;
  • can bloat: index pages fill with entries for dead rows, and plain VACUUM does not shrink the file.

See the space first, for the whole schema, in a database where you have not added anything yet:

Find indexes nobody uses

pg_stat_user_indexes.idx_scan counts how many times each index was used since the statistics were last reset. An index with zero scans over a representative period (a full business cycle, not an hour) costs you writes and space for nothing. Unique indexes with zero scans still enforce a constraint: keep them.

9. Building indexes on a live table

A plain CREATE INDEX takes a lock that blocks all writes (INSERT, UPDATE, DELETE) to the table until it finishes. Reads continue. On a big table that can mean minutes of outage. CREATE INDEX CONCURRENTLY builds the index without blocking writes:

It has costs and caveats you must know before you use it:

  • Slower. It scans the table twice and waits for older transactions to finish, so a long-running transaction anywhere in the database stalls it.
  • Not allowed inside a transaction block. After BEGIN, it fails with ERROR: CREATE INDEX CONCURRENTLY cannot run inside a transaction block. Most migration tools wrap each migration in a transaction; you must turn that off for this statement.
  • It can fail and leave an invalid index behind. A UNIQUE build that meets duplicates, a deadlock, or a cancelled session leaves an index that is still maintained on every write but never used by queries.

We provoked the failure on purpose, because shop.orders has many orders per customer:

indisvalid = f is the signature of a failed concurrent build. Drop it (drop index shop.orders_cust_uq), fix the cause, and run the build again. A re-run under the same name fails with “relation already exists” until you drop the leftover.

indnkeyatts counts the key columns (2) and indnatts all stored columns (3); the difference is the INCLUDE list. Concurrent builds are not available in the playground (they need several sessions), so try them in your scratch database.

Indexes do not fix a query that is wrong

A leading wildcard (like '%abc'), a function on the column (where date(occurred_at) = ...), comparing a column with a value of a different type, or selecting most of the table all defeat an ordinary index. Look at the plan before you build, and again afterwards.

Situation✅ Do this❌ Not this

Summary

  • A B-tree keeps values sorted, so it serves equality, ranges and ORDER BY; the planner still prefers a sequential scan when a query returns a large share of the table.
  • In a composite index, put equality columns first, then the range or sort column; the index serves its leading prefixes.
  • Partial indexes cover only the rows you query, expression indexes need the exact same expression (and an IMMUTABLE function), and INCLUDE enables index-only scans when the visibility map is current.
  • GIN is for containment in arrays, JSONB and text search; GiST for ranges and geometry; BRIN for huge tables whose column follows the physical row order (check correlation).
  • Every index costs disk and write time, and can bloat; VACUUM does not shrink it, REINDEX does. Drop indexes with zero scans.
  • On a live table use CREATE INDEX CONCURRENTLY outside a transaction, and check indisvalid afterwards.
