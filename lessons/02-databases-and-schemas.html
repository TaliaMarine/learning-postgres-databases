Lesson 02 · Part 1

Databases and schemas

lesson 02Docker exerciseslive playground

A PostgreSQL server holds a stack of containers: one cluster holds databases, a database holds schemas, a schema holds tables. Almost every confusing error message (“relation does not exist”, “permission denied for schema”, “cannot copy a database that is in use”) comes from not knowing which container you are standing in. This lesson draws the map, shows how a name like orders is turned into shop.orders, and teaches you to find out for yourself what exists and who owns it.

Learning goals

  • Place cluster, database, schema and table in one hierarchy, and say what you can and cannot do across each boundary.
  • Create a database from a template with CREATE DATABASE … TEMPLATE, and explain template0 versus template1.
  • Create and drop schemas, and use qualified names such as shop.orders.
  • Predict how search_path resolves an unqualified name, and set it for a session, a role or a database.
  • Explain what the public schema allows by default in PostgreSQL 18, and why that default changed.
  • Answer “what exists here, and who owns it?” with \l, \dn+, pg_database, pg_namespace and pg_class.

Set up for this lesson

Use the shop database and start the container with ./pg up if it is not running (see Set up your lab). The three exercises create a schema, a role and a database, The role and database they create have names starting with lab_, and the checker removes them for you.

\l lists the databases of the cluster; \dn+ lists the schemas of the database you are connected to. You will read both outputs line by line later in this lesson.

Docker and browser

The playgrounds on this page run one PostgreSQL in your browser. It has a single database, called postgres, with the same schemas as the course data (shop, analytics, course, public). So everything about schemas and search_path can be tried there. Creating databases and templates cannot, so those parts use the Docker database and are shown with its output.

1. The hierarchy: cluster, database, schema, table

Read the picture from the outside in. A cluster is one running PostgreSQL server with its data directory (lesson 1). Inside it live several databases. Inside each database live schemas, which are namespaces: folders for names. Tables, views, indexes, sequences, functions and types all live in a schema.

2. Databases

A database is the hard boundary. When a client connects it names one database (psql -d shop, or \c shop inside psql), and from then on everything it sees is inside that database. Backups, restores and most permissions work per database too. List them from SQL:

Two columns need explaining. datistemplate marks a database that may be used as the blueprint for new ones (next section). datallowconn says whether anyone may connect to it at all; it is false for template0, so nobody can modify the pristine blueprint by accident.

No queries across databases

You may write a three-part name database.schema.table, but only when the database part is the one you are connected to. Anything else is rejected, even though the other database is on the same server:

This is the main reason to prefer several schemas in one database over several databases when the parts of an application must be joined or kept consistent in one transaction. Separate databases are for things that must be isolated: different applications, different customers who must never share a backup, a test copy.

Creating and dropping

CREATE DATABASE cannot run inside a transaction block, and a plain DROP DATABASE refuses while anyone is connected. The owner of a database is a role (datdba in pg_database); lesson 3 introduced owners and lesson 4 shows what ownership allows.

3. Template databases

A new database is not built from nothing. CREATE DATABASE makes a file-level copy of another database, called the template. Everything in the template appears in the copy: schemas, tables, rows, functions, extensions and default grants. Roles are not copied, because they belong to the cluster.

TemplateWhat it isUse it when
template1The default source of every CREATE DATABASE. Ordinary, editable.You want something (an extension, a helper function) in every new database
template0A pristine copy that nobody can connect to or change.You need a different encoding or locale than template1 has, or a clean start
shop_templateThe course's own snapshot of the seeded shop data.The checker clones it for every exercise. You can too.

Copying 240 MB takes a moment, and then lab_s02_try is an independent database: change or delete anything in it and shop stays untouched. This is the fastest way to get a safe sandbox.

The third is about templates themselves. Any database can become a template with alter database NAME is_template true, and from then on drop database refuses it (cannot drop a template database) until you set the flag back to false.

Template changes are not retroactive

A copy is a snapshot. If you add a function to template1 today, databases created last week do not get it. Roles are never copied (they belong to the cluster), so objects in the copy keep the same owners as in the template, and the database itself belongs to whoever you name in OWNER.

4. Schemas

A schema is a namespace. Two schemas can each hold a table called orders without clashing, exactly like two directories can each hold a file called notes.txt. The full name is schema.object, and it is how you say precisely which one you mean.

A schema is also the unit of permission for access to a group of tables: a role needs USAGE on the schema before it can touch anything inside, whatever the table's own privileges say (lesson 4). Giving each application or concern its own schema is the usual way to organise a database.

playground two tables called orders, in two schemas

Both tables exist. shop.orders has 12 rows in the browser copy; archive.orders has the three you copied. Which one does a bare orders mean? That is decided by search_path.

A schema is not a database

drop schema … cascade deletes every table, view and function inside it with no further question. Read the name twice. A schema is only a namespace: it is not a separate place on disk, and the database is still the unit of connection, of backup and restore, and of isolation.

5. search_path: how a bare name finds its table

When you write select * from orders, PostgreSQL looks for orders in each schema listed in the setting search_path, in order, and uses the first match. If none matches you get relation “orders” does not exist, even though shop.orders is right there.

The three lines show the rules:

  • The default is "$user", public. $user means “a schema named like the current role”. It is skipped when no such schema exists, which is why current_schemas(false) shows only {public}.
  • pg_catalog is always searched first, even when you do not list it. That is how count(*), now() and text are found.
  • Nothing in the list contains orders (the table is in shop), so the query fails.
  • The first existing schema in the path is also where an unqualified CREATE TABLE puts the new table.
playground change the order, change the answer

With archive, shop the bare name orders finds archive.orders first and you see 3. Swap the order to shop, archive and you see 12. SET LOCAL lasts until the end of the transaction, so the playground session is left as it was; plain SET would last for the whole session.

Where a search_path can be set

The most specific setting wins. A new session starts from the server's default, then the settings stored in the catalog are applied at login, and a SET inside the session overrides all of them. The list runs from the shortest-lived and most specific to the broadest:

ScopeCommandApplies
One transactionSET LOCAL search_path = …Until COMMIT or ROLLBACK
One sessionSET search_path = …Until you disconnect or RESET
One role in one databaseALTER ROLE r IN DATABASE d SET search_path = …Every new session of that role in that database
One roleALTER ROLE r SET search_path = …Every new session of that role
One databaseALTER DATABASE d SET search_path = …Every new session in that database

To see the order, set all three catalog levels on a scratch database and then remove them one at a time. A new session reports shop, analytics (role in database), then shop (role only), then analytics (database only). The stored settings are visible with \drds:

ALTER ROLE … SET waits for the next login

ALTER ROLE r SET search_path and ALTER DATABASE d SET search_path change what is stored in the catalog. A session that is already open keeps its old value. If a change “does nothing”, reconnect before you suspect anything else.

The schema named after the role

Because of "$user", a role that owns a schema with its own name gets a private workspace without configuration: unqualified CREATE TABLE lands in that schema. This playground builds one inside a transaction and throws it away, so you can run it as often as you like. The browser database starts with the plain path public, so the script puts $user back first.

playground a table lands in the schema named after the role
Never put a schema others can write to at the front

The first match wins, so whoever can create objects in an early schema can create a table or function with a familiar name and have your queries find it first. Keep public last, never add schemas you do not control, and in security-sensitive code write qualified names. Lesson 5 shows how this is exploited through SECURITY DEFINER functions.

Qualify names in scripts

In migrations, deployment scripts and anything that must behave the same for every role, write shop.orders, not orders. It costs six characters and removes a whole class of “works on my laptop” differences caused by different search paths.

6. The public schema and its defaults

Every new database starts with a schema called public. For many years any role could create objects in it, which made it the place where tables ended up by accident and a standing security risk. In PostgreSQL 18 (and since version 15) the defaults are stricter. Read them straight from the catalog:

playground who may use and create in public, and in shop

Decode the acl column of public:

  • pg_database_owner=UC/pg_database_owner — the owner may Use and Create. The text after the slash says who granted it.
  • =U/pg_database_owner — an empty name before the equals sign means PUBLIC, every role. PUBLIC may use the schema (look up objects in it) but may not create anything.

The owner is pg_database_owner, a built-in role that is automatically “whoever owns the current database”. So the database's owner can create in public, and nobody else can unless the owner grants it. The shop schema has no ACL at all (null): only its owner may use it, and the superuser bypasses checks. Compare the last two columns: PUBLIC can use public but not shop.

See the effect with a role that has no privileges. This playground is meant to fail, and it ends with the error:

The message is permission denied for schema public. The playground stops at the first error, as psql does, but everything before it has already happened: the role intern now exists. Running the box again would fail with role "intern" already exists; press Reset data to start clean.

Old databases can still be open

The strict default applies to databases created with it. A database that was created on an older server and carried forward may still have =UC/… on public, which lets every role create tables there. Check with the query above. To close it: revoke create on schema public from public;. Lesson 4 explains this command.

Do not build on public

Even with the strict default, put your own tables in a schema that has a meaningful name and an explicit owner (shop, billing, app). Leave public for extensions and leftovers. Lesson 5 turns this into a full layout.

7. Finding things: catalogs and psql

PostgreSQL stores its own metadata in ordinary tables called the system catalogs, all in the schema pg_catalog. You never have to guess what exists: ask.

QuestionpsqlSQL
Which databases exist, who owns them?\lpg_database
Which schemas, who owns them, who may use them?\dn+pg_namespace
Which tables and views are there?\dt shop.*, \dvpg_class, pg_tables
What does one table look like?\d shop.orderspg_attribute
Which role or database settings are stored?\drdspg_db_role_setting
Everything in every schema\dt *.*pg_class

Read \dn+ in the course database. This is what a fresh clone prints:

The Access privileges column is the ACL (access control list) in text form. Empty means nobody has been granted anything beyond the owner's implicit rights. The same format appears in \l for databases (for example =c/postgres on template1: PUBLIC may connect). Lesson 4 teaches you to read every letter.

pg_catalog and information_schema

There are two places to look, and they answer slightly different questions. pg_catalog is PostgreSQL's own, complete view of everything. information_schema is the SQL standard's portable view of the same facts, but it only shows objects you have some privilege on. To check that, give a role SELECT on one table and query both as that role:

Use information_schema when you want portable SQL or want to see what the current role can reach. Use pg_catalog when you are administering and need the truth, including owners and ACLs.

Names to OIDs and back

Catalog tables link to each other through numbers called OIDs (object identifiers). You rarely type them: casts do the lookup. 'shop.orders'::regclass turns a name into the table's OID and fails if it does not exist; relnamespace::regnamespace turns a schema OID back into a name; and pg_get_userbyid(oid) turns an owner OID into a role name. A bare 'orders'::regclass obeys search_path exactly like a query does, which makes it a handy way to test it.

Summary

  • A cluster holds databases and roles; a database holds schemas; a schema holds tables and other objects. A connection reaches one database, and queries cannot cross databases.
  • Prefer several schemas in one database when the parts must be joined; use separate databases for real isolation.
  • CREATE DATABASE … TEMPLATE x is a file-level copy. The source must have no other sessions. Use template0 to change encoding or locale.
  • search_path is searched left to right; pg_catalog is implicit; the first schema is where unqualified creates land. Set it per session, role, database, or role-in-database; role and database settings apply from the next login.
  • Since PostgreSQL 15 an ordinary role can use public but not create in it. The owner is pg_database_owner. Put your tables in a named schema instead.
  • Ask the catalogs: \l, \dn+, pg_database, pg_namespace, pg_class. information_schema shows only what you may see; pg_catalog shows all.
