Lesson 23 · Part 6

Backup, restore and PITR

lesson 23Docker exerciseslive playground

A backup is only worth something on the day you restore it. This lesson shows the two kinds of PostgreSQL backup: a logical dump made with pg_dump, and a physical base backup plus archived WAL. It covers restoring each, recovering to a moment just before a mistake, and checking that a restore really worked.

Learning goals

  • Choose between a logical dump and a physical backup, and say what each one can and cannot restore.
  • Make dumps in the plain, custom, directory and tar formats, and say when each format fits.
  • Back up roles and other cluster-wide objects with pg_dumpall --globals-only, because pg_dump leaves them out.
  • Restore with pg_restore using --clean, --if-exists, --no-owner, --role and a list file.
  • Explain how pg_basebackup, WAL archiving and recovery_target_time give point-in-time recovery.
  • Verify a restore with row counts and fingerprints, and explain why an untested backup is not a backup.

Set up for this lesson

Use the Docker database. The commands in this lesson run inside the container through ./pg exec, because that is where pg_dump, pg_restore and pg_basebackup are installed and where the server's files live. Never practise a restore on shop: make a copy first and work on the copy. The copy is cloned from the course template, so it starts identical to a fresh shop.

The last line prints pg_dump (PostgreSQL) 18.6 …. The in-browser playground cannot run any of these programs: it is a single PostgreSQL process with no file system you can reach, no pg_dump and no WAL archive. It appears only once, for the verification query in section 7.

1. Two kinds of backup

A logical backup is a description of the data: SQL commands (or an archive of them) that recreate the tables and their rows. A physical backup is a copy of the server's data files, byte for byte. They answer different questions.

QuestionLogical: pg_dumpPhysical: pg_basebackup + WAL
What does it copy?One database, or chosen schemas and tablesThe whole cluster: every database, every role
Restore into another major version?Yes, that is one way to upgradeNo, same major version only
Restore one table?YesNo, all or nothing
Restore to 14:31 yesterday?No, only to the moment the dump startedYes, with archived WAL (section 6)
Speed on a large databaseSlow: rows are re-inserted and indexes rebuiltFast: files are copied, then WAL is replayed

Production systems usually have both: physical backups with WAL archiving for disasters and point-in-time recovery, and logical dumps for moving data, restoring a single table, and upgrades. A snapshot is the view of the data a transaction sees (lesson 15). pg_dump reads the whole database inside one snapshot, so the dump is consistent even while the application keeps writing, and it does not block normal reads or writes.

2. pg_dump and its four formats

pg_dump connects like any client and writes out one database. The -F option picks the format:

FormatOptionWhat you getRestore with
plain-Fp (default)One SQL script you can read and editpsql -f
custom-FcOne compressed archive filepg_restore, with selective and parallel restore
directory-FdA directory: one compressed file per table plus a toc.datpg_restore; the only format that can also be dumped in parallel (-j)
tar-FtA tar file of the directory layout, not compressedpg_restore

On the course database (about 240 MB on disk), the plain script was 129 MB and the custom archive 29 MB, because the custom format compresses by default. Use -Fc unless you have a reason not to: it is one file, it is compressed, and pg_restore can pick objects out of it. You can read an archive's table of contents without restoring it:

Each line after the header is one archive entry: a schema, a table definition, a table's data (TABLE DATA), a constraint, an index. Section 4 uses these lines to restore a single table.

Choosing what to dump

--exclude-table-data keeps the table's definition but skips its rows. It is useful when one huge, rebuildable table (a log, an event stream) dominates the dump.

A data-only dump of a self-referencing table

shop.categories has a foreign key to itself (parent_id). Dumping it with --data-only prints the warning there are circular foreign-key constraints on this table, because the rows may not load in an order that satisfies the key. Prefer full dumps; a data-only dump is for loading into tables that already exist, and then you need --disable-triggers or a careful order.

3. Roles are not in the dump: pg_dumpall

Roles, their passwords and memberships, and tablespaces are cluster-wide: they belong to the server, not to any one database (lesson 3). pg_dump dumps one database, so it does not include roles. Its archive says who owns each table and who was granted what, but not how to create those roles. Restore it on a new server without them and every ALTER … OWNER TO and GRANT fails.

pg_dumpall dumps the whole cluster as one plain SQL script. Its --globals-only option writes just the cluster-wide part:

The file contains CREATE ROLE and ALTER ROLE … PASSWORD 'SCRAM-SHA-256$…' lines, so it holds the password verifiers of every role. Store it as carefully as the data. --no-role-passwords leaves the passwords out, and --roles-only skips tablespaces too.

Settings attached to a database with ALTER DATABASE … SET, and grants on the database itself such as CONNECT, are written only when you dump with -C (--create). With -C the dump starts with CREATE DATABASE and recreates those too.

A restore that fails on owners is a restore that fails at 3 a.m.

The standard pair is pg_dumpall --globals-only plus one pg_dump -Fc per database. Back up both on the same schedule, and restore the globals first. If you cannot (a managed service often hides the real superuser), restore with --no-owner and reapply grants, as section 4 shows.

4. pg_restore

A restore needs a target database. To get an exact copy, start from an empty database made from template0: template1 may contain objects someone added, which would then clash with the dump.

Restore the same archive into the same database a second time and it fails: the objects already exist. pg_restore reports each failure and carries on, finishing with pg_restore: error: could not execute query: ERROR: schema "analytics" already exists … and pg_restore: warning: errors ignored on restore: 38. The options that matter:

OptionWhat it doesUse it when
--clean (-c)Drops each object before recreating itYou restore over an existing copy
--if-existsMakes those drops DROP … IF EXISTSAlways together with --clean, so missing objects are not errors
--no-owner (-O)Skips the ALTER … OWNER TO commands; the restoring role owns everythingThe original owner roles do not exist on the target
--role=NAMERuns SET ROLE NAME before restoring, so objects are created as that roleCombined with --no-owner: give everything to the application owner role
--no-acl (-x)Skips GRANT/REVOKEYou will apply the target's own privilege scheme
--exit-on-error (-e)Stops at the first error instead of continuingScripts and tests: a half restore should not look like success
--single-transaction (-1)Everything or nothingSmall restores where a partial result is worse than none
-j NRestores with N parallel jobs (custom and directory formats)Large restores on a machine with spare cores
-C with -d postgresCreates the database named in the archive, then restores into itRecreating a database with its own settings

The second command needs app_owner to exist and to be allowed to create schemas in some_db (the simplest way is to make it the database's owner). Exercise 3 does exactly this.

Restoring one table

pg_restore -t order_items restores a table's definition and its rows, but not its primary key, foreign keys or indexes: those are separate archive entries. Planner statistics after a restore

By default the course container's 18.6 pg_dump does not write planner statistics, so a restored database has none until ANALYZE runs, and the first queries can get poor plans. Run vacuumdb --analyze-in-stages (or ANALYZE) right after a large restore. PostgreSQL 18's pg_dump can carry statistics if you ask with --statistics.

5. Physical backups: pg_basebackup

pg_basebackup copies the whole data directory of a running server over a replication connection. The copy is taken while the server keeps writing, so on its own it is inconsistent. It becomes consistent when the WAL written during the copy is replayed over it. WAL (lesson 22) is the server's log of every change. -X stream makes pg_basebackup fetch that WAL alongside the files, so the backup is self-contained.

-Ft writes tar files; -Fp writes a ready-to-start data directory. The backup_manifest lists every file with a checksum, and pg_verifybackup checks the backup against it and prints backup successfully verified. For tar backups it needs -n (skip parsing the WAL), otherwise it stops with pg_waldump cannot read tar files. This backup is 2.2 GB, ten times the logical dump, because it copies the whole cluster as files: every database, every index and the WAL. Delete it when you are done; the container's disk is not a backup location.

Backups taken on the database server are not backups

The commands above write to /tmp inside the container to show how the tools work. A real backup must live somewhere that does not fail together with the server: another machine, another region, object storage. Tools such as pgBackRest and Barman manage base backups, WAL archives, retention and off-site copies for you, and they are what most teams run in production.

6. WAL archiving and point-in-time recovery

A base backup restores the cluster to the moment the backup finished. To get to any later moment, you also keep every WAL segment the server writes after that. This is WAL archiving: when a 16 MB segment file is full, the server runs archive_command to copy it somewhere safe. Restoring a base backup and replaying archived WAL up to a chosen time is point-in-time recovery (PITR).

%p is the path of the finished segment and %f its file name. The test ! -f refuses to overwrite a file that is already archived. The command must return success only once the file is safely stored: the server keeps a segment until archiving reports success, and retries otherwise. pg_stat_archiver shows how it is going, through the columns archived_count, last_archived_wal and failed_count.

Recovering to a moment

Suppose someone ran delete from t by mistake. You note a time just before it, then:

  1. Stop the damaged server (or build the recovery on another machine, which is safer).
  2. Put a copy of the base backup in place as the new data directory.
  3. Tell it where the archive is and where to stop, then create an empty file called recovery.signal in the data directory.
  4. Start the server. It replays archived WAL up to the target, then opens for writes.

Transaction 755 was the DELETE. Recovery stopped before its commit, so the table came back with all of its rows. recovery_target_action defaults to pause, which leaves the server read-only at the target so you can look around before you commit to that point. promote ends recovery and opens the server for writes. Instead of a time you can stop at a transaction (recovery_target_xid), a WAL position (recovery_target_lsn) or a named restore point created earlier with pg_create_restore_point().

The archive must be complete

Recovery can only replay WAL it has. One missing segment and recovery stops there, no matter what the target is. A base backup older than your oldest archived segment is useless for PITR. Monitor pg_stat_archiver.failed_count, and keep base backups and WAL under the same retention policy.

7. An untested backup is not a backup

Backups fail quietly. Common causes: the job stopped running months ago, the archive is missing a segment, the roles were never dumped, the file is truncated, or nobody knows the restore steps. You find out only when you restore. So restore on a schedule, into a scratch server, and check the result:

  1. The restore finished without errors (use --exit-on-error so a failure is loud).
  2. Row counts of the important tables match the source at the time of the backup.
  3. A fingerprint of key tables matches. A fingerprint here is a hash over the rows in a fixed order, so any changed value changes it.
  4. The application can connect as its own role and run a few real queries.
  5. You wrote down how long the restore took. That number is your real recovery time.

In the playground you get 12 orders and 8 products. In the Docker database the same query returns 200000 orders with fingerprint 7ea613783b108e6e025522a34219968c and 500 products with cc940a88a94301e4fae165f4897a6687. Run it on a restored copy and you should see exactly those values.

Two numbers to agree on before you need them

The recovery point objective (RPO) is how much recent data you can afford to lose. The recovery time objective (RTO) is how long you can be down. A nightly dump means an RPO of up to a day. WAL archiving brings it down to minutes or less. Only a timed test restore tells you your RTO.

When to use, when not to

Situation✅ Do this❌ Not this

Summary

  • A logical dump (pg_dump) copies one database as SQL or an archive; a physical backup (pg_basebackup) copies the whole cluster's files.
  • Use -Fc by default; -Fd when you want parallel dumps; plain SQL when a person must read it.
  • pg_dump leaves out roles and tablespaces. Back them up with pg_dumpall --globals-only.
  • pg_restore can clean first, skip owners, run as a role, stop on error, and restore exactly the entries in a list file.
  • Base backups plus archived WAL give point-in-time recovery: replay to recovery_target_time, then promote.
  • A backup is proven only by a timed test restore whose counts and fingerprints match.
