Lesson 07 · Part 2

Constraints and schema design

lesson 07Docker exerciseslive playground

A constraint is a rule the database enforces on every write, from every client, forever. This lesson shows the constraints PostgreSQL offers (keys, foreign keys with their actions, check and exclusion constraints), how to postpone a check until commit, how identity columns and generated columns replace hand-written counters and derived values, and how to tell whether a table is shaped well.

Learning goals

  • Choose between a primary key, a unique constraint and a unique index, and explain what NULL does to each.
  • Pick the right foreign key action (NO ACTION, RESTRICT, CASCADE, SET NULL, SET DEFAULT) for a delete and for an update.
  • Write check and exclusion constraints, and add a check to a big table without a long lock using NOT VALID.
  • Use DEFERRABLE constraints for cyclic references and multi-row swaps.
  • Prefer identity columns to serial, and explain why sequence gaps are normal.
  • Use generated columns, and say how STORED and VIRTUAL differ in PostgreSQL 18.
  • Spot a table that breaks first, second or third normal form, and say what to do about it.

Set up for this lesson

Use the shop database; it is already seeded. The shop tables already carry constraints, so you can read real ones before you write your own. The exercises create tables whose names start with lab_07_. One of them needs the btree_gist extension, which the course image includes. Start with ./pg up if the container is not running.

\d prints the columns, the primary key, the check constraints and the foreign keys of a table. Keep it in mind: it is the quickest way to see which rules a table enforces.

Playground and Docker

The playground boxes on this page create small tables of their own, so you can break rules without harming anything. They share one database per page. A box that creates tables starts with drop table if exists, so you can run it again. The lesson shows an error in a box only as that box's last statement, because a box runs as one transaction and an error undoes the whole box.

1. Primary and unique keys

A primary key says: this column (or this set of columns) identifies one row, and there is at most one row per value. It is a unique constraint plus NOT NULL, and a table has at most one. A unique constraint says only that no two rows share a value; a table can have many. Both are enforced by a unique index that PostgreSQL creates for you, so lookups by that key are fast.

The shop uses a surrogate key (a meaningless number the database makes up, such as customers.id) as the primary key and keeps the natural key (a value from the real world, such as email or sku) as a unique constraint. That way an email change touches one column in one table, not every table that points at the customer.

2. Foreign keys and their actions

A foreign key says: the value in this column must exist in a key of another table (or be NULL). The other table's column must itself be a primary key or have a unique constraint, or PostgreSQL refuses to create the foreign key (there is no unique constraint matching given keys for referenced table). The child table holds the foreign key; the parent table is the one it points at.

Inserting a child row with no parent is always an error. What happens when you delete or change a parent row that children still point at is up to the foreign key's action. You choose one for ON DELETE and one for ON UPDATE:

ActionWhen the parent row is deleted or its key changesCan be deferred
NO ACTION (default)Error, if children still point at the old value when the statement endsyes
RESTRICTError immediately, even if the statement would put things right laterno
CASCADEDelete the children (on delete) or copy the new key into them (on update)no
SET NULLSet the child's foreign key column to NULLno
SET DEFAULTSet the child's column to its default value, which must itself exist in the parentno

Every foreign key in the shop uses the default, NO ACTION. Run the lesson's first query in the Inspect section to see them. The playground below sets up two child tables with different actions and deletes one parent row:

playground the same delete, two different actions

Department 1 had two employees in each table. With CASCADE they were deleted along with the department, so one row is left. With SET NULL all three rows survive, and only one is still linked to a department.

CASCADE deletes more than you think

A cascade can chain: delete a customer, which deletes their orders, which deletes their order items. That is correct for data that has no meaning without its parent (order items), and wrong for data you must keep (invoices, audit rows). The shop's default, NO ACTION, makes deletes fail loudly, which is the safe starting point. Use CASCADE where you can say, in one sentence, why the child is worthless without the parent.

See the default in action. In the mini shop of the playground, product 1 is on order, so deleting it must fail. This box ends with an error, on purpose:

playground expected error: foreign key violation

The message is update or delete on table "products" violates foreign key constraint "order_items_product_id_fkey" on table "order_items". It names the constraint and the child table, which is how you find out who still depends on the row.

NO ACTION or RESTRICT?

They sound the same and differ in one way: when the check happens. NO ACTION checks at the end of the statement, and, if you declare the constraint DEFERRABLE (section 5), at commit. RESTRICT checks at once and can never be deferred. In a transaction that deletes a parent and then re-inserts the same key before commit, a deferred NO ACTION foreign key accepts the result; a RESTRICT one refuses at the DELETE. In practice, use the default unless you need the strict behaviour.

SET NULL can name the columns to clear, which matters for a composite foreign key that shares a column with something else (PostgreSQL 15 and later):

Foreign keys are not indexed for you

PostgreSQL indexes the parent side of a foreign key (it is a primary key or unique constraint). It does not index the child side. In the shop, nothing indexes orders.customer_id or order_items.product_id. Deleting a product then forces PostgreSQL to scan all of order_items to check that no row still points at it, and the same scan runs for every ON DELETE CASCADE. Joins from parent to child need the index too. Add one to every foreign key column you join on or delete through. The Inspect section has a query that lists the unindexed ones, and lesson 12 covers the indexes themselves.

A composite foreign key with a NULL is not checked

The default matching rule, MATCH SIMPLE, skips the check if any column of a composite foreign key is NULL. Mark every column of a composite foreign key NOT NULL, or use MATCH FULL, which refuses a mix of null and non-null values.

3. Check and NOT NULL constraints

A check constraint is a boolean expression over the columns of one row. The write is refused when the expression is false. Read that sentence twice, because NULL is not false:

If the column must have a value, add NOT NULL as well. Since PostgreSQL 18, NOT NULL is stored as a constraint with a name, like the others, and you can give it one: b integer constraint b_required not null. It appears in pg_constraint with type n.

Two limits to know:

  • A check sees only its own row. check (x in (select id from other)) fails with cannot use subquery in check constraint. Use a foreign key for rules about other tables.
  • The expression must be immutable (same inputs, same output, always). check (created_at < now()) would change its answer over time, and does not belong in a constraint.

Adding a check to a table that already has data

ALTER TABLE ... ADD CONSTRAINT ... CHECK scans the whole table to prove every existing row passes, and holds a strong lock while it does. On a big table, add the constraint as NOT VALID first: new writes are checked at once, old rows are not. Then VALIDATE CONSTRAINT checks the old rows with a much weaker lock. This block runs in a transaction that rolls back, so your shop stays untouched:

convalidated is f until validation. Here the VALIDATE fails with check constraint "products_price_cap" of relation "products" is violated by some row, because the shop sells products above 100. That is the point of the pattern: you find the bad rows, fix them, and validate again. The same NOT VALID option exists for foreign keys.

4. Exclusion constraints: no overlaps

A unique constraint says “no two rows are equal”. An exclusion constraint generalises it: “no two rows are in relation X”, for an operator you choose. The classic use is “no two bookings overlap”, with the range overlap operator &&. A range is a single value that holds a start and an end, such as daterange or tstzrange (lesson 6). Exclusion constraints are backed by a GiST index (an index type for non-equality questions such as “overlaps”), hence using gist.

playground bookings may touch, but not overlap

A range written [a, b) includes a and excludes b, so a stay that ends on the 4th does not collide with one that starts on the 4th. Now try an overlapping stay. This box ends with an error, on purpose:

playground expected error: conflicting key value

The error is conflicting key value violates exclusion constraint "room_booking_stay_excl" followed by a detail line that shows both ranges. Two warnings go with this feature. First, a check in the application (“select, then insert if free”) cannot do this job: two sessions can both see the room as free. The constraint can, because the index serializes the conflicting inserts. Second, the more useful form is “no overlap for the same room”, which mixes = on a column with && on a range. A plain GiST index cannot handle = on an integer or text column. The extension btree_gist adds that, and the course image ships it:

5. Deferrable constraints

Normally PostgreSQL checks a unique, foreign key or exclusion constraint right away. A constraint created DEFERRABLE can instead be checked at commit, so the data may be wrong in the middle of a transaction as long as it is right at the end. There are two flavours:

  • DEFERRABLE INITIALLY IMMEDIATE: checked at the end of each statement by default; you can switch it to commit time with SET CONSTRAINTS name DEFERRED.
  • DEFERRABLE INITIALLY DEFERRED: checked at commit by default.

Why you need it: swapping two rows

A plain unique constraint is checked one row at a time. Swapping two values with a single UPDATE fails halfway, when the first row already holds the second row's value. This box ends with an error, on purpose:

playground expected error: the swap collides in the middle

You should see duplicate key value violates unique constraint "queue_pos_key". The data before and after the swap is valid; only the middle is not. Declare the constraint deferrable, and ask for the check at commit:

playground the same swap, with the check postponed

The swap works. (A deferred unique check at commit is also why a deferrable unique constraint cannot be the target of INSERT ... ON CONFLICT, see lesson 9.)

Why you need it: a cycle

Table a points at b, and b points back at a. Whichever row you insert first has no parent yet. Make at least one of the two foreign keys DEFERRABLE INITIALLY DEFERRED, insert both rows in one transaction, and the check runs at commit, when both exist. The same trick lets you delete a parent and re-insert it in a single transaction.

Deferred errors arrive late

A deferred violation is reported by COMMIT, far from the statement that caused it, so the error is harder to trace in application code. Defer only the constraints that need it. Only UNIQUE, PRIMARY KEY, EXCLUDE and FOREIGN KEY constraints can be deferrable; CHECK and NOT NULL cannot.

6. Identity columns versus serial

A sequence is a separate database object that hands out increasing numbers. Two column features use one to fill an id automatically:

  • serial: an old shorthand. It creates a sequence, sets DEFAULT nextval(...) and links the sequence to the column. It is not in the SQL standard.
  • GENERATED ... AS IDENTITY: the standard way. The shop uses it everywhere, for example shop.customers.id.

Why identity is the better default:

  • It protects the column. With GENERATED ALWAYS, an INSERT that supplies its own value fails with cannot insert a non-DEFAULT value into column "id", unless you write OVERRIDING SYSTEM VALUE on purpose. A serial column happily accepts a manual value that collides later.
  • Privileges follow the table. A role with INSERT on a table with an identity column can insert. With serial the role also needs USAGE on the sequence, or the insert fails with permission denied for sequence (lesson 4).
  • It is tidier to copy. The sequence is part of the column, so dropping the column or the table drops the sequence.

GENERATED BY DEFAULT AS IDENTITY is the relaxed form: the database fills the value only when you give none. Use it when you load rows that already have ids. The shop's customers.id is ALWAYS, which information_schema.columns.identity_generation reports.

playground a skipped insert still uses a number
Gaps in ids are normal

Ticket b got id 3, not 2: the skipped insert used number 2. A sequence hands out each number once, and it does not hand it back if the transaction rolls back, if the insert hits a unique violation, or if INSERT ... ON CONFLICT DO NOTHING skips the row. Never use an id as a count or as a gap-free invoice number. If the law requires gap-free numbers, generate them in a separate table under a lock, and accept the contention.

Reloading data? Reset the sequence

If you copy rows in with explicit ids, the sequence does not know. The next normal insert then reuses an existing id and fails. Fix it once with select setval(pg_get_serial_sequence('shop.customers', 'id'), (select max(id) from shop.customers));. pg_get_serial_sequence finds the sequence behind an identity column as well as a serial one.

7. Generated columns

A generated column holds a value the database computes from other columns of the same row. You cannot write to it, and it cannot drift out of date the way a copy maintained by application code can. PostgreSQL 18 has two kinds:

STOREDVIRTUAL (the default in 18)
When it is computedOn every insert and update, then written to the tableWhen you read it
Takes disk spaceyesno
Can be indexedyesno (indexes on virtual generated columns are not supported)
Adding it to an existing tableRewrites the whole tableNo rewrite, instant

If you write GENERATED ALWAYS AS (expr) with neither keyword, you get VIRTUAL in PostgreSQL 18. Releases before 18 had only STORED, and required you to say so. Write the keyword every time, so the table means the same on every version.

playground one stored and one virtual column

Writing to a generated column is refused. This box ends with an error, on purpose:

playground expected error: generated column

The message is cannot insert a non-DEFAULT value into column "total". A generated column may use only immutable functions and columns of its own row: no subqueries, no other tables, and no other generated column.

Choosing between them

Use STORED when you want to index or sort by the value, or when computing it is expensive and you read it often. Use VIRTUAL when it is cheap to compute and you would rather not pay disk space. For an index on a derived value, you can also index an expression directly (lesson 12).

8. Normalisation in one example

Normalising means arranging tables so each fact is stored once, which keeps updates from contradicting each other. You do not need the theory; you need to recognise three smells. Start with a table that stores orders the way a spreadsheet would:

  1. First normal form (1NF): one value per cell. product_skus packs a list into one column, so you cannot count, join or constrain it. Move the list to rows: a table order_items (order_id, line_no, sku, ...) with a composite primary key. That is what the shop has.
  2. Second normal form (2NF): every non-key column depends on the whole key. In order_items, if you also stored product_name, it would depend only on the product, not on the (order, line) pair. Rename a product and old rows disagree. Move it to products.
  3. Third normal form (3NF): non-key columns depend on the key and on nothing else. customer_name depends on the customer, not on the order, and city_zip depends on customer_city, not on the order. Both belong in their own tables (customers, cities), referenced by a foreign key.

The shop is built this way: orders holds a customer_id, not a name and an email. The rule of thumb for “which table does this column belong to?” is: what does this value describe? Put it with that thing.

Deliberate duplication is allowed

order_items.unit_price copies a price that also lives in products.price. That is correct: the price on an order must stay as it was on the day of the order, even if the product's price later changes. A copy that records history is not a normalisation error. A copy that is supposed to stay equal is. Likewise orders.total duplicates a sum of its items for speed; if you keep such a total, keep it correct in one place (a trigger, lesson 19, or a single write path) and document it.

Summary

  • A primary key is unique plus not null; unique constraints allow several NULLs unless you say NULLS NOT DISTINCT.
  • Foreign key actions decide what a parent delete or update does: NO ACTION and RESTRICT refuse, CASCADE follows, SET NULL and SET DEFAULT detach. Index the child column yourself.
  • A check fails only on false, so add NOT NULL when the value is required. Use NOT VALID then VALIDATE on big tables.
  • Exclusion constraints forbid overlaps and need no race-prone application check; btree_gist lets them combine = and &&.
  • DEFERRABLE constraints let a transaction pass through invalid states: swaps, cycles, delete-and-reinsert.
  • Prefer GENERATED ... AS IDENTITY to serial; expect gaps. Generated columns are VIRTUAL by default in PostgreSQL 18, and only STORED ones can be indexed.
  • Store each fact once, with the thing it describes. Copy a value only when the copy is a snapshot (a price on an order).
