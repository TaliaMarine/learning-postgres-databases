Lesson 10 · Part 2

JSONB and arrays

lesson 10Docker exerciseslive playground

Some data does not fit neatly into columns: product attributes that differ per category, a list of tags, an event payload that changes every month. PostgreSQL stores such data in jsonb and in arrays, and lets you query, change and index both. This lesson shows how to use them without giving up the things a plain column gives you for free: types, constraints and cheap filtering.

Learning goals

  • Decide whether a value belongs in a column, in a jsonb document or in an array.
  • Explain how jsonb differs from json, and read values with ->, ->>, #> and #>> without type surprises.
  • Filter with containment (@>), key tests (?) and jsonpath (jsonb_path_exists, @?).
  • Change a document with ||, - and jsonb_set, and know what that costs.
  • Choose between a GIN index, a B-tree on an expression and a generated column for a field you filter on.
  • Use arrays correctly: 1-based subscripts, ANY, @>, &&, unnest, array_agg, and the NULL traps.

1. jsonb, json, and when a column is better

JSON is a text format for nested data: objects ({"key": value}), arrays, strings, numbers, booleans and null. PostgreSQL has two types for it. json stores the exact text you sent. jsonb stores it parsed, in a binary form. The difference shows as soon as you read the value back:

playground real PostgreSQL 18 in your browser · seeded with a small shop

json keeps your spaces, your key order and the duplicate key a. jsonb removes the extra spaces, sorts keys (shorter keys first, then by bytes), and keeps only the last value of a duplicate key, giving {"a": 3, "b": 1}. Because jsonb is already parsed, it is faster to query, supports indexes and has all the operators in this lesson. Use json only when you must preserve the original text byte for byte (an audit copy of a webhook body, for example). For everything else, use jsonb.

The rule of thumb

A jsonb column is not a way to avoid designing a table. It is the right place for data that is flexible and rarely queried by itself. It is the wrong place for anything you filter on constantly, join on, or want the database to guarantee.

You need to…A column gives youA key inside jsonb gives you
Reject bad valuesA type, NOT NULL, CHECK, UNIQUENothing, unless you write a CHECK on the expression
Point a foreign key at itA real foreign keyNot possible
Filter fast on itA plain B-tree index and accurate statisticsAn expression index or a GIN index; weaker statistics
Add a new attribute per product typeAn ALTER TABLE for everybodyJust write the key
Update one attributeRewrites the rowRewrites the row and the whole document

In the shop, products.attrs and customers.profile are the flexible part: a colour, a weight, a locale. price, stock and category_id are columns, because the course filters, sums and joins on them.

Cast after extracting. If a single document has a non-number in that key, the cast fails for the whole query; the safest filter is a jsonpath comparison (section 4), which compares JSON numbers as numbers.

Two kinds of null

A JSON null is a value; SQL NULL means "nothing here". '{"a": null}'::jsonb -> 'a' returns the JSON value null, which is not SQL NULL (IS NULL is false), while ->> 'a' returns SQL NULL. jsonb_typeof(doc -> 'a') tells them apart: it returns 'null' for the JSON value and SQL NULL for a missing key.

3. Containment and key tests

Containment asks "does this document contain that smaller document?". It is written @> ("contains"); its mirror is <@ ("is contained by"). The right-hand side is the shape you are looking for:

Containment is recursive and understands arrays: an array contains another array if it holds all its elements, in any order. An array does not contain a bare scalar, which surprises people:

Three more operators test only for the presence of keys (top level only, and for string elements of an array):

  • doc ? 'key': the key exists.
  • doc ?| array['a','b']: at least one of these keys exists.
  • doc ?& array['a','b']: all of these keys exist.

The question mark is also used for parameters by some database drivers. If yours rejects ?, use the function forms jsonb_exists(doc, 'key'), jsonb_exists_any and jsonb_exists_all.

4. jsonpath: a small query language for documents

A jsonpath is an expression in its own mini-language ($ is the document, .key a field, [*] every array element, ? (…) a filter where @ is the current item). It lets you compare JSON numbers as numbers and reach into arrays of objects, which @> cannot do.

jsonb_path_exists(doc, path) or doc @? pathDoes the path match anything? Good in WHERE.

doc @@ predicateEvaluate a true/false predicate such as $.weight_g > 1000.

5. Taking a document apart

To treat a document as rows, use the set-returning functions. jsonb_each(doc) returns one row per top-level key with columns key and value; jsonb_each_text returns the value as text; jsonb_object_keys(doc) returns only the keys; jsonb_array_elements(doc) does the same for an array. A set-returning function is a function that produces a table instead of a single value, so it goes in FROM.

jsonb_object_keys is the quickest way to learn what a column really contains. It is also how you discover that a "schemaless" column has a schema after all; the Inspect it section uses it.

6. Changing a document

A jsonb value is immutable: every "change" builds a new document, which you assign back with UPDATE.

ExpressionResult
doc || '{"k": v}'Merge: keys on the right replace or add to the left (top level only).
doc - 'key'Remove a top-level key (- 'a'), or several (- array['a','b']).
doc #- '{a,b}'Remove the value at a path.
jsonb_set(doc, '{a,b}', new_value)Replace the value at a path. The new value must itself be jsonb, so a string needs quotes: '"pink"'.

jsonb_set does not create missing parents

jsonb_set(attrs, '{dims,w}', '10') returns the document unchanged when dims does not exist yet: no error, no change. Create the parent first: jsonb_set(attrs, '{dims}', '{"w": 10}'). Also, jsonb_set with a SQL NULL as the new value returns SQL NULL for the whole document, wiping it. Guard with coalesce, or use jsonb_set_lax with an explicit 'delete_key' or 'use_json_null' action.

Updating one key rewrites the whole value

A jsonb value is stored as one unit. Changing a single key writes a new copy of the whole document (and of the row, as lesson 17 explains). That is fine for a small attrs; it is costly for a 100 kB document updated many times per second. Large, hot, frequently updated values belong in columns or their own table.

7. Indexing jsonb

Without an index, every jsonb filter reads the whole table. PostgreSQL offers two separate tools, and they serve different queries.

GIN for containment

A GIN index (Generalized Inverted Index) maps each key and value inside the documents to the rows that contain it, like the index at the back of a book. It answers @>, ?, ?|, ?& and @?/@@. It has two operator classes (the set of operators an index supports):

  • jsonb_ops (the default): supports @> and the key operators ?, ?|, ?&. Bigger.
  • jsonb_path_ops: supports only @> and the jsonpath operators. Smaller and faster for containment.

A GIN index on the whole column does not help ->>

A GIN index can only answer the operators it supports. With the index above in place, the query where payload ->> 'path' = '/cart' and (payload ->> 'ms')::int = 1000 still ran a Parallel Seq Scan on the same 1 000 000-row table, because ->> is not an indexable operator for it. 8. Promote a field you filter on: generated columns

When a key becomes important, make it a real column but keep the document as the single source of truth. A generated column is a column whose value PostgreSQL computes from other columns of the same row. The message is column "path" can only be updated to DEFAULT. Change the payload and the column follows.

A bad value breaks the ALTER, or the INSERT

A generated column that casts ((attrs ->> 'weight_g')::int) fails for any row where the key holds something that is not a number, such as "abc": the error is invalid input syntax for type integer: "abc". When you add the column to an existing table, the ALTER TABLE fails and nothing changes; later, the offending INSERT fails. That is the point, since it is the check the document alone could not give you, but find and fix the bad rows first. Adding a stored generated column also rewrites the table, which takes a lock; see lesson 16.

9. Arrays

An array column holds an ordered list of values of one type, for example text[]. shop.products.tags is one. A literal is written '{sale,popular}' or array['sale','popular']. Four rules explain most array bugs:

  1. Subscripts start at 1, not 0. tags[1] is the first element.
  2. Out-of-range subscripts return NULL, not an error. tags[0] is always NULL.
  3. array_length(a, 1) is NULL for an empty array, while cardinality(a) is 0. cardinality counts all elements of all dimensions; array_length takes a dimension number.
  4. An array can have NULL elements, and they behave as in section 11.
playground real PostgreSQL 18 in your browser · seeded with a small shop

The rows with an empty array show array_length as NULL and cardinality as 0. Use cardinality unless you need a specific dimension.

To change an array, assign a new one. Use the functions rather than string tricks:

tags || 'x' needs a type hint

tags || 'extra' fails with malformed array literal: "extra", because PostgreSQL reads the unknown-typed string as an array literal. Write tags || 'extra'::text, array_append(tags, 'extra') or tags || array['extra'].

11. The NULL traps in arrays

An array may contain NULL elements. Equality of whole arrays treats two NULL elements as equal, but comparing a value to the elements follows ordinary SQL three-valued logic: the result is true, false or unknown (NULL).

playground real PostgreSQL 18 in your browser · seeded with a small shop

found is true. not_found is NULL, not false, because "is 'z' equal to the unknown element?" cannot be answered. For the same reason not_in_list is NULL, so WHERE x <> ALL (list_with_a_null) returns no rows at all. It is the same trap as NOT IN (subquery_with_a_null). Keep arrays free of NULLs (array_remove(a, NULL) does that), or declare a CHECK (array_position(tags, NULL) IS NULL) on the column.

An array column cannot have a foreign key to its elements

If the tags must be rows in a tags table, each product-to-tag link is a row in a join table with two foreign keys, not an array. Arrays suit small lists of simple values that you read and write together with the row: tags, phone numbers, a list of allowed roles. They do not suit anything you would join, count per element in a large table, or update one element at a time.

Summary

  • Use jsonb, not json, unless you need the original text. Columns win for anything you filter, join, constrain or update often.
  • -> returns jsonb, ->> returns text: cast after extracting, or compare numbers with jsonpath. Missing keys give NULL; a JSON null is a value.
  • @> tests containment, ? tests keys, and jsonpath (jsonb_path_exists, @?) reaches into nested arrays.
  • Changing a document builds a new one: ||, -, jsonb_set. It rewrites the whole value, and jsonb_set does not create missing parents.
  • A GIN index (jsonb_path_ops for containment only) serves @> but not ->>; a stored generated column plus a B-tree serves one hot field.
  • Arrays are 1-based, out-of-range reads are NULL, cardinality beats array_length on empty arrays, and NULL elements make = ANY and <> ALL return unknown.
