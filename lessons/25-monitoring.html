Lesson 25 · Part 6

Monitoring and diagnostics

lesson 25Docker exerciseslive playground

When someone says "the database is slow", PostgreSQL can usually tell you why, if you know where to look. This lesson covers the statistics views that describe what the server is doing right now and what it has done since the last reset: sessions, databases, statements, tables and locks. It covers the server log as well, and ends with a short checklist you can follow under pressure.

Learning goals

  • Read pg_stat_activity: process types, session states, wait events, and long or idle-in-transaction sessions.
  • Read the per-database counters in pg_stat_database: commits, rollbacks, cache hits, deadlocks and temporary files.
  • Find the statements that cost the most with pg_stat_statements, using its PostgreSQL 18 column names.
  • Spot tables that are scanned sequentially or need vacuum with pg_stat_user_tables.
  • Find who is blocking whom with pg_locks and pg_blocking_pids().
  • Use the server log (log_min_duration_statement, log_lock_waits) and a checklist for "the database is slow".

1. pg_stat_activity: what is happening now

pg_stat_activity has one row per server process. Client connections are rows with backend_type = 'client backend'. The other rows are the server's own helpers: the checkpointer, the background writer, the WAL writer, the autovacuum launcher and, new in PostgreSQL 18, io worker processes that perform asynchronous reads.

playground every process, and what each is doing

The browser returns one row, standalone backend, because it has no separate processes. The Docker database returns nine:

States

stateMeaningWorry when
activeRunning a statement right nowMany are active for a long time, or there are more active sessions than CPU cores
idleConnected, waiting for the client to send somethingHundreds of them: each holds memory and a connection slot (lesson 26)
idle in transactionInside BEGIN, but not running anythingAlways, if it lasts: it holds locks, and its snapshot stops vacuum from removing dead rows
idle in transaction (aborted)A statement in the transaction failed; the client has not rolled backAlways: an application bug

Wait events

When a session is not using the CPU, wait_event_type and wait_event say what it is waiting for. Lock means it waits for a lock another session holds. IO means a disk read or write. LWLock means a short internal lock, and many of them can point at contention inside the server. Client means it waits for the application, as with ClientRead on an idle session. Activity is the normal resting state of a background process. An active session with wait_event null is running on the CPU.

On an idle course container this returns no rows. On a busy server, the first rows are the ones to look at. query is the session's current statement, or its last one if it is idle.

Cancel first, terminate second

select pg_cancel_backend(pid) stops the session's current statement and leaves the connection open. select pg_terminate_backend(pid) closes the connection, and rolls back its open transaction. Try the first before the second, and be sure of the pid: a wrong one may kill a session the business needs.

Let the server end forgotten transactions

idle_in_transaction_session_timeout ends sessions that stay idle inside a transaction for too long. It is 0 (off) in the course container. Set it per role or per database (lesson 21), for example alter role app set idle_in_transaction_session_timeout = '5min'.

2. pg_stat_database: one row of counters per database

pg_stat_database holds counters that only grow, from the last statistics reset (stats_reset) or server start. A single value tells you little. Read it twice, a minute apart, and subtract to get rates.

A blks_read is not necessarily a disk read: the operating system's page cache may answer it. With track_io_timing = on (set in the course container) the columns blk_read_time and blk_write_time say how long those reads and writes took.

3. pg_stat_statements: which statements cost the most

pg_stat_statements is an extension that keeps counters per normalised statement, meaning the statement text with its constants replaced by $1, $2 (lesson 14 introduces it). It must be listed in shared_preload_libraries, which needs a restart, and then created in a database with CREATE EXTENSION. The course container does both.

Sort by total_exec_time to find what costs the server the most overall. A 2 ms query run a million times costs more than a 10 s report run once. Sort by mean_exec_time to find what each user waits longest for.

The column names changed in PostgreSQL 13

Older blog posts use total_time, mean_time and blk_read_time. Those columns no longer exist. In PostgreSQL 18 the view has total_exec_time, mean_exec_time, min_exec_time, max_exec_time and stddev_exec_time, a matching set of *_plan_time columns for planning, and shared_blk_read_time and shared_blk_write_time for I/O timing. It also has wal_bytes, the parallel_workers_to_launch and parallel_workers_launched counters, and stats_since, the time this statement's counters started. List them yourself with \d pg_stat_statements in psql.

To measure a change, reset the counters, run the workload, and read again: select pg_stat_statements_reset(); (it needs superuser or a grant). Do not reset on a shared server without telling the people who use these numbers.

4. pg_stat_user_tables: how each table is used

pg_stat_user_tables has one row per table, with counts of scans, row changes, dead rows and the last vacuum and analyze. It answers two questions: which tables are read by sequential scans often (a missing index?), and which tables need vacuum (lesson 17)?

In the course database, after the earlier lessons have run their examples and checks, the top row is orders with about 140,000 sequential scans that together read about 28 billion rows. Your numbers will differ, because they depend on what has run on your machine. seq_tup_read / seq_scan is the average number of rows each scan read. A large table with many sequential scans and a large average is where an index pays off first.

Statistics arrive a little late

Each session sends its counters to shared memory at most about once a second, and at the end of a transaction. A query that reads pg_stat_user_tables straight after your own statements in the same session may not see them yet. select pg_stat_force_next_flush(); makes your session send its counters at the end of the current statement. Exercise 2 uses it so that its numbers are repeatable.

5. pg_locks and pg_blocking_pids: who blocks whom

pg_locks lists every lock held or wanted, one row per lock. granted = false means the session is waiting for it. Here is what one UPDATE holds while its transaction is open:

The browser and the Docker database return the same six rows. The table and both of its indexes are locked in RowExclusiveLock mode, which only conflicts with schema changes. The transaction also holds its own transaction id (transactionid) and a virtualxid, plus an AccessShareLock on pg_locks taken by the query itself. The row lock on product 1 is not in the list: row locks are stored in the row, and appear in pg_locks only when someone waits for one.

6. The server log

The views show the present and the totals. The log shows individual events with timestamps, which is what you need to explain yesterday's slow period. The settings that matter most:

SettingEffectIn the course container
log_min_duration_statementLogs every statement that runs longer than this, with its duration500ms, set in docker-compose.yml
log_lock_waitsLogs sessions that wait longer than deadlock_timeout for a lockon, set in docker-compose.yml
log_temp_filesLogs temporary files larger than this size (0 logs all)off (-1)
log_autovacuum_min_durationLogs autovacuum runs that take longer than thisthe default, 10min
log_line_prefixWhat starts every log line (time, pid, user, database, application)the default, %m [%p]

Because log_min_duration_statement is 500 ms in the course container, any statement you run that takes longer appears in ./pg logs. Try select pg_sleep(0.7); and look: LOG: duration: 704.207 ms statement: select pg_sleep(0.7).

Logging every statement is a load of its own

log_min_duration_statement = 0 or log_statement = 'all' writes every statement to the log. On a busy server that is a lot of disk I/O, and the log may then contain personal data from the query text. Use a threshold that catches the slow minority, and use pg_stat_statements for the totals.

7. A checklist for "the database is slow"

Work from the outside in. Each step takes a minute and either finds the cause or rules it out:

  1. Is it the database? Compare the application's timing for a slow request with the statements it ran. If the database part is small, look elsewhere: the network, the pool, the application.
  2. Sessions: count pg_stat_activity by state. Too many active sessions? Connections near max_connections? Long idle in transaction?
  3. Waits: group active sessions by wait_event_type, wait_event. Mostly Lock: find the blocker with pg_blocking_pids. Mostly IO: the working set does not fit in memory, or a big scan is running. No wait: CPU-bound queries.
  4. Statements: top pg_stat_statements by total_exec_time, then by mean_exec_time. Did a new statement appear at the top since the last deploy? Run EXPLAIN (ANALYZE, BUFFERS) on it (lesson 13).
  5. Tables: pg_stat_user_tables for big tables with many sequential scans, many dead rows, or an autovacuum that has not run for a long time.
  6. The server: temp_bytes growing, a falling cache hit ratio, checkpoints more often than checkpoint_timeout (lesson 22), a replica far behind, or a disk filling with WAL from an abandoned replication slot.
  7. The log: what does it show around the time it started? Slow statements, lock waits, errors, a restart?
Keep history

Every view in this lesson shows the present or a running total. To answer "what changed since Tuesday?" you need the numbers from Tuesday. A monitoring system that samples these views every few seconds and keeps the history is what turns this checklist into a five-minute job. Examples are Prometheus with postgres_exporter, pganalyze, or your cloud provider's database insights.

Summary

  • pg_stat_activity shows every process now: its type, its state, what it waits for, and its current or last query.
  • idle in transaction sessions hold locks and stop vacuum; find them, and set a timeout.
  • pg_stat_database and pg_stat_user_tables are running totals; compare two readings to get rates.
  • pg_stat_statements ranks normalised statements; in PostgreSQL 18 the time columns are total_exec_time, mean_exec_time and friends.
  • pg_blocking_pids() names the blocker of a waiting session; log_lock_waits records waits in the log.
  • The course container logs statements slower than 500 ms. Follow the checklist from the outside in.
