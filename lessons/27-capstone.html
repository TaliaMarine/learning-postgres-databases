Lesson 27 · Part 7

Capstone project

lesson 27Docker exercises

This is the last lesson, and it has one job: build a small service database from a blank scratch database, using what you learned in the other lessons. You will create roles and a locked-down schema, load data and add the one index its busiest query needs, then take a backup, restore it somewhere else, and prove the copy is identical. It is longer than the other lessons on purpose. There is little new here to read, and a lot to do.

Learning goals

  • Lay out a service database with an owner role, an application role and a read-only role, and give each only the privileges it needs.
  • Design tables with keys, foreign keys and check constraints that reject bad data.
  • Load test data in bulk with generate_series, and index for one real query with a partial index.
  • Read an EXPLAIN plan to confirm the index is used and no sort remains.
  • Take a pg_dump backup, restore it into a blank database, and compare row counts and fingerprints.
  • Run a check that proves your work, and clean up everything you created.

Set up for this lesson

The service is a tiny support-desk database: agents who work on tickets. You build it in a new database named lab_27_service, never in shop. Roles and databases are cluster-wide, so every name carries the lab_27_ prefix and the checker removes them all when it is done. The three parts are independent: each file begins from a blank state. Part 1 creates everything, and parts 2 and 3 give you a short setup block to paste so they do not depend on the previous part. Start the container with ./pg up.

The browser playground cannot create databases or roles that outlive the page, and it has no pg_dump, so this lesson has no playground. Everything runs in Docker. Because the files contain several steps, run them with ./pg run to see every statement's output, or open them in ./pg psql and paste one step at a time.

1. The design

The service has three kinds of user, which map to three roles:

RoleCan log in?PurposePrivileges
lab_27_ownernoOwns the database, the schema and every table. Migrations run as this role.Everything, on its own objects
lab_27_appyesThe application's own connectionSELECT, INSERT, UPDATE, DELETE on the two tables; no CREATE, no DROP
lab_27_readeryesReports and dashboardsSELECT only

Separating the owner from the application is the layout from lesson 5. If the application connects as the owner, one SQL injection can drop your tables. If it connects as lab_27_app, the worst it can do is what the application could do anyway.

2. Part 1: roles, database and schema

Work in this order, because each step needs the previous one. Roles come first (they are cluster-wide). The database comes next. CREATE DATABASE cannot run inside a transaction block, so give it its own statement. Then connect to the new database, and create the schema and tables as the owner, so the owner owns them. Finally grant.

  1. Roles: create role lab_27_owner nologin; and two login roles with a password. The password lab-only is for the local container only.
  2. Database: create database lab_27_service owner lab_27_owner template template0; (template0 is always blank). A new database lets PUBLIC connect to it, so revoke connect on database … from public, then grant connect back to the two login roles (lesson 4).
  3. Switch: \c lab_27_service in psql. This works in a file run by ./pg run too.
  4. Objects as the owner: set role lab_27_owner; then create schema tickets; and the two tables. reset role; afterwards. Objects are owned by whoever creates them, which is why you switch first (lesson 2).
  5. Grants: usage on the schema, then table privileges, to each login role. Tables with an identity column need no separate sequence grant: the INSERT privilege is enough.
Why not just create everything as postgres?

Then postgres owns the schema and the tables, and the owner role owns nothing. The next time someone runs a migration as lab_27_owner it fails with must be owner of table. Decide who owns what before you create anything, because changing it later means ALTER … OWNER TO on every object.

Check as you go

After the grants, test from the outside. ./pg psql-as lab_27_reader lab_27_service opens a session as the reader (it works because the container trusts local connections). Try select count(*) from tickets.tickets; and then an update, and read the error. \dp tickets.* shows the access privileges you set.

3. Part 2: data and the index the busy query needs

A support screen shows an agent the ten newest open tickets assigned to them. It runs this query all day:

Load 20,000 tickets in one statement with generate_series (lesson 9), so that the table is big enough for the planner to care. In the data recipe, one ticket in 47 is open and the rest are closed, which is how a support desk looks: a long history and a short list of live work. Without an index the planner reads the whole table, and sorts what it found:

It reads 20,000 rows to keep 85. A partial index (lesson 12) fits this shape well: the WHERE status = 'open' condition is in the index definition, so only the 425 open tickets are stored, and the key columns are in the order the query needs them: first the one it compares (agent_id), then the one it sorts by (created_at desc). The index then returns the rows already sorted:

No Seq Scan, no Sort, and 12 buffers instead of 167. The index file is 32 kB, against 456 kB for the table's primary key, because it holds only the open tickets. Exercise 2 asks you to build exactly this. Finish by running ANALYZE so that the planner's statistics reflect the loaded data (lesson 13).

Why not index status too?

status has only two values, so an ordinary index on it is nearly useless. The partial index answers the question "which tickets are open?" without storing the 19,000 that are not. The rule to remember: a partial index is smallest when the condition matches a small share of the rows.

4. Part 3: a backup you have proved

A backup is real only after a restore (lesson 23). You will take a custom-format dump of the service database, restore it into a second, blank database, and then compare the two. What this restore does not prove

It proves that this dump restores into an empty database on the same server, with the same roles available. It does not prove that the roles exist on a new machine (you need pg_dumpall --globals-only for that), that your WAL archive is complete, or how long a restore of production data takes. The habit matters more than this one test.

Inspect it

When your part 1 is done, this query summarises the layout, using the catalogs you met in lessons 2 to 4:

relacl lists each grantee as role=privileges/grantor. The letters are a = INSERT, r = SELECT, w = UPDATE, d = DELETE. With the solution, lab_27_app=arwd/lab_27_owner and lab_27_reader=r/lab_27_owner. The owner holds arwdDxtm, every table privilege.

Two quick tests as the application role show the layout working. An attempt to change the table's structure fails with ERROR: must be owner of table agents, and the reader's update fails with ERROR: permission denied for table tickets.

Summary

  • A service database has an owner role that creates objects, an application role with data privileges only, and a read-only role. Take CONNECT away from PUBLIC.
  • Constraints in the table protect the data from every program that writes to it.
  • Bulk-load with generate_series, then build the smallest index that serves the hot query: a partial index whose key matches the filter and the sort.
  • Confirm an index with EXPLAIN: an index scan, no Sort, and fewer buffers.
  • A backup is proved by restoring it into a blank database and comparing counts and fingerprints.
  • Drop every scratch database and role you create. Everything named lab_* is fair game for the checker.
