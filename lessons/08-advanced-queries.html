Lesson 08 · Part 2

Advanced queries

lesson 08Docker exerciseslive playground

You already write joins and GROUP BY. This lesson adds the tools that turn a pile of queries and application loops into one statement: named subqueries (CTEs), window functions, the LATERAL join, FILTER, subtotals with ROLLUP, recursive queries for trees, set operations and DISTINCT ON. For each one you will see what it does, what it costs and the mistake it invites.

Learning goals

  • Write a CTE and say whether PostgreSQL runs it once or folds it into the outer query (MATERIALIZED / NOT MATERIALIZED).
  • Use window functions (row_number, rank, lag, running sums) and explain what a frame is.
  • Use LATERAL to get the top N rows per group.
  • Count several things in one pass with FILTER, and produce subtotals with GROUPING SETS, ROLLUP and CUBE.
  • Walk a tree with a recursive CTE, with a depth column and protection against cycles.
  • Choose between UNION and UNION ALL, and use INTERSECT, EXCEPT and DISTINCT ON correctly.

Set up for this lesson

Use the shop database (./pg psql). Every query here only reads, so nothing needs cleaning up. The playgrounds in this page use the small in-browser copy of the shop (8 customers, 12 orders), so their rows differ from the ones you get in Docker (20 000 customers, 200 000 orders). Where this page quotes output, it says which of the two it came from.

1. CTEs: naming a subquery

A CTE (common table expression) is a named subquery written with WITH before the main query. It makes long queries readable: each step gets a name and you read top to bottom.

playground real PostgreSQL 18 in your browser · seeded with a small shop

In the playground this returns 1 paid order with an average total of 24.95. In the Docker shop the same query finds 8 111 paid orders (average 788.53).

Is the CTE run once, or folded into the query?

Older PostgreSQL versions always ran a CTE first and stored its result (an optimisation fence: the planner could not look through it). Since PostgreSQL 12 the rule is:

  • A CTE that is read once and has no side effects is inlined: it is treated like a plain subquery, so conditions from the outer query can be pushed into it.
  • A CTE that is read more than once, or is recursive, or contains INSERT/UPDATE/DELETE, is materialized: computed once and stored.
  • You can force either choice with AS MATERIALIZED or AS NOT MATERIALIZED.

The plans below come from the Docker shop (the playground is too small to show realistic plans):

In the second plan every paid order is produced and stored before the customer_id = 42 filter is applied. That is only good when the CTE is expensive and you really read it several times.

A CTE read twice is computed once, and cannot use your index

When you join a CTE to itself, PostgreSQL materializes it. The outer filter (where customer_id = 42) is then applied to the stored result, one row at a time. The aggregate over all 200 000 orders is built in full first. If you only need one customer, put the filter inside the CTE, or write the query without a CTE.

Data-modifying CTEs

A CTE may contain INSERT ... RETURNING, UPDATE ... RETURNING or DELETE ... RETURNING, and the main query can read what it returned. Lesson 9 uses this. Such a CTE always runs exactly once, whether or not the main query reads it.

2. Window functions

GROUP BY collapses rows. A window function does a calculation across a set of related rows but keeps every row. You write it as function(...) OVER (...). Inside OVER:

  • PARTITION BY splits the rows into independent groups (like GROUP BY, but nothing is collapsed).
  • ORDER BY orders the rows inside each partition.
  • A frame says which rows around the current row the function may see (more below).
playground numbering, running total and previous value per customer

Customer 1 has three orders in the playground, with totals 99.89, 189.00 and 104.45, so the running total goes 99.89, 288.89, 393.34 and previous_total is NULL on the first row. The line window w as (...) is a named window: you define it once and use it in several functions with over w.

Ranking: row_number, rank, dense_rank

The three differ only when there are ties:

playground two products with the same price
FunctionTiesResult for prices 4.00, 4.00, 3.50, 1.00
row_number()Never ties; breaks them arbitrarily unless you add a tiebreaker1, 2, 3, 4
rank()Ties share a rank; the next rank skips1, 1, 3, 4
dense_rank()Ties share a rank; no gaps1, 1, 2, 3

Frames: which rows the function sees

Aggregates such as sum used as window functions work on a frame. With an ORDER BY and no explicit frame the default is RANGE BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW. RANGE treats rows with equal sort values as one unit (peers). ROWS counts physical rows. This matters when the sort column has duplicates:

playground RANGE (the default) versus ROWS

The two rows with v = 2 both show default_frame = 5 (1 + 2 + 2: both peers are included), while rows_frame shows 3 and then 5. For a running total, you almost always want ROWS, or an ORDER BY that is unique. A moving average over the last three rows is avg(x) over (order by id rows between 2 preceding and current row).

You cannot filter on a window function in WHERE

WHERE runs before windows are computed, so this fails (an intentional error, shown as an example):

select id, total from shop.orders where row_number() over (order by total) = 1;
ERROR: window functions are not allowed in WHERE

Compute the window in a subquery or CTE, then filter in the outer query: with ranked as (select ..., row_number() over (...) as rn from ...) select ... from ranked where rn = 1.

What it costs

A window with PARTITION BY and ORDER BY needs its input sorted by those columns. In the Docker shop, row_number() over (partition by customer_id order by ordered_at, id) over all orders plans as WindowAgg on top of a Sort of the whole table. An index on (customer_id, ordered_at, id) could remove that sort (lesson 12).

3. LATERAL: a subquery that sees the row before it

Normally a subquery in FROM cannot refer to other tables in the same FROM. LATERAL lifts that rule: the subquery runs once for each row of the tables to its left and can use their columns. The classic use is top N per group: the two latest orders of each customer.

playground the two most recent orders of every customer

cross join lateral drops customers with no orders (Finn Smit has none in the playground). Use left join lateral (...) o on true to keep them, with NULL in the order columns.

The window-function alternative is to number orders per customer and keep rn <= 2. Both are correct. LATERAL ... LIMIT is usually faster when you want a few rows from a large table and have an index on (customer_id, ordered_at), because each customer's lookup stops after two rows. The window version has to number every order first.

Without the index, LATERAL does a scan per customer

shop.orders has no index on customer_id in the Docker shop. For three customers the plan is a Seq Scan on orders repeated three times (a nested loop with a sort and a limit inside). For all 20 000 customers that is 20 000 scans of 200 000 rows, and it is very slow. Try it on a handful of customers first (where c.id <= 3) and add the index before you run it for everyone.

4. FILTER, GROUPING SETS and ROLLUP

FILTER: several conditional aggregates in one pass

aggregate(...) FILTER (WHERE condition) makes one aggregate count only the rows that match. It replaces the older sum(case when ... then 1 else 0 end) and reads better.

This output is from the Docker shop. avg(total) FILTER (WHERE status = 'delivered') averages only the delivered orders and leaves the other aggregates in the same query untouched. That is the point: one scan of the table feeds all four numbers.

GROUPING SETS, ROLLUP and CUBE

A report often needs several groupings at once: per country and status, per country, and a grand total. GROUPING SETS lists the groupings you want, and PostgreSQL computes all of them in one statement. Two shorthands:

  • ROLLUP (a, b) = the sets (a, b), (a) and (): subtotals that roll up from right to left.
  • CUBE (a, b) = every combination: (a, b), (a), (b) and ().

In the subtotal rows the grouped column is NULL. That is ambiguous if the data itself can contain NULL, so use grouping(col, ...): it returns a bit mask where a bit is 1 when that column is not part of the current grouping (that is, a subtotal row).

playground ROLLUP with a FILTER count and grouping()

The last row is the grand total: 12 orders, 4 of them over 100, with g = 3 (binary 11: both columns are rolled up). Rows with g = 1 are per-country subtotals (status rolled up), and rows with g = 0 are the detail rows. Sorting by grouping(...) first puts details before subtotals before the total.

Subtotals versus UNION ALL

You could write one query per grouping and glue them with UNION ALL, but that scans the table once per grouping. GROUPING SETS does it in one statement and the planner can often share the work.

5. Recursive CTEs: walking a tree

shop.categories is a tree: parent_id points to another row of the same table, and the top-level categories have parent_id is null. A recursive CTE walks such a tree. It has two parts joined by UNION ALL: the anchor (where to start) and the recursive step, which reads the rows produced so far and adds the next level. It stops when a step produces no new rows.

playground the category tree with depth and path

Ordering by the text path makes children appear under their parent. The Docker shop has 13 categories: four top-level ones (Books, Electronics, Home, Outdoor) and nine children. The playground has fewer.

Cycles

If the data contains a loop (A is the parent of B, B of A), a recursive step never runs out of new rows and the query runs until it exhausts memory or disk. Since PostgreSQL 14 you can ask PostgreSQL to detect loops with a CYCLE clause. Here is a loop on purpose (1, 2, 3, then 1 again), stopped by cycle n set looped using path:

playground a query that would never end, stopped by CYCLE

The result is 1, 2, 3 and then 1 again with looped = true; PostgreSQL stops following a row once it sees a value it has already visited on that path. PostgreSQL 14 also added a SEARCH DEPTH FIRST BY name SET ord (or BREADTH FIRST) clause that builds a sort key for you, as an alternative to the hand-made path column above.

An endless recursion is your job to prevent

Without CYCLE or a depth limit (where t.depth < 10 in the recursive step), a loop in the data hangs the query. A foreign key does not prevent a loop in a parent-child table. Always add one of the two guards when the data comes from users.

6. Set operations

Set operations combine the rows of two queries that have the same number of columns, with compatible types:

OperatorResultDuplicates
UNIONRows in either queryRemoved (needs a sort or hash of everything)
UNION ALLRows in either queryKept (just appends; cheap)
INTERSECTRows in bothRemoved (INTERSECT ALL keeps them)
EXCEPTRows in the first and not in the secondRemoved (EXCEPT ALL keeps them)
playground every country that appears anywhere in the shop

Change union to union all and count the rows: you get 20 rows (8 customers + 12 orders) instead of 5. In the Docker shop union all over the same two columns returns 220 000 rows and union returns 9. Try except in the other direction too: in Docker, select country from shop.customers except select shipping_country from shop.orders returns no rows, because every customer country is also a shipping country.

Use UNION ALL unless you need the de-duplication

UNION pays for removing duplicates even if there are none. If the two queries cannot overlap, or you do not mind duplicates, write UNION ALL. The columns are matched by position, not by name: swapping two columns in one query gives wrong results or a type error, not an error about names. A different number of columns fails with each UNION query must have the same number of columns.

7. DISTINCT ON: one row per group, PostgreSQL style

SELECT DISTINCT ON (a) keeps only the first row for each value of a. "First" is decided by your ORDER BY. It is a short way to say "the latest row per customer":

playground the latest order of every customer
The ORDER BY must start with the DISTINCT ON columns

PostgreSQL refuses to guess which row you mean unless the leading ORDER BY columns match the DISTINCT ON list: select distinct on (customer_id) ... order by ordered_at desc fails with SELECT DISTINCT ON expressions must match initial ORDER BY expressions. Always end the ORDER BY with a unique column such as id, otherwise ties make the result non-deterministic. DISTINCT ON is PostgreSQL-only; the portable form is the row_number() ... where rn = 1 pattern from section 2.

Summary

  • A CTE read once is inlined like a subquery; read twice, recursive or data-modifying, it is materialized. MATERIALIZED / NOT MATERIALIZED override that.
  • Window functions keep every row. PARTITION BY groups, ORDER BY orders, and the frame decides which rows an aggregate sees. Use ROWS for running totals.
  • You cannot use a window function in WHERE; compute it in a subquery or CTE and filter outside.
  • LATERAL runs a subquery per row to its left: the tool for top N per group. Index the lookup column.
  • FILTER gives conditional aggregates; ROLLUP, CUBE and GROUPING SETS give subtotals, and grouping() tells subtotal rows from real NULLs.
  • Recursive CTEs walk trees; guard them with CYCLE or a depth limit.
  • Prefer UNION ALL. DISTINCT ON needs an ORDER BY that starts with its columns and ends with a unique one.
