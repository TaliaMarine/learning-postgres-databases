Lesson 26 · Part 6

Connections, pooling, extensions and upgrades

lesson 26Docker exerciseslive playground

Every PostgreSQL connection is a whole operating-system process, so a thousand idle application connections are a real cost. This lesson explains that cost, what a connection pooler such as pgbouncer does about it and what it breaks, how extensions add features to a database, and how you move to a new PostgreSQL version without losing data. The course image runs PostgreSQL 18.6.

Learning goals

  • Explain why a PostgreSQL connection is expensive and what max_connections limits.
  • Describe transaction pooling with pgbouncer, and name what breaks with it: session state, prepared statements and advisory locks.
  • Install, list and update extensions with CREATE EXTENSION and pg_available_extensions.
  • Tell a minor update from a major upgrade, and say what each one involves.
  • Compare the major-upgrade methods: pg_upgrade, dump and restore, and logical replication.
  • Make a pre-upgrade checklist from the server's own catalogs.

Set up for this lesson

Use the shop database for read-only queries and a scratch copy for anything that installs or changes objects. The course container does not include pgbouncer, so that part is explained and shown as configuration, not run. Extension commands do run, in the scratch database:

The browser playground is a single process with one session and only the plpgsql extension, so the pooling and extension examples there show the idea, not real server behaviour.

1. Why connections are expensive

PostgreSQL starts a new backend process for every client connection (lesson 1). Making the connection costs a TCP handshake, authentication and a process start, and with TLS a key exchange too. In a test inside the course container, a new local connection plus select 1 took about 1.8 ms on average, while a statement on an already-open connection took 0.035 ms: roughly 50 times longer. That is on a fast loop-back network. Across a real network, the gap is larger.

An open connection also costs memory (each backend has its own caches, and its work_mem allowances while it runs queries) and a slot in shared structures such as the lock table and the snapshot list. An idle connection uses little CPU. A connection that is active uses a CPU core while it runs, so having far more active sessions than cores only adds scheduling overhead: throughput stops growing and latency does not.

max_connections

max_connections is the number of client connections the server accepts. It is fixed when the server starts, so changing it needs a restart. A few slots are held back for administrators:

With 100 slots and 3 reserved for superusers, ordinary roles can use 97. Beyond that a new connection from an ordinary role fails at once with a FATAL: remaining connection slots are reserved for … error (when every slot is taken, even a superuser sees FATAL: sorry, too many clients already). reserved_connections keeps further slots for members of the built-in role pg_use_reserved_connections. Per-role and per-database limits also exist: alter role app connection limit 20 (lesson 3).

More connections is not more speed

The usual reflex when you see "too many connections" is to raise max_connections to 1000. That treats the symptom: memory grows with it, and the server gets slower because every snapshot has more sessions to look at. A common starting point for the number of active server connections is a small multiple of the CPU core count, and a pooler to queue the rest. Measure with the checklist in lesson 25.

2. Connection pooling with pgbouncer

A connection pooler is a small program between the application and PostgreSQL. The application opens many cheap connections to the pooler. The pooler keeps a small set of real connections to the server and lends one out for as long as it needs to. pgbouncer is the most widely used one for PostgreSQL. A pooler has three pool modes, which differ in how long a client keeps its server connection:

ModeServer connection is held forSharingCompatibility
sessionThe whole client connectionLow: saves connect time onlyFull
transactionOne transactionHigh: this is the mode people mean by "pooling"Breaks anything that lives in a session
statementOne statementHighestNo multi-statement transactions

The application then connects to port 6432 instead of 5432, and nothing else changes in its connection string. default_pool_size = 20 means at most 20 server connections for each database and role pair, however many clients are connected. When all 20 are busy, further transactions wait in a queue inside pgbouncer.

What breaks with transaction pooling

In transaction mode, two consecutive transactions from the same client can run on different server connections, and one server connection serves many clients in turn. Everything that PostgreSQL attaches to a session rather than a transaction stops being reliable:

FeatureWhy it breaksWhat to do
SET (not SET LOCAL), SET ROLEThe setting stays on the server connection and leaks to the next client, or is gone for your next transactionUse SET LOCAL inside a transaction, or set defaults per role (lesson 21)
Named prepared statements (PREPARE, protocol-level prepare)The statement was prepared on one server connection; your next transaction may land on another and fail with prepared statement … does not existUse a pgbouncer version that tracks protocol-level prepared statements (max_prepared_statements), or turn prepared statements off in the driver
Session-level advisory locks (pg_advisory_lock)The lock belongs to the server connection, not to your client; it can be held for the wrong client, or never released (lesson 16)Use pg_advisory_xact_lock, which ends with the transaction
Temporary tables, WITH HOLD cursorsThey live as long as the server connection, not the transactionUse ON COMMIT DROP temp tables inside one transaction
LISTEN / NOTIFY (lesson 19)You listen on one server connection and get handed anotherConnect directly to PostgreSQL for the listener
Session-level settings such as search_path set at connectNot applied to the connection you are lentSet them per role or per database

Step 1 shows 64MB, 1, 1 and 1. Step 2 shows 4MB, 0, 0 and 0. Session-mode pgbouncer sends DISCARD ALL (its server_reset_query) when a client leaves. Transaction mode does not reset between transactions, because the client is not expected to rely on session state at all. That is why you must remove that reliance from the application before you switch modes.

A pooler can hide a leak and then multiply it

An application that never closes connections, or leaves transactions open, will fill the pool just as it filled max_connections. Pooling smooths a spike. It does not repair a connection leak or a idle in transaction session (lesson 25), and a long transaction now blocks one of only 20 server connections instead of one of hundreds.

3. Extensions

An extension is a package of objects (types, functions, operators, index methods) that PostgreSQL installs into a database with one command. Many ship with the server in the contrib collection; others you install as operating-system packages first (PostGIS and pgvector are the best known). pg_available_extensions lists the extensions whose files the server can see, and pg_extension lists the ones installed in the current database:

A blank installed_version means "available, not installed in this database". The course image offers 46 extensions in all. Install one in the scratch database, use it, update it and remove it:

  • An extension is installed per database. Installing pg_trgm in shop does nothing for another database.
  • CREATE EXTENSION name SCHEMA s puts its objects in schema s. The default is the first schema of search_path, usually public.
  • ALTER EXTENSION name UPDATE moves it to the newest version the server files provide, which is how you pick up changes after a PostgreSQL minor update or a major upgrade.
  • Creating most extensions needs superuser rights. Those marked trusted (citext, pg_trgm, pgcrypto, hstore, uuid-ossp) can be created by a role that has CREATE on the database. pg_available_extension_versions has a trusted column.
  • Some extensions must also be preloaded with shared_preload_libraries and a restart. pg_stat_statements is one (lesson 25).
Extensions are a dependency like any other

A pg_dump of the database contains CREATE EXTENSION, not the extension's code, so the new server must have the extension's files installed before you restore (lesson 23). Managed services allow only the extensions on their own list. Check that every extension you use is supported on the version and the platform you are moving to.

4. Minor and major versions

Since PostgreSQL 10 a version number has two parts. The course image reports:

18 is the major version; 6 is the minor version. The two are very different events:

Minor update (18.5 → 18.6)Major upgrade (17 → 18)
What changesBug and security fixes onlyNew features, changed behaviour, possibly changed catalogs and data format
Data directorySame files and format; nothing to convertNot compatible: you must convert or copy the data
HowInstall the new binaries, restart the serverOne of the three methods in section 5
DowntimeA restart, secondsMinutes to hours, or seconds with logical replication
RiskLow; apply every one promptlyModerate: test the application first
How oftenSeveral times a yearOnce a year a new major appears; each is supported for five years

Minor releases never need a dump or any conversion. After a minor update, run ALTER EXTENSION … UPDATE for the extensions that ship with a new version, and read the release notes for anything marked as needing action (a rare index rebuild, for example). A server that is several minor versions behind is the one that gets hit by a known, already fixed bug.

Data checksums in the course image

The course container's docker-compose.yml creates the cluster with --data-checksums, and show data_checksums returns on. Checksums detect a corrupted page when it is read. For pg_upgrade, the old and the new cluster must agree about checksums. Check show data_checksums on both.

5. Major upgrades: three methods

MethodHow it worksDowntimeNotes
pg_upgradeDumps only the catalogs, then copies (or hard-links) the data files into a new clusterMinutes; seconds to minutes with --link, however large the dataBoth versions' binaries on one machine. --check does a dry run. Run ANALYZE afterwards unless statistics were carried over. --link makes the old cluster unusable once the new one has started
Dump and restorepg_dumpall --globals-only plus pg_dump -Fc from the old server, pg_restore into the new one (lesson 23)As long as the dump and restore take; proportional to data sizeSimplest and safest. Works across platforms. Fine for small databases
Logical replicationSubscribe a new-version server to the old one, wait until it has caught up, switch the application over (lesson 24)SecondsMost work to prepare: tables need a replica identity, sequences must be copied at the end, schema changes are not replicated, and large objects are not

pg_upgrade is installed in the course container, so you can read its options with ./pg exec pg_upgrade --help. The usual flow, shown as commands (do not run this against the course container, because upgrading in place would destroy the course database):

vacuumdb --analyze-in-stages --missing-stats-only analyzes only the tables that have no statistics. In the course container's 18.6 tools, vacuumdb accepts --missing-stats-only and pg_upgrade accepts --no-statistics, which shows that in 18 the upgrade can carry the old statistics along, so queries do not start with empty ones.

Never upgrade without a rehearsal

Take a backup you have restored before (lesson 23), restore it to a scratch machine, run the upgrade there, and run your application's tests against the result. Note the time each step took: that is your downtime. Keep the old cluster until you are sure; with --link that is only possible if you have the backup.

When to use, when not to

Situation✅ Do this❌ Not this
Hundreds of short-lived application connectionsA pooler in transaction mode, with the application free of session stateRaising max_connections to 2000
An app that uses SET, temp tables or session advisory locksSession pooling, or change the app to SET LOCAL and transaction-level locks firstSwitching to transaction mode and hoping
A long-lived LISTEN connectionA direct connection to PostgreSQL for that one sessionSending it through a transaction pooler
A new feature that exists as an extensionCheck it is supported on the target (including managed services), then CREATE EXTENSION in one databaseInstalling it everywhere "just in case"
Security fixes for the current major versionApply every minor update, with a restartStaying on the 18.0 you installed
A small database moving to a new majorDump and restoreBuilding a logical replication setup for 2 GB
A multi-terabyte database moving to a new majorpg_upgrade --link or logical replication, after a rehearsalA dump and restore that needs a day of downtime

Summary

  • A connection is a backend process: slow to open, memory-hungry to keep, and useful only while it runs queries on a core. Raising max_connections is rarely the fix.
  • A transaction-mode pooler such as pgbouncer shares few server connections between many clients, and breaks session state: SET, named prepared statements, session advisory locks, temp tables, LISTEN.
  • An extension is installed per database with CREATE EXTENSION; pg_available_extensions shows what you can install and ALTER EXTENSION … UPDATE moves it to a newer version.
  • A minor update (18.5 to 18.6) swaps the binaries and restarts. A major upgrade (17 to 18) needs pg_upgrade, a dump and restore, or logical replication.
  • Rehearse a major upgrade on a restored backup and time it. The course image runs PostgreSQL 18.6.
