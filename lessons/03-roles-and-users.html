Lesson 03 · Part 1

Roles and users

lesson 03Docker exerciseslive playground

PostgreSQL has one kind of account, the role. A “user” is a role that may log in; a “group” is a role that other roles belong to. Everything that acts on the database (connecting, owning, reading, changing) is done by a role. This lesson shows what a role is, how logging in is decided, and how roles combine.

Learning goals

  • Explain why PostgreSQL has roles rather than separate “users” and “groups”.
  • Create login roles and group roles, and tell them apart with \du and pg_roles.
  • Set role attributes (LOGIN, CREATEDB, CREATEROLE, CONNECTION LIMIT, VALID UNTIL).
  • Grant one role to another, and explain what INHERIT changes.
  • Use SET ROLE and current_user versus session_user to see who is acting.
  • Explain, in one sentence, how pg_hba.conf and roles fit together when a client connects.

Set up for this lesson

Use the shop database. The exercises create roles whose names start with lab_; the checker removes them for you. Start with ./pg up if the container is not running.

\du lists the roles. You should see only postgres, plus the built-in pg_* roles that PostgreSQL ships with. The postgres role is the superuser the Docker image creates.

1. There is only one thing: the role

In PostgreSQL, “user” and “group” are not separate concepts. Both are roles. The difference is one attribute: whether the role may log in. The command CREATE USER is a shorthand for CREATE ROLE … LOGIN, and nothing more.

playground create two roles, then look at the catalogue

The column rolcanlogin is the whole distinction. A role with rolcanlogin = false is a group: you can grant privileges to it and make other roles members of it, but no client can connect as it.

Where the catalogue lives

Roles are stored once for the whole server, in pg_authid. The view pg_roles hides the password hash. Roles are cluster-wide: a role created in shop exists in postgres too. That is why the course checker has to clean up after itself.

2. Attributes: what a role is allowed to do

Beyond privileges on objects, a role has a handful of attributes that grant server-wide powers. The ones you will meet most often:

AttributeDefaultWhat it allowsCaution
LOGINno (for CREATE ROLE)Connect to the serverWithout it, the role is a group
SUPERUSERnoBypasses permission checks, including row-level securityNever give this to an application role
CREATEDBnoCreate databasesGrants nothing on existing data
CREATEROLEnoCreate, alter and drop other rolesCan grant itself most things if careless
BYPASSRLSnoIgnore row-level security policiesReporting roles only, deliberately
INHERITyesUse the privileges of roles it is a member of, automaticallySee section 4
CONNECTION LIMIT n−1 (no limit)At most n simultaneous sessionsProtects the server from one runaway client
VALID UNTILneverPassword stops working at this timeExpiry is checked at login, not during a session

A superuser is not a safer administrator

SUPERUSER bypasses privilege checks and row-level security, and can run COPY ... FROM PROGRAM, which executes commands on the server's operating system. An application that connects as a superuser turns a single SQL injection into control of the database host. Give applications an owner role or a narrow role instead (lesson 4 and lesson 5).

3. Membership: roles inside roles

A role can be a member of another role. This is how you manage privileges for many people at once: grant the privileges to a group role, then add people to the group.

4. INHERIT and SET ROLE

Membership comes with two different mechanisms, and the difference matters when you debug a permission error.

  • INHERIT (the default): the member automatically uses the privileges of the groups it belongs to.
  • NOINHERIT: the member does not use the group's privileges until it explicitly switches to the group with SET ROLE.

Read step 1 carefully. set role contractor made the session act as contractor, but contractor was created NOINHERIT, so it does not automatically use the group's SELECT. In step 2, set role auditors switches to the group itself, and the privilege is there. The error in step 1 is the permission system doing its job, not a bug.

Membership is not a password check

Membership lets you act as a role, not log in as it. Any member of a role may run SET ROLE to it, so a login role that is a member of a powerful role inherits that power whenever it chooses. Review memberships of powerful roles as carefully as you review the roles themselves.

5. Who is acting? current_user and session_user

Two functions answer “who am I?”, and they differ after SET ROLE:

  • session_user — the role that logged in on the connection. It does not change.
  • current_user — the role whose privileges are used right now. SET ROLE changes it.

Audit trails should record session_user, because it identifies the human or service that connected. Permission checks use current_user. The SET ROLE example above is the reason both exist.

6. Logging in: pg_hba.conf

Creating a login role does not, on its own, let anyone connect. Before it checks a password, the server decides whether a connection may use that method at all, by reading pg_hba.conf (host-based authentication). Each line says: for this kind of connection, this database, this role, from this address, use this method. The first matching line wins.

You can read the live rules from SQL, which is safer than opening the file in a container:

In the course container the image's defaults apply. Connections over the local socket or from 127.0.0.1 use trust: no password is asked, which is why ./pg psql-as works without one. Connections from any other address use scram-sha-256, and a wrong password is rejected. You can see this yourself: connecting over the container's network address with a wrong password fails with password authentication failed.

trust is for a laptop, never for a server

trust means “let anyone in, no questions asked” for the matching addresses. It is the image's convenience for the course. On a real server, every line that reaches the network should use scram-sha-256 (or a certificate method), and trust should not appear at all.

Passwords are stored as SCRAM-SHA-256 verifiers (show password_encryption; confirms the default). A LOGIN role created without a password can still connect where trust applies, but it cannot connect where a password method is required.

Try it

Create a role with a password, then try two connections: ./pg psql-as (trusted, no prompt), and the same role over the network address with a wrong password (rejected). Remove the role afterwards with ./pg clean-roles.

When to use, when not to

Situation✅ Do this❌ Not this
One application connects to the databaseOne login role for the app, with only the privileges it needsConnect as postgres
Ten people need the same read accessA group role holding the privileges, and ten login roles as membersGrant to ten roles one at a time
A reporting tool needs to read everythingA read-only group role (pg_read_all_data is built in)A superuser account
A developer wants to test as a restricted userSET ROLE in a transaction, or a dedicated login roleChanging privileges on the owner role
A password must expireVALID UNTIL, plus your secrets manager's rotationA calendar reminder

Summary

  • A role is the only account type. LOGIN makes it a user; without it, it is a group.
  • Attributes (SUPERUSER, CREATEDB, CREATEROLE, …) grant server-wide powers. Use the smallest set that works.
  • Grant privileges to group roles and add members to them, rather than granting to many people one by one.
  • INHERIT applies a group's privileges automatically; SET ROLE switches to them explicitly.
  • session_user is who connected; current_user is whose privileges count now.
  • pg_hba.conf decides which authentication method a connection must pass; roles decide what it may do afterwards.
