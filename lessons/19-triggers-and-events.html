Lesson 19 · Part 5

Triggers, LISTEN/NOTIFY and audit

lesson 19Docker exerciseslive playground

A trigger is a function that PostgreSQL runs for you when a row or a table changes. It is how you keep an audit trail that no application can forget to write, how you clean values on the way in, and how you tell other programs that something happened. This lesson covers row and statement triggers, event triggers for DDL, and LISTEN/NOTIFY, with the rules about transactions that catch people out.

Learning goals

  • Write a trigger function and attach it with CREATE TRIGGER.
  • Choose between BEFORE and AFTER, and between FOR EACH ROW and FOR EACH STATEMENT.
  • Use NEW, OLD, TG_OP and a WHEN condition to react only to the changes you care about.
  • Build an audit table that records who changed what, and say what such a table cannot guarantee.
  • Write an event trigger that logs or blocks DDL commands.
  • Explain when a NOTIFY is delivered, and why a rolled-back transaction sends nothing.

Set up for this lesson

Use the shop database. The playgrounds run in your browser, share one database, and are meant to be run in order (press Reset data to start again). Triggers fire in the browser engine exactly as on the server. LISTEN/NOTIFY needs two connections, which the single-user browser engine does not have, so that part is explained with psql output from the Docker database.

1. A trigger has two parts

A trigger is made of a trigger function (a function with no arguments that returns the special type trigger, usually written in PL/pgSQL, see lesson 18) and a CREATE TRIGGER statement that says when to call it. Inside the function, PostgreSQL gives you variables: NEW (the row being written), OLD (the row as it was), TG_OP (the words INSERT, UPDATE or DELETE) and TG_TABLE_NAME.

The first example cleans an e-mail address on the way in. It is a BEFORE trigger: it runs before the row is stored, so it can change NEW, and what it returns is what gets stored.

2. BEFORE or AFTER, ROW or STATEMENT

Two choices decide how a trigger behaves:

What it meansUse it for
BEFORERuns before the change is made. May edit NEW, or return NULL to skip the row, or raise an error to refuse it.Cleaning values, defaults that need logic, extra validation
AFTERRuns after the change, when all constraints have been checked. Cannot change the row. Its return value is ignored.Audit logs, updating summary tables, sending notifications
FOR EACH ROWCalled once per affected row. NEW and OLD are available.Anything that depends on the row's values
FOR EACH STATEMENTCalled once per statement, even if it touched zero rows. No NEW or OLD row, but it can read transition tables.Cheap bulk bookkeeping, “something changed” signals

A transition table is a temporary table of all the changed rows that a statement-level AFTER trigger can query. It lets you handle a 100,000-row update with one function call instead of 100,000:

playground one call per statement, however many rows

Both statements logged one row each: the first counted 7 delivered orders, the second counted zero. A row-level trigger would have run seven times for the first statement and not at all for the second.

The order triggers run in

For one statement the order is: BEFORE statement triggers, then for each row the BEFORE row triggers, the change itself, and the AFTER row triggers, then finally the AFTER statement triggers. When one table has several triggers of the same kind, they run in alphabetical order of their names, which is a quiet way to build surprises. Keep the number of triggers per table small.

3. Refusing a change, and conditions with WHEN

A trigger that raises an error cancels the whole statement. Combined with OLD and NEW, that makes a rule about transitions, which a CHECK constraint cannot express because it only sees the new row:

playground this one fails on purpose

Order 1 is delivered, so the update is refused with order 1 cannot go back to pending from delivered. The WHEN (...) clause is evaluated by PostgreSQL before it calls your function, so rows that do not match cost almost nothing. Use it whenever you only care about some changes: when (old.status is distinct from new.status) is the usual way to say “the status actually changed”. (IS DISTINCT FROM is the NULL-safe version of <>.)

Return values in BEFORE triggers

A BEFORE ... FOR EACH ROW trigger must return new (for insert and update) or return old (for delete) to carry on. Returning NULL silently skips that row. Forgetting the return makes every insert or update vanish without an error, which is a classic first-trigger bug.

4. Audit trails

An audit trail records who changed what, and when. The standard pattern is an AFTER row trigger that writes the old and new row, as jsonb, into a log table:

playground audit every change to shop.products

Four changes, four log rows. The default session_user records the role that connected, not the one a SET ROLE or a SECURITY DEFINER function switched to (lesson 3). Because the trigger lives in the database, a script that connects with psql is audited just like the web application.

An audit table is only as trustworthy as its permissions

A superuser or the table's owner can disable the trigger or edit the log. Give the application role no UPDATE, DELETE or TRUNCATE on the log table, keep the trigger function owned by a role the application cannot become, and ship the log elsewhere if it must be tamper-proof. Triggers also add write cost to every statement on the table, and the log grows without limit unless you partition and drop it (lesson 20).

Triggers are invisible

Nothing in an INSERT statement tells the reader that a trigger changed the row or wrote somewhere else. Row triggers do not fire for TRUNCATE; that needs a separate BEFORE TRUNCATE trigger. Bulk loads can switch triggers off with ALTER TABLE ... DISABLE TRIGGER, a deliberate and privileged act, and changes made that way leave no audit row. List them with select tgname, tgrelid::regclass from pg_trigger where not tgisinternal; or \d tablename in psql.

5. Event triggers: reacting to DDL

A normal trigger watches rows. An event trigger watches commands that change the schema: CREATE, ALTER, DROP. It belongs to the whole database, only a superuser can create one, and it fires on one of four events: ddl_command_start, ddl_command_end, sql_drop and table_rewrite. Inside it, pg_event_trigger_ddl_commands() lists what was just done.

playground log every DDL command

You should see CREATE TABLE, ALTER TABLE and CREATE INDEX (on the Docker database the index is named public.t_demo_note_idx). An event trigger can also refuse a command by raising an error: on sql_drop, raise exception cancels any DROP. On the Docker database this printed dropping objects is blocked in this database (DROP TABLE), and the table survived.

A broken event trigger blocks DDL until you remove it

If an event trigger always fails, every matching CREATE, ALTER or DROP fails with it. You can still get out: commands on event triggers themselves never fire event triggers, so a superuser can run drop event trigger name; (or alter event trigger name disable;). The setting event_triggers (default on) lets a superuser switch all of them off for a session. Test event triggers on a scratch database first.

6. LISTEN and NOTIFY

NOTIFY channel, 'payload' sends a short text message to every session that has run LISTEN channel. It gives you a push signal from the database to a worker without polling. A trigger is the natural sender:

These are the rules, each one verified with two psql sessions on the Docker database:

  • Delivery happens at commit. A notification sent inside a transaction waits until that transaction commits. A ROLLBACK throws it away: a rolled-back pg_notify never arrived.
  • Identical notifications in one transaction collapse into one. Two notify order_events, 'same' statements in one transaction reached the listener once. Different payloads, or the same payload from different transactions, each arrive.
  • Delivery is not durable. A listener that is not connected when the notification is sent never receives it. Nothing is stored or replayed.
  • The payload is small (under 8000 bytes). Send an id, and let the listener query the row.
  • The queue is bounded. A listener that stays inside a long transaction stops the queue from draining; when it fills, NOTIFY starts to fail at commit. pg_notification_queue_usage() shows how full it is (a fraction between 0 and 1).
NOTIFY is a doorbell, not a message queue

Use it to wake a worker up, and have the worker read the real work from a table (with FOR UPDATE SKIP LOCKED, lesson 16). On start-up the worker must also read what it missed while it was away. If you need guaranteed delivery, a table is the queue and NOTIFY is only the hint to look at it. Also remember that connection poolers in transaction mode break LISTEN, because your session is not yours between statements (lesson 26).

When to use, when not to

Situation✅ Do this❌ Not this
Every change to a table must be recordedAn AFTER row trigger writing to an audit table, with restricted permissionsHoping every application does it
A value must be cleaned or filled inA BEFORE row trigger (or a generated column or default, when they are enough)An AFTER trigger that updates the row again
A rule about one row's valuesA CHECK constraintA trigger
A rule about how a value may changeA BEFORE UPDATE trigger using OLD and NEWApplication-only checks
A big bulk update must be summarisedA statement trigger with a transition tableA row trigger that does a query per row
Wake a worker up when data arrivesNOTIFY from a trigger, plus a table the worker readsUsing NOTIFY as the only copy of the message
Complex business workflowsApplication code or explicit procedures you can read and testChains of triggers that fire other triggers

Summary

  • A trigger is a trigger function plus a CREATE TRIGGER. NEW, OLD and TG_OP describe the change.
  • BEFORE triggers can change or refuse a row; AFTER triggers observe it. Row triggers run per row; statement triggers run once and can read transition tables.
  • WHEN filters cheaply before the function is called.
  • An audit trigger writes old and new rows to a log table; guard that table with permissions.
  • Event triggers react to DDL and can log or block it; a broken one can block you, so test on a scratch database.
  • NOTIFY is delivered on commit, dropped on rollback, de-duplicated within a transaction, and not stored. Treat it as a doorbell.

Looking ahead

Audit tables and event logs grow forever, which is exactly the case where one big table becomes a problem. Lesson 20 shows how to split a table into partitions, how queries skip the partitions they do not need, and how dropping a partition replaces a slow bulk delete.
