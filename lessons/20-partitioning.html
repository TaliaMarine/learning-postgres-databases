Lesson 20 · Part 5

Partitioning

lesson 20Docker exerciseslive playground

Partitioning splits one big table into smaller physical tables that still look like one table to your queries. Done well, queries read only the pieces they need, and old data disappears by dropping a piece instead of deleting millions of rows. Done for the wrong reason, it adds complexity and speeds up nothing. This lesson shows both, using analytics.events as the worked example.

Learning goals

  • Create range, list and hash partitioned tables and say which one fits which data.
  • Explain why a primary key on a partitioned table must contain the partition key.
  • Read an EXPLAIN plan to see which partitions were skipped (partition pruning), and write queries that allow it.
  • Use a default partition, and explain what it costs when you add a new partition later.
  • Remove old data with DETACH PARTITION and DROP TABLE, and attach a ready-made table as a partition.
  • Decide when a table should not be partitioned.

Set up for this lesson

Use the shop database, where analytics.events holds one million rows. The examples build a copy called analytics.events_p, so the original stays as it is for the other lessons; run them in a scratch database (./pg sql "create database lab_scratch template shop_template", then ./pg psql lab_scratch) if you want to keep shop clean. Copying the rows takes a few seconds.

The playgrounds use the small in-browser events table (240 rows, all in the first nine days of January 2025), so they partition by days rather than months. They show that pruning happens, but not how much time it saves: the data is too small for that, so plans and counts there differ from the Docker output below. Every plan on this page uses EXPLAIN (COSTS OFF) without timings so it stays stable.

1. What partitioning is, and what it is for

A partitioned table is an empty shell with a rule. The rows live in partitions: ordinary tables that each hold the rows matching part of the rule. You insert into and query the parent; PostgreSQL routes each row to its partition and, for queries, looks only into the partitions that can match.

There are two real reasons to do this, and one popular wrong one:

  • Retention. Dropping a partition is instant and leaves no dead tuples. A DELETE of 80,000 old rows is slow, writes WAL, and needs vacuum afterwards.
  • Pruning for big scans. Reports that read one month of a table that holds years read only that month's partition.
  • “It will make everything faster.” It will not. A query that does not filter on the partition key reads every partition, and the planner has more work to do. A well-indexed single table is often faster for lookups by id.

2. Range partitioning: events by month

Range partitioning fits data with a natural ordering, above all time. Each partition has a half-open range: FROM is included, TO is not. That is why one partition can end at 2025-02-01 and the next can start there with no gap and no overlap.

Notice id has no generated always as identity here. For a copy you keep the old ids; for a new table, an identity column on the parent is fine (new partitions inherit it), but you cannot attach an existing table that has its own identity column.

3. The primary key must include the partition key

PostgreSQL enforces uniqueness inside each partition's own index; it has no index that spans partitions. So a unique constraint on the parent can only be guaranteed if the partition key is part of it, which forces every duplicate to land in the same partition. The error is unique constraint on partitioned table must include all partitioning columns. The usual answer is the composite key (id, occurred_at). It has a consequence worth knowing: id on its own is not guaranteed unique any more. On the Docker database, inserting a second row with id = 5 but a different occurred_at succeeds, and select count(*) from analytics.events_p where id = 5 returns 2. If other tables must reference a row by id alone, you need another design: keep the ids from a sequence (as identity does) and treat uniqueness as a property of the generator, not of the table.

4. Partition pruning

Pruning means the planner leaves out partitions that cannot contain matching rows. Look for it in EXPLAIN: the pruned partitions are simply absent from the plan.

Three more cases, each tested on the same twelve partitions:

  • A range that straddles two months (2025-03-15 to 2025-04-15) scans exactly events_2025_03 and events_2025_04, and nothing else.
  • A filter on another column (where kind = 'purchase') cannot prune. All 13 partitions, the default included, are scanned.
  • A filter that wraps the key in a function (where date_trunc('month', occurred_at) = '2025-03-01') cannot prune either, even though it is logically one month. All 13 partitions are scanned. Compare the column itself with a range, as above.

Pruning also works for values the planner learns at run time, such as a parameter or a subquery result. In that case the plan shows the partitions that remain as Subplans Removed: N. For where occurred_at >= date_trunc('month', now()), the plan of the twelve-month 2025 table shows Subplans Removed: 12 and a single scan of the default partition: now() is later than every defined range, so only the default partition could hold such rows. (The result depends on the day you run it, because now() does.)

Pruning needs the key in the WHERE clause, as itself

The setting enable_partition_pruning is on by default; leave it on. What turns pruning off in practice is the query: a condition on another column, a cast or function around the partition key, or a join where the key value comes only from another table. Check with EXPLAIN every time you add partitioning, and count the partitions in the plan.

5. The default partition and its cost

Without a default partition, inserting a row that matches no range fails with no partition of relation found for row. A default partition catches such rows instead, which avoids lost writes when you forget to create next month's partition. But it has a price. Insert a row from March 2026 into the 2025 table and it lands in the default partition:

Creating a partition for a range that the default partition already holds rows for is refused. PostgreSQL must prove the default partition has no row that belongs in the new one. To fix it, move the rows out first: detach the default partition, create the new one, insert the rows into the parent, then attach the default partition again. A default partition also makes DETACH PARTITION ... CONCURRENTLY impossible (cannot detach partitions concurrently when a default partition exists), and when it grows large, pruning cannot skip it for any range that might reach beyond the defined ones.

Create partitions ahead of time

Whether or not you keep a default partition, a scheduled job (the pg_partman extension, or your own cron job) should create the next few months of partitions in advance. Monitor the default partition: if its row count is not 0, something is writing data your partition scheme did not expect. It is a smoke alarm.

8. Indexes and other limits

  • Indexes created on the parent (create index on analytics.events_p (kind)) are created on every partition, and on partitions you add later. Each partition has its own, smaller index.
  • Uniqueness across partitions is only possible with the partition key in the index (section 3).
  • Many partitions cost planning time. Hundreds are fine; tens of thousands are not. Do not partition by hour "just in case".
  • Autovacuum works per partition. Old, no-longer-written partitions are vacuumed once and then left alone, which is a quiet benefit for append-only data.
  • You cannot convert in place. Changing a normal table to a partitioned one means creating the new structure and copying the rows (as the exercises do), or detaching and attaching in stages.
Do not partition a small or well-indexed table

A table of a few million rows that you query by id through an index gains nothing from partitioning, and every query that cannot prune pays for it. Reasonable reasons to partition are a table too big to maintain as one piece (vacuum, index builds and backups taking too long), and a retention rule that matches the key. If neither applies, add the right index instead (lesson 12).

Summary

  • A partitioned table is a shell; rows live in partitions chosen by RANGE, LIST or HASH on the partition key.
  • A primary key or unique constraint must include the partition key, so id alone is no longer guaranteed unique.
  • Pruning skips partitions the WHERE clause rules out, but only if you compare the key itself. Check the plan, without timings.
  • A default partition catches stray rows, but blocks creating a partition that overlaps its rows and blocks DETACH ... CONCURRENTLY.
  • Retention by DETACH and DROP is instant and leaves no bloat. That is the strongest reason to partition.
  • Do not partition small tables, or by a column queries ignore.
