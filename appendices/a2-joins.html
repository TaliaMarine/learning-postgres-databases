Annex

A2. Joins and combining tables

A join puts rows from two tables side by side, using a condition that says which rows belong together. The join type decides what happens to the rows that have no partner. This annex shows every join type on the shop tables, with a picture of which rows survive and a playground for each.

Set up

The playgrounds run a real PostgreSQL 18 in your browser on a small copy of the shop (8 customers, 8 products, 12 orders). In that copy, customer 6 (Finn Smit) has never ordered, and the product “Retro kettle” has never been sold. Those two rows are what make the differences between join types visible. To try the same queries on the Docker database, use ./pg psql; the names are the same, the row counts are larger.

1. Why joins exist

Data is split across tables so that each fact is stored once. An order stores a customer_id, not the customer's name. To print “Anna Jansen ordered …” you need both tables, joined on orders.customer_id = customers.id. That condition is the ON clause. A column that points at another table's key is a foreign key; you will meet the constraint itself in lesson 7.

2. INNER JOIN: only the matches

INNER JOIN (plain JOIN means the same) keeps a row only when the ON condition finds a partner on the other side. Rows without a partner disappear from the result.

playground orders with the customer's name

Notice the table aliases o and c. They keep the query short, and they are required whenever both tables have a column of the same name (here both have id), because id alone would be ambiguous.

3. LEFT, RIGHT and FULL: keep the lonely rows

An outer join keeps rows that have no partner and fills the other side with NULL.

  • LEFT JOIN keeps every row of the table written before the word JOIN.
  • RIGHT JOIN keeps every row of the table written after it. It is a mirror image; most people just swap the tables and use LEFT JOIN.
  • FULL JOIN keeps the unmatched rows of both sides.

Now the same idea on real tables. Customer 6 has no orders, so a LEFT JOIN from customers keeps her:

playground LEFT JOIN: every customer, with or without orders

Look for the customer whose order_id and total are NULL. An inner join would have dropped her. A customer with three orders appears three times; a join repeats the left row once per matching right row.

FULL JOIN is rare, and useful for comparing two sets. Below, the left side is the active customers and the right side is the delivered orders. A row with a NULL name is a delivered order whose customer is not active. A row with a NULL order is an active customer with no delivered order.

4. The anti-join: rows with no partner

“Which customers never ordered?” asks for rows that have no match. Do a LEFT JOIN, then keep only the rows where the right side came back empty. Test a column that can never be NULL in a real row, such as the right table's primary key.

playground anti-join: customers who never ordered

The same question for products that were never sold. Change it to compare with NOT EXISTS, which says the same thing and is often easier to read (annex A4):

playground products never ordered, two ways

5. ON versus WHERE in an outer join

With an inner join, a condition in ON and the same condition in WHERE give the same rows. With an outer join they do not. ON decides which rows match; WHERE filters the result afterwards, and it also removes the NULL-filled rows you just asked for.

playground same condition, two places, different results
A WHERE on the optional side turns a LEFT JOIN into an inner join

If you LEFT JOIN and then write WHERE right_table.column = …, the NULL-filled rows can never pass, so you have quietly written an inner join. Put conditions about the optional table in ON, unless you are deliberately testing for IS NULL (the anti-join).

6. USING versus ON

When the two columns have the same name, USING (col) is a shorthand for ON a.col = b.col, and it merges the pair into a single output column. With ON you get both columns under the same name.

playground USING returns the shared column once

The result has one customer_id column. Rewrite the join as join (…) c on c.customer_id = shop.orders.customer_id and select * returns it twice. Use USING when your columns are named consistently, and ON for anything else, including conditions that are not plain equality.

Skip NATURAL JOIN

NATURAL JOIN joins on every column the two tables share by name. Adding a column to either table later can silently change the join. Name your join columns.

7. A self join: a table joined to itself

Some tables point at themselves. shop.customers.referred_by holds the id of the customer who referred this one, and shop.categories.parent_id points at the parent category. To read both rows in one result, join the table to itself and give each use a different alias.

playground who referred whom

It is a LEFT JOIN because most customers were not referred by anyone, and you still want them in the list. For trees that go more than one level deep, see recursive queries in lesson 8.

8. CROSS JOIN: every combination

CROSS JOIN has no ON. It pairs every row on the left with every row on the right, so m rows and n rows give m × n rows. It is useful for building a grid, such as every country with every status, to fill in the combinations that have no data.

playground a grid of country by status, then fill it with counts
The accidental cross join

Writing from a, b (a comma) and forgetting the join condition in WHERE gives a cross join. Two tables of 20,000 and 200,000 rows would try to produce four billion rows. Prefer the explicit JOIN … ON syntax, so a missing condition is a syntax error instead of a silent explosion.

9. When a join multiplies rows

A join returns one row per matching pair. If one order has three items, joining orders to items gives three rows for that order, and sum(orders.total) over the join would count its total three times. Check the row count after each join you add, and aggregate before joining when you only want one row per parent (annex A3).

playground the order total is counted once per item

10. Combining result sets: UNION, INTERSECT, EXCEPT

Joins combine tables sideways. Set operations stack the results of two queries vertically. The two queries must return the same number of columns with compatible types.

  • UNION — all rows from both, duplicates removed. UNION ALL keeps duplicates and is faster.
  • INTERSECT — rows that appear in both.
  • EXCEPT — rows in the first that are not in the second.
playground countries customers live in versus countries orders ship to

Summary

  • JOIN … ON pairs rows that satisfy a condition. Unmatched rows are dropped by an inner join.
  • LEFT JOIN keeps every left row; RIGHT JOIN keeps every right row; FULL JOIN keeps both. Missing sides are NULL.
  • An anti-join is LEFT JOIN … WHERE right.key IS NULL, or NOT EXISTS.
  • Put conditions on the optional table in ON, not WHERE.
  • USING (col) shortens equal-named columns and merges them; ON works for everything.
  • A self join needs two different aliases for the same table.
  • CROSS JOIN returns m × n rows. Joins can multiply rows; count after each one.
