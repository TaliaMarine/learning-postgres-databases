Annex

C. Catalog and diagnostic queries

Everything PostgreSQL knows about itself is stored in tables you can query: the system catalogs (pg_catalog), the standard information_schema views, and the statistics views (pg_stat_*). This annex is a library of copy-paste queries for everyday questions, from “how big is this table?” to “who is blocking whom?”. They are all read-only.

How to use this page

Every query here was run against the course's Docker database (./pg psql, database shop). The structural ones (tables, columns, keys, roles, privileges) also have a playground, which runs on the small in-browser copy, so the sizes and row counts there are tiny. Queries about live activity, locks and statistics have no playground: the browser database has no other sessions and almost no history, so they return nothing useful there. Run those in Docker.

The three sources, in one sentence each:

  • pg_catalog — PostgreSQL's own tables (pg_class, pg_namespace, pg_attribute, pg_roles, …). Complete and precise; specific to PostgreSQL.
  • information_schema — views defined by the SQL standard. Portable between databases, but they only show objects you have some privilege on, and they hide PostgreSQL-specific detail.
  • pg_stat_* and pg_statio_* — counters and live state: sessions, scans, dead rows, cache hits. Counters accumulate since the last statistics reset.
Learn the catalogs from psql

\set ECHO_HIDDEN on in psql prints the catalog query behind every \d command (annex B). That is how most of the queries below started.

1. Tables and their sizes

pg_relation_size is the table's main data. pg_indexes_size is all its indexes. pg_total_relation_size is everything, including TOAST (out-of-line storage for large values). reltuples is the planner's row estimate, refreshed by ANALYZE and autovacuum; it is -1 for a table that has never been analysed. Use count(*) when you need the exact number.

This one does not list views directly: a view depends on the table through its rewrite rule, so for views it is easier to try DROP … RESTRICT inside a transaction and read the error (annex E).

5. Roles and memberships

playground roles with attributes and memberships

pg_roles is the readable view of pg_authid, with the password hash hidden. Membership is in pg_auth_members. In PostgreSQL 16 and later each membership carries three options: admin_option (may grant the role to others), inherit_option (privileges apply automatically) and set_option (may SET ROLE to it). See lesson 3.

6. Privileges

Table privileges with aclexplode

Privileges are stored as an ACL (access control list) array on each object, such as {postgres=arwdDxtm/postgres,lab_reader=r/postgres}. aclexplode turns it into one row per grantee and privilege. A NULL ACL means “the defaults”, which is why the query substitutes acldefault('r', owner): the owner has everything, nobody else has anything.

playground table privileges, one row per grantee and privilege

Grantee PUBLIC (stored as OID 0) means every role. The same information from the standard views, limited to tables you can see:

The two differ in one detail: information_schema does not know the MAINTAIN privilege (VACUUM, ANALYZE, REINDEX and friends, granted by the letter m), so it shows seven privileges where aclexplode shows eight.

Schema privileges

playground schema privileges

On PostgreSQL 15 and later, the public schema is owned by pg_database_owner and PUBLIC has only USAGE on it, not CREATE. The course database shows exactly that.

Default privileges

Default privileges apply to objects created in the future by a given role (ALTER DEFAULT PRIVILEGES, lesson 4). An empty result means none are defined, as in a fresh course database.

7. Sessions and activity

pg_stat_activity has one row per server process. Filter on backend_type = 'client backend' to see only client connections, not autovacuum, the checkpointer and the other background processes. The state column is active (running a query), idle (waiting for the client), or idle in transaction (a transaction is open and nothing is happening, which holds locks and blocks vacuum).

Long-running queries and transactions

Change the threshold to suit you. To stop one, select pg_cancel_backend(pid) cancels its current query; select pg_terminate_backend(pid) closes its connection. Both need you to be the same role or have the pg_signal_backend role (or be a superuser).

9. Unused indexes

pg_stat_user_indexes.idx_scan counts how often each index was used since statistics were last reset. An index with zero scans costs space and slows every write, and helps nobody. Leave out unique indexes: they enforce a rule even if no query ever reads them.

In the course database this returns no rows, because every index there is a primary key or unique constraint. To see the counters for all indexes:

Zero scans on this server is not zero scans everywhere

The counters are per server and since the last reset. An index that a replica uses for reports, or that a monthly job needs, shows idx_scan = 0 on the primary. Check when the counters were last reset (stats_reset in pg_stat_database; empty means never) and look at every replica before dropping one.

10. Dead tuples and a rough bloat check

A dead tuple is an old row version that an UPDATE or DELETE left behind, waiting for vacuum. Many dead tuples, or a table much larger than its live rows need, is bloat (lesson 17).

A rough size check: the table's actual size compared with the size its live rows would need (average row width from pg_stats, plus a 24-byte row header, plus 15% for page overhead). It needs fresh statistics (ANALYZE) and is a hint, not a measurement. A ratio near 1 is healthy; a large ratio on a large table is worth a look. The pgstattuple extension gives exact numbers.

Read it with judgement: shop.categories has a ratio of 13.7 because a table never takes less than one 8 kB page, and 13 rows fill a fraction of one. shop.orders at 2.4 is the interesting row: updates in other lessons left space behind.

11. Databases, settings and the server

source says where a value came from: configuration file, command line (the course container sets a few with -c), database, user, client or session (lesson 21).

playground installed extensions

Cache hits and sequential scans

pg_statio_user_tables counts table blocks found in shared buffers (hit) versus read from the operating system (read; the OS may still have had them in its own cache). pg_stat_user_tables counts sequential and index scans. A big table with many sequential scans and a large seq_tup_read is often missing an index.

Transaction ID age

Each database's oldest unfrozen transaction ID must stay well below about two billion, or PostgreSQL stops accepting writes to protect the data. Autovacuum takes care of this; this query lets you check that it does (lesson 17).

12. The most expensive statements

The pg_stat_statements extension, installed in the course database, groups statements by their shape and records calls and time. Sort by total_exec_time to find the queries that cost the server the most overall. The workflow built on it is lesson 14.

select pg_stat_statements_reset(); starts the counters over, which is useful before measuring a change.
