Annex

A5. Creating and changing things

So far you have only read data. This annex covers the statements that create and change things: DDL (data definition language: CREATE, ALTER, DROP) and DML (data manipulation language: INSERT, UPDATE, DELETE). It also shows transactions, which let you make several changes and keep them all or none, and the basic constraints that keep bad data out.

Set up

The playgrounds here run PostgreSQL 18 in your browser. Each block starts with drop table if exists, so you can run it as often as you like. It creates tables of its own, such as shop.wishlist; it does not touch the shop tables. The playground keeps one database per page, so a table made in one block is visible in the next, and Reset data starts over.

If you want to try DDL on the Docker database, do not do it in shop. Make a scratch copy and throw it away afterwards:

shop_template is a pristine copy of the shop that the course keeps for exactly this purpose. Any database whose name starts with lab_ is removed by ./pg clean-roles too.

1. CREATE TABLE

CREATE TABLE names the table, then lists its columns, each with a type and optional rules. The table here belongs to the schema shop; without a schema prefix it goes into the first schema of your search_path (usually public).

playground create a table and look at it

Common column types you will use first:

TypeHolds
integer, bigint, smallintWhole numbers (4, 8 and 2 bytes)
numeric(10,2)Exact decimals: 10 digits in all, 2 after the point. Use it for money.
textStrings of any length. varchar(n) adds a length limit and nothing else.
booleantrue, false or NULL
date, timestamptzA day; a moment in time (stored in UTC, shown in your time zone)

There are many more, and a few traps. They get a full lesson: lesson 6.

2. The basic constraints

A constraint is a rule the database enforces on every write. If a statement would break it, PostgreSQL rejects the statement with an error and changes nothing.

ConstraintRuleExample
NOT NULLThe column must have a valueemail text not null
DEFAULTValue used when the insert gives none (not a restriction)status text default 'active'
PRIMARY KEYUnique and not null: identifies one rowid integer primary key
UNIQUENo two rows may have the same value (NULLs are allowed, and do not clash)unique (customer_id, product_id)
CHECKAn expression that must not be falsecheck (priority between 1 and 5)
FOREIGN KEY (REFERENCES)The value must exist in another table's keycustomer_id integer references shop.customers (id)

generated always as identity gives the column an automatic number from a sequence, and refuses hand-written values unless you say so. Keys, foreign-key actions (ON DELETE …), exclusion constraints and design advice are in lesson 7.

3. INSERT

INSERT INTO table (columns) VALUES (…) adds rows. Always name the columns; an insert that depends on the table's column order breaks the day someone adds a column. Columns you leave out get their default (or NULL). Give several rows in one statement, separated by commas: it is shorter and faster than many single inserts.

playground insert several rows at once

(This block assumes you ran the CREATE TABLE block above first. If you get relation "shop.wishlist" does not exist, run that one.) Note the word default in the values list: it asks for the column's default, here 3.

RETURNING: get the new row back

RETURNING makes INSERT, UPDATE and DELETE send back the rows they changed, including values the database made up, such as an identity number or a default. It saves a second query and cannot race with another session.

playground INSERT ... RETURNING

ON CONFLICT … DO NOTHING skips a row that would break a unique rule instead of raising an error. If you run the block twice, the second run returns no rows. The upsert form (DO UPDATE) is in lesson 9.

The error names the constraint (wishlist_priority_check), and no row is inserted. Other errors you can provoke the same way (a duplicate pair, a missing customer, a NULL in a NOT NULL column) are listed with their exact messages in annex E.

4. UPDATE

UPDATE table SET column = value, … WHERE condition changes existing rows. The expression on the right can use the row's current values.

UPDATE and DELETE without WHERE change every row

There is no confirmation prompt. Write the WHERE first, run it as a SELECT to see which rows it picks, and only then turn it into an UPDATE or DELETE. In a real database, do it inside a transaction (section 6) so you can ROLLBACK.

playground UPDATE with a WHERE and RETURNING

To update from another table, use UPDATE … FROM (lesson 9).

5. DELETE

DELETE FROM table WHERE condition removes rows. TRUNCATE table removes all rows at once, faster, but it takes a stronger lock and cannot be filtered.

playground DELETE ... RETURNING shows what went

A foreign key also protects the other direction: you cannot delete a customer who still has orders pointing at them, unless the foreign key was created with ON DELETE CASCADE (which deletes the orders too) or similar. The default is to refuse.

playground a foreign key refusing a delete

6. Transactions: BEGIN, COMMIT, ROLLBACK

A transaction groups statements so they succeed or fail together. BEGIN starts one, COMMIT makes every change permanent, and ROLLBACK undoes them all. Without an explicit BEGIN, each statement is its own transaction and is committed as soon as it finishes (autocommit).

playground change, look, undo

Only the last result is shown, so the block shows the count after the rollback; the delete was undone. Change rollback to commit and run it again to see the other outcome. If a statement fails inside a transaction, PostgreSQL marks the whole transaction as aborted and ignores everything until you ROLLBACK. DDL is transactional in PostgreSQL

Unlike in many databases, CREATE TABLE and ALTER TABLE can be rolled back too. That is a useful safety net for migrations: BEGIN; …changes…; ROLLBACK; shows you whether they work and leaves nothing behind. A few commands cannot run in a transaction, such as CREATE DATABASE and CREATE INDEX CONCURRENTLY.

7. ALTER TABLE

ALTER TABLE changes the structure of a table that already exists. Several actions can be combined in one statement, separated by commas.

playground add, rename and drop things

The forms you will use most:

  • ADD COLUMN, DROP COLUMN, RENAME COLUMN a TO b, RENAME TO new_name
  • ALTER COLUMN c SET DATA TYPE … (may rewrite the table), SET DEFAULT, DROP DEFAULT, SET NOT NULL, DROP NOT NULL
  • ADD CONSTRAINT name …, DROP CONSTRAINT name
On a big, busy table, some ALTERs are not free

Some changes take a strong lock that blocks every other query on the table while they run, and some rewrite the whole table. Adding a column with a constant default is quick in modern PostgreSQL; changing a column's type usually is not. The safe-migration patterns are in lesson 16.

8. DROP

DROP TABLE name removes a table and its data for good, along with its indexes and constraints. IF EXISTS turns "it is not there" from an error into a notice. If other objects depend on the table (a view, or another table's foreign key), PostgreSQL refuses unless you add CASCADE, which drops those too. Treat CASCADE with respect: read what it will remove first.

playground drop the table, safely

to_regclass returns the table's name if it exists and NULL if not. The other objects have the same shape: DROP INDEX, DROP VIEW, DROP SCHEMA, DROP ROLE, DROP DATABASE.

Summary

  • CREATE TABLE lists columns, types and rules. ALTER TABLE changes it, DROP TABLE removes it.
  • Constraints (NOT NULL, PRIMARY KEY, UNIQUE, CHECK, FOREIGN KEY) reject bad writes.
  • INSERT accepts several rows; always name the columns. RETURNING gives back what was written.
  • UPDATE and DELETE need a WHERE; test it as a SELECT first.
  • BEGIN … COMMIT makes changes atomic; ROLLBACK undoes them. DDL is transactional too.
  • Practise on a lab_ database cloned from shop_template, never on a database you care about.
